# Заметки об архитектуре мессенджера

Рабочие предложения для обсуждения. Действующие правила организации кода описаны в [архитектуре проекта](../../fsd-architecture.md).

Начни с [цели и принципов рефакторинга](principles.md). Они объясняют проблему координации и границу между бизнес-модулями, страницами и UI.

Для верхнего уровня выбрано разделение на `applications` (мессенджер, календарь, почта) и общие бизнес-`modules` (каталог пользователей). Внутри мессенджера выбрано `pages → features → model`: страница собирает экран, самостоятельные блоки живут в `features`, данные и операции — в `model`. Составные экраны собираем в `pages`. Слой `widgets` возможен, когда понадобится отдельный составной блок. [Полное дерево и примеры](source-structure.md#дерево) · [Правила импортов](dependencies.md#связи-внутри-мессенджера)

[Проектный навык Workspace module design](../../../.agents/skills/workspace-module-design/SKILL.md) помогает применять эти принципы при обсуждении архитектуры и согласованном рефакторинге.

[Независимое ревью](review.md) фиксирует четыре замечания к плану. Первое разбирается в [общем запуске Workspace](workspace-runtime.md). Это уточнение границы между общими модулями и приложениями.

Для realtime сохраняем композицию обработчиков и один общий курсор на сессию. Сборку переносим из `layout` в runtime Workspace. Если нужный обработчик не готов или упал, транспорт останавливается на последней подтверждённой позиции и повторяет события после восстановления. [Контракт курсора](workspace-runtime.md#контракт-продвижения-курсора) · [Неготовность и сбой](workspace-runtime.md#общий-курсор-и-ещё-не-готовые-потребители)

Каждая авторизованная сессия получает свой runtime и тёплый Zustand-стор для первого экрана. Переключение аккаунта меняет подписку UI, история загружается при открытии чата. [Жизненный цикл и пример кода](workspace-runtime.md#runtime-и-тёплый-стор-на-каждую-сессию)

После второго пункта ревью отправка остаётся внутри `messages`: очередь — его внутренняя часть `outgoing`, а HTTP, история и realtime сходятся в одном сценарии приёма. Отдельный публичный `sending` пока не нужен. [Почему выбрали эту границу](scenarios/send-message.md#решение-отправка-внутри-messages) · [Зависимости](dependencies.md#связи-внутри-мессенджера)

Как пополнять заметки:

1. Начни с этой карты и дополни страницу, которая владеет темой. Для нового сценария добавь страницу и ссылку сюда.
2. Запиши, какую проблему решает модуль и что его граница упрощает. Покажи короткий вызов. Укажи, кто кого вызывает, где хранится состояние, кто вправе его менять и сколько оно живёт.
3. Свяжи пересекающиеся сценарии ссылками. Например, порядок подтверждения отправки описывается в отправке, а страница realtime ссылается на эту часть.
4. Отмечай, что уже есть в коде, что предложено и какие вопросы остались. Для текущего поведения оставляй ссылки на исходники, а для предложений — пример и ожидаемое поведение на спорных переходах.
