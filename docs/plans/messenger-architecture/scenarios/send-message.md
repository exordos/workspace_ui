# Отправка сообщения

[Карта заметок](../README.md) · [Владельцы состояния](../modules.md)

Предлагаемый сценарий охватывает отправку текста из обычного и зашифрованного чата. Уже существуют очередь исходящих, проверка версии черновика при завершении отправки и подготовка зашифрованного сообщения к отображению. Связь между ними во многом координирует `handleSend` на [странице чата](../../../../packages/web/src/pages/chat/chat-page-workspace.ui.tsx).

## Решение: отправка внутри messages

В целевом дереве отправка остаётся внутренней частью `model/messages`. Отдельный публичный модуль `sending` пока не выделяем. Это выбранная граница рефакторинга, а не описание уже перенесённого кода. Сигнатуры и имена внутренних файлов условные.

Исходный кейс: сервер сохранил отправленное сообщение, HTTP-ответ потерялся, а затем сообщение пришло через realtime или историю. Нужно одновременно принять серверную строку и распознать подтверждение исходящей операции. Сейчас такая сверка уже есть в загрузчике и обработчиках realtime. [Замечание ревью](../review.md#p2-не-назначен-владелец-общего-приёма-сообщений) относится к месту этой координации в новом плане, а не к доказанному отсутствию поведения в текущем приложении.

Первоначальный граф `sending → messages` требовал обратного обращения для подтверждения из истории. Обсуждались callback, подписка и отдельный координатор в `sync`. После проверки необходимости самой границы выбрали одного владельца: `messages` координирует свои внутренние части. Ответственность очереди сохраняется, но самостоятельное внешнее использование или отдельный жизненный цикл `sending` пока не обоснованы.

```text
model/messages/
  messages.ts                 # публичные операции и координация
  messages-store.ts           # подтверждённые сообщения
  messages-cache.ts
  accept-server-messages.ts   # общий приём и сверка
  history/                    # загрузка, окна и границы страниц
  outgoing/                   # очередь, попытки, доставка и повтор
```

`repository` хранит серверные сообщения, `outgoing` — локальные операции с их попытками и подготовленным payload. Вторую копию подтверждённой истории очередь не создаёт. Обе части живут в контексте владельца и поколения сессии `messages`, независимо от открытия экрана. Публичный модуль связывает их операции; внутренние части не импортируют друг друга или публичный вход родителя. Подробный [граф зависимостей](../dependencies.md#связи-внутри-мессенджера) и более подробное [дерево файлов](../source-structure.md#дерево) следуют этой границе.

## 1. Ввод и сохранение

```ts
drafts.update(draftRef, { text });
```

`features/composer` подписан на текущий черновик через публичный контракт `model/drafts`. `drafts` хранит его содержимое, версию и статус сохранения. Применение правил приватности и защиты от устаревшего ответа остаётся за [модулем черновиков](../modules.md#composer-и-черновики).

## 2. Намерение отправить

```ts
await messages.sendDraft({ draftRef, revision: draft.revision });
```

`messages.sendDraft` передаёт намерение своей внутренней части `outgoing`. Она фиксирует неизменяемый снимок отправляемой версии: текст, ответы, вложения, назначение, владельца и поколение сессии, режим защиты и идентификатор операции. Проверяет возможность отправки и готовность необходимых ресурсов через `drafts` и `crypto`. Если операция отклонена до принятия, черновик остаётся в редакторе. Асинхронная подготовка работает со снимком, поскольку пользователь уже мог изменить текст.

## 3. Принятие в очередь

Принятие приложением и подтверждение сервером — разные события. При принятии `messages` регистрирует исходящую операцию в своей очереди `outgoing` и принимает ответственность за снимок и вложения. `drafts` отмечает переданной конкретную версию. Редактор освобождается, только если в нём всё ещё эта версия.

```text
Пользователь отправил версию 12.
Пока шла подготовка, он написал версию 13.
Очередь принимает версию 12.
В редакторе остаётся версия 13.
```

Очистка при принятии в очередь — предложение по поведению. Сейчас момент очистки зависит от ветки. Очередь в памяти переживает смену экрана в той же сессии. Для восстановления после перезапуска потребуется отдельное решение об устойчивом хранении. Для E2EE оно должно исключать сохранение открытого текста.

## 4. Оптимистичное отображение

Лента получает подтверждённые сообщения и локальные исходящие операции через публичные подписки `messages`. Она управляет показом исходящей строки и её переходом к серверной. Прямой доступ UI к внутреннему `outgoing` не требуется. Регистрация в очереди создаёт строку со статусом подготовки или отправки. Изменение статуса обновляет эту же строку. Очередь владеет исходящей операцией, поэтому её состояние доступно и при повторном открытии чата. Локальные строки не становятся серверными границами пагинации.

Прокрутка принадлежит ленте. Сигнал о принятии отправки может содержать идентификатор операции и использоваться для навигации в исходном разговоре. Создание строки следует из состояния очереди.

## 5. Подготовка и доставка

```text
принято → подготовка → отправка → подтверждено
                    ↘ ошибка    ↘ ошибка / результат неизвестен
```

Готовность вложений учитывается до отправки. Внутренний `outgoing` формирует допустимый серверный payload. Для E2EE он получает пригодную криптосессию и ключ через `crypto`, шифрует предусмотренные протоколом данные и передаёт шифротекст. Недоступный ключ блокирует операцию или даёт явную ошибку. Секретные фрагменты в обычном чате используют свой режим подготовки в той же очереди. `crypto` отвечает за ключи и криптографические операции независимо от React и состояния экрана.

Повтор сохраняет идентификатор операции и использует подготовленный payload, пока тот допустим по протоколу. Смена ключа требует отдельного решения о повторе. Текущий код уже удерживает подготовленный зашифрованный payload. [Доставка из очереди](../../../../packages/web/src/entities/messenger/messenger-outbox-delivery.lib.ts)

## 6. Согласование с сервером

Ответ HTTP, [realtime](realtime.md) и подтверждённое сообщение из [загруженной истории](load-messages.md) могут наблюдаться в разном порядке. Общим приёмом владеет `messages`. Все три входа вызывают один внутренний сценарий; внешний `sync` направляет событие в `messages` и не обновляет его очередь отдельно.

```ts
// Внутри messages. Все зависимости уже привязаны к сессии.
async function acceptServerMessages(batch, scope) {
  const result = await repository.accept(batch, scope);

  if (result.status === "stale-session") return result;

  await outgoing.confirmObserved(result.serverEvidence, scope);
  return result;
}
```

`repository.accept` проверяет владельца, согласует тела и удаления с более свежими изменениями и обновляет кеш по принятой политике. `outgoing.confirmObserved` сопоставляет пригодные серверные свидетельства с исходящими операциями по идентификаторам и правилам протокола. Он знает подготовленный payload и особенности зашифрованной отправки. Совпадение текста или одного произвольного UUID не считается достаточным подтверждением. Каждая часть проверяет актуальность сессии внутри своих асинхронных записей.

```ts
// Внутри messages: HTTP-ответ на доставку.
await acceptServerMessages({ source: "send-response", messages: response.messages }, scope);

// Внутри messages: страница истории.
await acceptServerMessages({ source: "history", messages: page.messages }, scope);

// Внутри messages.applyEvent: нормализованное событие.
await acceptServerMessages({ source: "realtime", changes: event.changes }, scope);
```

Пакет условный: полная строка истории, частичная правка и удаление сохраняют разные семантики. DTO адаптируются на входе. Если доставка вернула только квитанцию, протокольные сведения подтверждают операцию без выдумывания отсутствующего тела. Общая функция и обратный вызов для результата доставки собираются внутри `messages`; ни история, ни очередь не импортируют внешний координатор. Обработка данных для списка чатов остаётся у `chats` и связывается на уровне сценария мессенджера.

Приём тел и присоединение страницы к текущему окну — отдельные решения. Устаревшая граница не позволяет расширить окно, но безопасные данные ответа могут быть полезны для хранилища и подтверждения. [Разбор загрузки](load-messages.md#применение-страницы-и-сохранение-данных)

Серверное свидетельство и свежесть тела также различаются. Старый HTTP не заменяет новую правку, но может подтверждать доставку. Уже известное сообщение при повторе должно снова позволять согласовать очередь: первый проход мог обновить `repository`, а затем завершиться ошибкой до подтверждения `outgoing`. Эти операции не объявляются общей транзакцией. При необходимой ошибке согласования realtime не продвигает курсор, а повтор безопасно завершает обработку. [Контракт курсора](../workspace-runtime.md#контракт-продвижения-курсора)

Повторное применение одного подтверждения должно оставлять одну строку. Ошибка HTTP после подтверждения по realtime сохраняет статус подтверждения. Таймаут с неизвестным результатом оставляет возможность сверить состояние и повторить ту же операцию. Гарантии от создания дублей при повторе зависят от контракта сервера.

Удаление серверного черновика выполняется отдельно. Его сбой или конфликт сохраняет факт отправки и более новый черновик.

### Четвёртый перенос messages

Обычный и E2EE POST, серверный ответ обычного открытия и верхней догрузки `tail`, одиночный и пакетный активный `message.created` сходятся в одном внутреннем сценарии `messages`. Он применяет данные по правилам источника и подтверждает исходящие в одном месте. Запросы истории, запись её окна в кеш, realtime-курсор и управление попытками доставки принадлежат своим входам. [Решение о владельце](../review.md#p2-не-назначен-владелец-общего-приёма-сообщений) · [Общий приём в коде](../../../../packages/web/src/entities/messenger/messages-accept-server.lib.ts) · [Доставка исходящих](../../../../packages/web/src/entities/messenger/messenger-outbox-delivery.lib.ts)

```ts
const outcome = acceptServerMessages({ ...input, ownerKey, isCurrent });
```

1. Транспорт сохраняет построение запроса, стабильный canonical UUID, свои проверки ответа и передаёт нормализованный DTO внутреннему входу. Для E2EE действуют проверки владельца, размещения, подготовленного содержимого и поколения ключа, в том числе для фрагментов, служебных сообщений и объявления ротации. Сохранить проверки опросов и текущие контракты прямых вызовов.
2. `messages` применяет тело или страницу и подтверждает исходящее по наблюдённым серверным данным. Placement UUID, владелец, проект, чат, автор и подготовленное зашифрованное содержимое определяют пригодность ответа для очереди. Запоздалый POST или `message.created` может подтвердить отправку, сохраняя новую правку, перемещение или удаление в каноническом состоянии. Проверить актуальность после синхронных публикаций и перед отложенной записью.
3. Доставщик владеет in-flight, повторами, ошибкой и восстановлением после потерянного HTTP. При успешном POST он читает результат приёма уже подтверждённой операции. Если сообщение пришло через историю или realtime, сверка завершает доставку без нового POST. Факт принятого подтверждения сохраняется до конца текущей попытки, даже если тело успели изменить или удалить. Ручное удаление исходящей строки не даёт подтверждения. Повтор использует сохранённый UUID и подготовленный пакет. [Третий перенос](load-messages.md#третий-перенос-messages)

#### Проверки четвёртого шага

- Для Markdown и E2EE подтвердить исходящее реальным путём приёма POST. Для E2EE отдельно проверить несоответствующие размещение или содержимое и смену ключа. Обычная и смешанная отправка сохраняют протокольные проверки, служебные E2EE-сообщения продолжают работать без исходящей строки.
- Проверить POST → realtime и realtime → POST для одного UUID. После POST и более свежей серверной истории задержанный `message.created` сохраняет актуальные тело, окно и кеш. Повторить с одиночным событием и пачкой со свежим сообщением. Курсор продвигается и при устаревшем событии. Поздние данные после удаления не возвращают строку, указатели или запись кеша.
- Если HTTP потерян после подтверждения из истории или realtime, доставка завершается успешно. Проверить, что редактирование или удаление подтверждённого сообщения даёт тот же результат. Если подтверждения ещё нет, повтор использует прежние canonical UUID и зашифрованный пакет. Проверить отмену или смену поколения до ответа и выход между публикацией сообщения и следующими эффектами.
- Запустить тесты message actions, E2EE runtime, outbox, загрузчика истории, realtime и страницы чата. Прогнать `npm run typecheck`, `npm run docs:check` и `git diff --check`.

В Chromium с подставными ответами проверить обычную отправку, смену маршрута во время POST, повтор с тем же UUID и пакетом после потерянного ответа, а также отправку секретных фрагментов в обычный чат. [Отправка из ленты](../../../../e2e/message-send.spec.ts) · [Очередь и повторы](../../../../e2e/workspace-outbox.spec.ts) · [Секретные фрагменты](../../../../e2e/workspace-secret-fragments.spec.ts)

## 7. Переход к серверному содержимому

`messages` хранит серверный шифротекст. `features/decrypted-message` вызывает `crypto` и возвращает состояние расшифровки: подготовка, готово, ключ недоступен или ошибка. Обычный текст, заблокированное сообщение и служебный запрос ключа могут иметь разные компоненты с общей оболочкой. [Примеры подготовки и рендера бабла](present-message.md)

Готовность представления и подтверждение доставки изменяются независимо. При замене исходящей строки на серверную нужен стабильный идентификатор, чтобы избежать исчезновения строки, скачка высоты и потери её состояния. Сейчас [лента](../../../../packages/web/src/widgets/workspace-message-list/workspace-message-list.ui.tsx) уже удерживает исходящую строку, пока серверная версия готовится. Это правило остаётся в ленте. `decrypted-message` отдельно следит за актуальностью открытого текста при потере доступа, ключа или смене сессии.

## Проверяемые переходы

| Ситуация                                  | Ожидаемое поведение                                                  |
| ----------------------------------------- | -------------------------------------------------------------------- |
| Пользователь начал следующий черновик     | Завершение предыдущей отправки сохраняет новый ввод                  |
| Пользователь открыл другой чат            | Доставка продолжается, положение новой ленты сохраняется             |
| Аккаунт или поколение сессии сменились    | Запоздавшие операции не меняют состояние текущей сессии              |
| HTTP завершился таймаутом                 | Можно сверить результат и повторить ту же операцию                   |
| Realtime подтвердил сообщение раньше HTTP | В ленте одна строка, поздняя ошибка HTTP сохраняет подтверждение     |
| Ключ удалён во время расшифровки          | Поздний результат не возвращает открытый текст                       |
| Доставка завершилась ошибкой              | Очередь удерживает снимок для повтора, новый черновик сохраняется    |
| Серверная версия ещё готовится            | Строка сохраняет идентичность, доступ к открытому тексту проверяется |

Главная граница для проверки — кто принимает решение об отправке, подтверждении и завершении черновика. Эти переходы нужно проверять с разным порядком HTTP, realtime и смены сессии.
