# Отправка сообщения

[Карта заметок](../README.md) · [Владельцы состояния](../modules.md)

Предлагаемый сценарий охватывает отправку текста из обычного и зашифрованного чата. Уже существуют очередь исходящих, проверка версии черновика при завершении отправки и подготовка зашифрованного сообщения к отображению. Связь между ними во многом координирует `handleSend` на [странице чата](../../../../packages/web/src/pages/chat/chat-page-workspace.ui.tsx).

## 1. Ввод и сохранение

```ts
drafts.update(draftRef, { text });
```

Composer подписан на текущий черновик. `drafts` хранит его содержимое, версию и статус сохранения. Применение правил приватности и защиты от устаревшего ответа остаётся за [модулем черновиков](../modules.md#composer-и-черновики).

## 2. Намерение отправить

```ts
await sending.submitDraft({ draftRef, revision: draft.revision });
```

`sending` фиксирует неизменяемый снимок отправляемой версии: текст, ответы, вложения, назначение, владельца и поколение сессии, режим защиты и идентификатор операции. Проверяет возможность отправки и готовность необходимых ресурсов. Если операция отклонена до принятия, черновик остаётся в редакторе. Асинхронная подготовка работает со снимком, поскольку пользователь уже мог изменить текст.

## 3. Принятие в очередь

Принятие приложением и подтверждение сервером — разные события. При принятии `sending` регистрирует исходящую операцию и принимает ответственность за снимок и вложения. `drafts` отмечает переданной конкретную версию. Редактор освобождается, только если в нём всё ещё эта версия.

```text
Пользователь отправил версию 12.
Пока шла подготовка, он написал версию 13.
Очередь принимает версию 12.
В редакторе остаётся версия 13.
```

Очистка при принятии в очередь — предложение по поведению. Сейчас момент очистки зависит от ветки. Очередь в памяти переживает смену экрана в той же сессии. Для восстановления после перезапуска потребуется отдельное решение об устойчивом хранении. Для E2EE оно должно исключать сохранение открытого текста.

## 4. Оптимистичное отображение

Лента подписана на представление, объединяющее подтверждённые сообщения и локальные исходящие операции. Регистрация в очереди создаёт строку со статусом подготовки или отправки. Изменение статуса обновляет эту же строку. Очередь владеет исходящей операцией, поэтому её состояние доступно и при повторном открытии чата.

Прокрутка принадлежит ленте. Сигнал о принятии отправки может содержать идентификатор операции и использоваться для навигации в исходном разговоре. Создание строки следует из состояния очереди.

## 5. Подготовка и доставка

```text
принято → подготовка → отправка → подтверждено
                    ↘ ошибка    ↘ ошибка / результат неизвестен
```

Готовность вложений учитывается до отправки. Для обычного сообщения `sending` формирует допустимый серверный payload. Для E2EE он получает пригодную криптосессию и ключ через `crypto`, шифрует предусмотренные протоколом данные и передаёт шифротекст. Недоступный ключ блокирует операцию или даёт явную ошибку. Секретные фрагменты в обычном чате используют свой режим подготовки в той же очереди. `crypto` отвечает за ключи и криптографические операции независимо от React и состояния экрана.

Повтор сохраняет идентификатор операции и использует подготовленный payload, пока тот допустим по протоколу. Смена ключа требует отдельного решения о повторе. Текущий код уже удерживает подготовленный зашифрованный payload. [Доставка из очереди](../../../../packages/web/src/entities/messenger/messenger-outbox-delivery.lib.ts)

## 6. Согласование с сервером

Ответ HTTP, [realtime](realtime.md) и подтверждённое сообщение из [загруженной истории](load-messages.md) могут наблюдаться в разном порядке. Предлагаемая общая операция сверяет владельца и идентификаторы протокола, применяет серверное сообщение с учётом более свежих обновлений, подтверждает исходящую операцию и запускает обработку отправленной версии черновика. Затем обновляются кеш и данные для списка чатов.

Повторное применение одного подтверждения должно оставлять одну строку. Ошибка HTTP после подтверждения по realtime сохраняет статус подтверждения. Таймаут с неизвестным результатом оставляет возможность сверить состояние и повторить ту же операцию. Гарантии от создания дублей при повторе зависят от контракта сервера.

Удаление серверного черновика выполняется отдельно. Его сбой или конфликт сохраняет факт отправки и более новый черновик.

## 7. Переход к серверному содержимому

`messages` хранит серверный шифротекст. `presentation` запрашивает у `crypto` подготовку содержимого и выдаёт одно из состояний: подготовка, готово, ключ недоступен, ошибка расшифровки. Обычный текст, заблокированное сообщение и служебный запрос ключа могут иметь разные компоненты с общей оболочкой.

Готовность представления и подтверждение доставки изменяются независимо. При замене исходящей строки на серверную нужен стабильный идентификатор, чтобы избежать исчезновения строки, скачка высоты и потери её состояния. Сейчас [лента](../../../../packages/web/src/widgets/workspace-message-list/workspace-message-list.ui.tsx) уже удерживает исходящую строку, пока серверная версия готовится. Предлагаемое место этого правила — `presentation`. Открытый текст временный и инвалидируется при потере доступа, ключа или смене сессии.

## Проверяемые переходы

| Ситуация                                  | Ожидаемое поведение                                                  |
| ----------------------------------------- | -------------------------------------------------------------------- |
| Пользователь начал следующий черновик     | Завершение предыдущей отправки сохраняет новый ввод                  |
| Пользователь открыл другой чат            | Доставка продолжается, положение новой ленты сохраняется             |
| Аккаунт или поколение сессии сменились    | Запоздавшие операции не меняют состояние текущей сессии              |
| HTTP завершился таймаутом                 | Можно сверить результат и повторить ту же операцию                   |
| Realtime подтвердил сообщение раньше HTTP | В ленте одна строка, поздняя ошибка HTTP сохраняет подтверждение     |
| Ключ удалён во время расшифровки          | Поздний результат не возвращает открытый текст                       |
| Доставка завершилась ошибкой              | Очередь удерживает снимок для повтора, новый черновик сохраняется    |
| Серверная версия ещё готовится            | Строка сохраняет идентичность, доступ к открытому тексту проверяется |

Главная граница для проверки — кто принимает решение об отправке, подтверждении и завершении черновика. Эти переходы нужно проверять с разным порядком HTTP, realtime и смены сессии.
