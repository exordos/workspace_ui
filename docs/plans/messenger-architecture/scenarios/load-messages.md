# Загрузка истории

[Карта заметок](../README.md) · [Владельцы состояния](../modules.md)

Сценарий входит в план рефакторинга мессенджера.

`messages` владеет загруженным окном разговора. `timeline` выбирает окно, запрашивает следующую страницу и управляет прокруткой. Кеш, HTTP и [realtime](realtime.md) передают данные владельцу окна. Лента подписывается на его состояние.

Примеры описывают контракт между модулями. Сигнатуры условные. `messages` можно реализовать классом, объектом с функциями или модулем с экспортируемыми функциями. В примерах он уже привязан к сессии мессенджера. Разбор исходит из одного загруженного окна на разговор, как в текущем store. Если понадобится одновременно показать две разные части истории одного разговора, у окон появятся отдельные идентификаторы. Тела сообщений при этом можно по-прежнему хранить один раз.

## Кто кого вызывает

```ts
// Timeline: открытие разговора.
useEffect(() => {
  const request = messages.openWindow({ conversationId, at: "latest" });
  return () => request.cancel();
}, [messages, conversationId]);

const history = useMessageWindow(messages, conversationId);

// Timeline: пользователь достиг верхней границы.
function onReachTop() {
  return messages.loadMore({ conversationId, direction: "before" });
}
```

При переходе по ссылке лента просит открыть `at: { messageUuid }`. Сценарий навигации при необходимости сначала выясняет, в каком разговоре сейчас находится сообщение. Прокрутка к нему выполняется после применения нужного окна и готовности строки. Новый переход отменяет предыдущий. У фонового realtime свой жизненный цикл, который запускается при [bootstrap](bootstrap.md).

`useMessageWindow` читает снимок из `messages` и подписывается на изменения этого разговора. Снимок содержит упорядоченные строки, доступные направления догрузки и статус загрузки. Когда `messages` применяет кеш, страницу или событие, лента получает новое состояние через ту же подписку. Например, правка по realtime меняет тело уже видимой строки с тем же UUID.

| Владелец        | Что хранит                                                                                                                                                        |
| --------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `messages`      | Тела по UUID. На разговор — упорядоченные UUID окна, режим (последние сообщения или вокруг якоря), якорь, маркеры до и после окна, ревизию окна и статус загрузки |
| `timeline`      | Текущий запрос навигации, видимые строки, якорь прокрутки и его смещение, позицию у конца ленты                                                                   |
| Кеш мессенджера | Последний пригодный снимок для владельца, включая принадлежность сообщений к разговору и известные границы                                                        |
| `presentation`  | Готовность содержимого строк, в том числе временный результат расшифровки                                                                                         |

Якорь окна определяет, какую часть истории загрузили. Якорь прокрутки — конкретная видимая строка и её положение в списке. При вставке старых сообщений лента сохраняет второй, пока `messages` расширяет первое. При добавлении новых сообщений автоматическая прокрутка зависит от того, был ли пользователь у конца.

## 1. Открытие из кеша и обновление по HTTP

Например, пользователь открывает разговор, для которого в IndexedDB остались последние 20 сообщений. Сначала видит эти строки, затем сервер подтверждает или уточняет окно. Если уже открыто более полное окно, маленький кеш не должен на время сжимать ленту.

```ts
// Внутри messages. Упрощённый сценарий открытия последних сообщений.
async function openLatest(request: WindowRequest) {
  const cacheRead = captureSnapshotContext(request);
  const cached = await cache.tryReadTail(request.ownerKey, request.conversationId);

  if (!isCurrent(request)) return;
  if (cached && canRestoreTail(cacheRead)) {
    applyWindowSnapshot(cacheRead, cached);
  }

  // Снимок контекста для HTTP берём после возможного восстановления кеша.
  const fetch = captureSnapshotContext(request);
  const page = await api.fetchTail(request.conversationId, request.signal);

  if (!isCurrent(request)) return;
  const applied = applyWindowSnapshot(fetch, page);
  if (applied) await persistIfCurrent(request, applied);
}
```

`captureSnapshotContext` фиксирует ревизию окна и ревизию изменений сообщений. `applyWindowSnapshot` проверяет обе перед применением. Снимок кеша относится к владельцу (аккаунт, инстанс, организация, проект, пользователь). Поколение сессии используется для допуска асинхронной записи. Сами сохранённые данные можно повторно использовать при следующем входе того же владельца.

Кеш хвоста пригоден для открытия хвоста. Для перехода к старому сообщению нужно окно, которое содержит нужный якорь и подходит по границам. HTTP обновляет подходящее окно либо применяет другое, если именно его запросила навигация. Ошибка обновления сохраняет пригодные строки и даёт повтор. Подтверждённое пустое окно отображается как пустая история. В примере сбой чтения кеша допускает продолжение через HTTP. Это предлагаемое поведение, которое нужно проверять отдельно.

Кеш обновляется из принятого состояния с проверкой актуальности при записи. Пока идёт IndexedDB, данные могут снова измениться. Старый HTTP-снимок не должен вернуть в кеш удалённое сообщение. Текущие правила хранения и курсоров описаны отдельно. [Кеш мессенджера](../../../WORKSPACE_MESSENGER_CACHE.md)

## 2. Догрузка страницы и смена окна

```ts
// Внутри messages. direction передаёт лента, маркер берёт владелец окна.
const boundary = captureBoundary({ conversationId, direction });
const page = await api.fetchPage({
  conversationId,
  direction,
  pageMarker: boundary.pageMarker,
});
applyPageIfCurrent(boundary, page);
```

`boundary` хранит владельца, поколение сессии, токен запроса, ожидаемые ревизию окна и маркер, а также ревизию изменений сообщений на момент запроса. Маркер выдаёт сервер. Используем его как непрозрачное значение.

Граница окна — место, с которого сервер продолжает пагинацию. Например, в ленте сообщения 101–150, а у верхней границы есть маркер для страницы перед 101. Номера здесь показывают порядок сообщений. Маркер остаётся непрозрачным значением, полученным от сервера.

Применённая страница расширяет окно с нужной стороны, объединяет строки по UUID и обновляет маркер этой стороны. Лента сохраняет видимую строку на её месте. В текущем коде проверяются и ревизия окна, и маркер, поэтому даже изменение состава окна по realtime может потребовать нового запроса.

### Переход к другому окну во время запроса

```ts
// Видно 101–150. Timeline просит загрузить страницу перед 101.
void messages.loadMore({ conversationId, direction: "before" });

// Пока идёт запрос, пользователь открывает ссылку на сообщение 500.
// Timeline или навигация меняет цель просмотра и начинает новый запрос.
messages.openWindow({ conversationId, at: { messageUuid: linkedMessageUuid } });
```

Навигация знает, что пользователь сменил цель, и отменяет или заменяет прежний запрос просмотра. `messages` знает, для какой границы была запрошена страница. Если поздний ответ принесёт строки 81–100, присоединение их к окну вокруг 500 создаст разрыв. Тот же принцип действует при возврате от якоря к последним сообщениям.

Уход с экрана отменяет принадлежащий ему запрос и намерение прокрутить. Загруженное окно может остаться в памяти мессенджера и использоваться при возвращении. Смена аккаунта или поколения сессии лишает старые запросы права записывать результат. Проверка перед применением нужна и после вызова отмены. [Границы асинхронных операций](../../../ORG_SCOPED_ASYNC_SAFETY.md)

### Применение страницы и сохранение данных

- **Применение к окну.** Ответ для прежней границы оставляет строки, маркеры и статус загрузки нового окна прежними. Лента продолжает читать новое окно и выполняет только актуальное намерение прокрутки.
- **Сохранение тел сообщений.** Можно рассмотреть отдельный приём уже полученных полезных данных в хранилище `messages` или кеш. Для этого нужны актуальная сессия, проверка принадлежности и защита от запоздавших правок, удалений и переносов. Сам факт приёма тел не подтверждает границу страницы и не добавляет её строки в активное окно.

Сейчас при несовпадении ревизии окна или маркера путь догрузки отклоняет страницу целиком, до слияния тел. Раздельный приём безопасных данных остаётся вариантом для рефакторинга. Выбор касается уже полученного ответа. Отмена запроса по-прежнему может остановить его до получения данных. [Текущая проверка страницы](../../../../packages/web/src/entities/message/message.model.ts#L516)

## 3. Realtime и запоздавший HTTP

```ts
// Мессенджер направляет событие в тот же модуль, который загружает историю.
await messages.applyEvent(event);
```

`messages` применяет событие к телам и подходящим загруженным окнам. Создание может добавить строку в актуальный хвост. В окне вокруг старого сообщения новая строка за его границей не должна создавать разрыв истории. Редактирование меняет тело. Удаление убирает UUID из окон и фиксирует факт удаления. При переносе UUID исчезает из исходного окна и добавляется в целевое только при подходящих границах. Если целевое окно ещё не загружено, можно сохранить тело, не создавая окно. Лента видит результат через ту же подписку. Realtime обновляет кеш с сохранением порядка событий и правил продвижения курсора.

Пример гонки:

```text
1. HTTP начал запрос. Локальная ревизия изменений — 41.
2. Realtime обновил текст сообщения M. Для M записана ревизия 42.
3. HTTP вернул страницу со старым текстом M и ранее незагруженными строками.
4. Если ревизия окна и маркер ещё подходят, применяем страницу,
   сохраняя актуальный текст M. Если M удалили или перенесли,
   старое тело или принадлежность исходному окну не восстанавливаем.
```

Здесь два разных вопроса. **Ревизия окна и маркер** определяют, можно ли применить всю страницу к этой границе. **Ревизия изменения сообщения и отметка об удалении** определяют, какие данные можно взять из принятой страницы. Если перенос или удаление изменили состав окна, страница может быть отклонена уже на первой проверке. Одного порядка завершения промисов для этих решений недостаточно.

При загрузке серверная строка также может подтвердить локальное исходящее сообщение. Сверку по UUID стоит проводить через общий переход [подтверждения отправки](send-message.md#6-согласование-с-сервером). Для E2EE `messages` и кеш хранят серверный шифротекст. Подготовка строки и прокрутка к ней остаются отдельным шагом после применения окна.

## Что уже есть

- В [store сообщений](../../../../packages/web/src/entities/message/message.model.ts) уже разделены тела, окна по разговорам и ревизии изменений. Замена окна и расширение страницами учитывают ревизии, маркеры и поздние изменения.
- [Загрузчик](../../../../packages/web/src/entities/messenger/messenger-messages-loader.lib.ts) восстанавливает кеш при обычном открытии, обновляет по HTTP, отдельно получает и применяет окно вокруг якоря, умеет расширять его в обе стороны и сверяет загруженные сообщения с исходящими.
- [Обработчик realtime](../../../../packages/web/src/entities/messenger/messenger-realtime-applier.lib.ts) применяет серверные события к store и кешу. [Страница чата](../../../../packages/web/src/pages/chat/chat-page-workspace.ui.tsx) ещё координирует запросы окон, пагинацию и её ошибки. Предложение переносит работу с границами и статусами загрузки за интерфейс `messages`, сохраняя решение о прокрутке в ленте.

## Проверяемые переходы

| Ситуация                                                     | Ожидаемое поведение                                                            |
| ------------------------------------------------------------ | ------------------------------------------------------------------------------ |
| Кеш меньше уже открытого окна                                | Видимые строки не исчезают во время обновления                                 |
| Кеш читается с ошибкой или не содержит якорь                 | Нужное окно запрашивается по HTTP                                              |
| HTTP недоступен, пригодный кеш уже показан                   | Лента сохраняет строки и предлагает повтор                                     |
| Старые строки добавились сверху                              | Видимая строка остаётся на прежнем месте                                       |
| Второй переход заменил окно до завершения первого            | Первый ответ не меняет активное окно, его маркеры, статус загрузки и прокрутку |
| Правка, удаление или перенос пришли между запросом и ответом | Поздний снимок не отменяет изменение ни в store, ни в кеше                     |
| Realtime добавил строку за пределами старого окна            | Лента не перескакивает и не показывает разрыв                                  |
| История подтвердила сообщение из очереди                     | В ленте одна строка с подтверждённым статусом                                  |
| Владелец или поколение сменились в процессе записи           | Поздний результат не попадает в текущую сессию                                 |
