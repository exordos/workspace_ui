# Bootstrap мессенджера

[Карта заметок](../README.md) · [Владельцы состояния](../modules.md)

Сценарий рефакторинга. Оболочка запускает мессенджер для выбранной сессии. Мессенджер восстанавливает каталог, обновляет его с сервера и передаёт транспорту точку отсчёта событий. Лента запрашивает историю отдельно при открытии разговора.

## 1. Кто запускает

Платформа выбирает аккаунт и проект, предоставляет авторизованную сессию и обновляет её поколение. Оболочка связывает эту сессию с жизненным циклом мессенджера.

```ts
// В оболочке. Ссылка на session стабильна в рамках поколения.
useEffect(() => {
  if (!session) return;

  const run = messenger.start(session);
  return () => run.stop();
}, [messenger, session]);
```

Сигнатуры условные. `start` сразу возвращает управление запуском, чтобы `stop` был доступен даже во время первого запроса. Это может быть класс или модуль с функциями. Bootstrap координирует работу, а каталог, сообщения и черновики принадлежат своим модулям. Готовность bootstrap привязана к конкретной сессии и попытке.

Сейчас `Layout` вызывает bootstrap и сам передаёт его результат в хук realtime. При рефакторинге последовательность этих действий можно спрятать за `messenger.start(session)`. [Layout](../../../../packages/web/src/widgets/layout/layout.ui.tsx) · [Хук bootstrap](../../../../packages/web/src/widgets/layout/layout-workspace-messenger-bootstrap.hook.ts)

## 2. Что грузится

| Данные              | Из кеша                                                                 | С сервера                                                                                         |
| ------------------- | ----------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------- |
| Каталог чатов       | Чаты, темы, папки и указатели на последние сообщения текущего владельца | Чаты и темы запрашиваются параллельно с пользователями. Папки обновляются отдельным шагом         |
| Пользователи        | Сохранённые профили владельца                                           | Актуальный список пользователей                                                                   |
| Превью списка чатов | Тела последних сообщений, на которые указывает каталог                  | Получение недостающих тел и обновление кешированных превью по UUID                                |
| Черновики           | Своё состояние и правила хранения у `drafts`                            | Общий список загружается отдельно при запуске, поскольку у черновиков сейчас нет realtime-событий |
| История разговора   | Пригодное окно по запросу ленты                                         | Обновление окна и догрузка при навигации                                                          |

Пригодный кеш можно показать, пока идёт серверная подготовка. Если HTTP уже обновил каталог, позднее чтение IndexedDB его не заменяет. При сбое HTTP доступные данные остаются на экране, а состояние загрузки позволяет показать ошибку и повтор. Кеш каталога и кеш окон истории отвечают на разные запросы. [Текущий загрузчик](../../../../packages/web/src/entities/messenger/messenger-bootstrap.lib.ts) · [Загрузка истории](load-messages.md)

```ts
const sidebar = useChatCatalog(chats);
messages.openWindow({ conversationId, at: "latest" });
```

У каталога, истории, черновиков и превью свои статусы. Показ списка из кеша может начаться до готовности realtime.

## 3. Когда запускается realtime

```ts
async function bootstrap(scope: MessengerSessionScope) {
  const session = await auth.ensureFresh(scope);
  if (!scope.isCurrent()) return;

  // Restore applies only while this attempt is current and no fresh catalog has won.
  void catalog.restoreCached(scope);

  const startCursor = await events.getEpoch(session, scope.signal);
  if (!scope.isCurrent()) return;

  const result = await catalog.refresh(scope, { requireCompleteSnapshot: true });
  if (!scope.isCurrent() || result.status !== "applied") return;

  await realtime.start({ scope, startCursor });
}
```

Вызовы с `scope` проверяют владельца, поколение и актуальность попытки внутри операций записи. В примере `realtime.start` выполняет HTTP catch-up, затем открывает сокет от последней обработанной позиции. Пример показывает первый запуск. Политика остановки транспорта при уходе с маршрута задаётся отдельно.

Курсор берётся **до** запросов свежего каталога. Допустим, сервер вернул позицию 100. HTTP успел прочитать старое имя темы, затем тема была переименована событием 101. После применения каталога catch-up дочитывает событие 101 и исправляет имя. Если взять курсор после запроса, можно получить позицию 101, хотя каталог остался со старым именем. События, которые HTTP уже успел отразить, тоже могут прийти при catch-up, поэтому их применение должно сохранять согласованное состояние.

Курсор становится стартовой точкой только после успешного снимка **той же** попытки и сессии. В текущем коде для этого обязательны чаты, темы, пользователи и папки. Превью и черновики загружаются независимо. Если один обязательный запрос упал, частично загруженные данные могут быть видны, а граница realtime не публикуется. При повторе bootstrap получает новый курсор.

Сейчас realtime привязан к маршруту мессенджера. Первый активный запуск использует границу bootstrap, а повторный вход на маршрут в рамках той же попытки продолжает с сохранённой позиции. Какие процессы должны жить при переходе в почту или календарь, остаётся вопросом рефакторинга. Например, время жизни доставки [исходящих](send-message.md#5-подготовка-и-доставка) задаётся независимо от экрана. [Хук realtime](../../../../packages/web/src/widgets/layout/layout-workspace-realtime.hook.ts) · [Транспорт](../../../../packages/web/src/shared/lib/workspace-realtime/workspace-realtime-runtime.lib.ts) · [Сценарий realtime](realtime.md)

## 4. Смена аккаунта

1. **A → B.** Платформа публикует новую сессию. Оболочка перестаёт читать данные A, останавливает старый активный запуск и запускает B. Запросы A отменяются, его таймеры и подписки освобождаются.
2. **Запуск B.** Мессенджер открывает состояние B и восстанавливает его кеш. Сохранённые данные A остаются в отдельном разделе.
3. **Поздний ответ A.** Перед изменением каталога, ошибок, кеша или курсора проверяются владелец и поколение. Отмена запроса дополняет проверку. Уже запущенное продолжение всё ещё может выполниться.
4. **B → A.** Сохранённый кеш A пригоден для восстановления, но поколение новое. Ответ из первого запуска A не получает права записать результат.

```ts
const requestScope = sessions.capture();
const snapshot = await api.loadCatalog(requestScope);

if (!sessions.isCurrent(requestScope)) return;
chats.applyCatalog(requestScope, snapshot);
```

Ключ кеша состоит из аккаунта, инстанса, организации, проекта и пользователя. Поколение защищает асинхронные операции конкретной сессии. Проверка нужна и внутри записи в IndexedDB, если операция ждёт перед фиксацией. При выходе без выбора нового аккаунта активное состояние освобождается.

У оставшегося авторизованным аккаунта может быть фоновая синхронизация. Она работает со своим владельцем, кешем и курсором и не меняет активный store. [Правила владения асинхронной работой](../../../ORG_SCOPED_ASYNC_SAFETY.md)

## Проверяемые переходы

| Ситуация                                                          | Ожидаемое поведение                                         |
| ----------------------------------------------------------------- | ----------------------------------------------------------- |
| Кеш готов раньше HTTP                                             | Список появляется до готовности realtime                    |
| Кеш завершился после применения свежего каталога                  | Свежие данные остаются на экране                            |
| Событие произошло между получением курсора и завершением каталога | HTTP catch-up обрабатывает его перед открытием сокета       |
| Обязательный запрос каталога упал                                 | Курсор незавершённой попытки не становится стартовой точкой |
| Превью или черновики ещё грузятся                                 | Их статус меняется независимо от готовности realtime        |
| A → B → A, старый запрос ещё в работе                             | Результат первого запуска A не применяется к новому         |
| Повторный вход на маршрут в той же попытке                        | Realtime продолжает с сохранённой позиции                   |
