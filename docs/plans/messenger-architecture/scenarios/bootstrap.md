# Bootstrap мессенджера

[Карта заметок](../README.md) · [Владельцы состояния](../modules.md)

После выделения общего `users` границу этого сценария пересматриваем. Запуск общего транспорта и подключение пользователей разбираются на [уровне Workspace](../workspace-runtime.md), см. [первое замечание ревью](../review.md#p1-общие-данные-зависят-от-мессенджера). Ниже сохранён первоначальный порядок bootstrap мессенджера и текущие механизмы его защиты.

В целевом плане Workspace поддерживает отдельный runtime для каждой авторизованной сессии. Каждый runtime восстанавливает свои данные и согласует стартовую позицию событий. Лента запрашивает историю отдельно при открытии разговора. [Runtime и тёплые сторы](../workspace-runtime.md#runtime-и-тёплый-стор-на-каждую-сессию)

## 1. Кто запускает

Платформа предоставляет список авторизованных сессий и актуальный контекст каждого владельца. Workspace сверяет с этим списком запущенные runtime. При выборе аккаунта оболочка передаёт экранам runtime выбранного владельца.

```ts
// На уровне Workspace при запуске и изменении списка сессий.
workspaceRuntimes.reconcile(auth.sessions);
```

Сигнатуры условные. Запуски сессий могут идти независимо. Bootstrap координирует подготовку одной сессии, а каталог, сообщения и черновики принадлежат своим модулям. Готовность bootstrap привязана к конкретной сессии и попытке.

Сейчас `Layout` вызывает bootstrap и сам передаёт его результат в хук realtime. [Layout](../../../../packages/web/src/widgets/layout/layout.ui.tsx) · [Хук bootstrap](../../../../packages/web/src/widgets/layout/layout-workspace-messenger-bootstrap.hook.ts)

## 2. Что грузится

| Данные              | Из кеша                                                                 | С сервера                                                                                         |
| ------------------- | ----------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------- |
| Каталог чатов       | Чаты, темы, папки и указатели на последние сообщения текущего владельца | Чаты и темы запрашиваются параллельно с пользователями. Папки обновляются отдельным шагом         |
| Пользователи        | Сохранённые профили владельца                                           | Актуальный список пользователей                                                                   |
| Превью списка чатов | Тела последних сообщений, на которые указывает каталог                  | Получение недостающих тел и обновление кешированных превью по UUID                                |
| Черновики           | Своё состояние и правила хранения у `drafts`                            | Общий список загружается отдельно при запуске, поскольку у черновиков сейчас нет realtime-событий |
| История разговора   | Пригодное окно по запросу ленты                                         | Обновление окна и догрузка при навигации                                                          |

Пригодный кеш можно показать, пока идёт серверная подготовка. Если HTTP уже обновил каталог, позднее чтение IndexedDB его не заменяет. При сбое HTTP доступные данные остаются на экране, а состояние загрузки позволяет показать ошибку и повтор. Кеш каталога и кеш окон истории отвечают на разные запросы. [Текущий загрузчик](../../../../packages/web/src/entities/messenger/messenger-bootstrap.lib.ts) · [Загрузка истории](load-messages.md)

```ts
const sidebar = useChatCatalog(chats);
messages.openWindow({ conversationId, at: "latest" });
```

У каталога, истории, черновиков и превью свои статусы. Показ списка из кеша может начаться до готовности realtime.

## 3. Когда запускается realtime

Пример сохраняет порядок для случая, когда сессии нужен свежий снимок каталога и граница воспроизведения. Для запуска с пригодным локальным состоянием и курсором используется догон событий этой сессии.

```ts
async function bootstrap(scope: MessengerSessionScope) {
  const session = await auth.ensureFresh(scope);
  if (!scope.isCurrent()) return;

  // Restore applies only while this attempt is current and no fresh catalog has won.
  void catalog.restoreCached(scope);

  const startCursor = await events.getEpoch(session, scope.signal);
  if (!scope.isCurrent()) return;

  const result = await catalog.refresh(scope, { requireCompleteSnapshot: true });
  if (!scope.isCurrent() || result.status !== "applied") return;

  await realtime.start({ scope, startCursor });
}
```

Вызовы с `scope` проверяют владельца, поколение и актуальность попытки внутри операций записи. В примере `realtime.start` выполняет HTTP catch-up, затем открывает сокет от последней обработанной позиции.

Курсор берётся **до** запросов свежего каталога. Допустим, сервер вернул позицию 100. HTTP успел прочитать старое имя темы, затем тема была переименована событием 101. После применения каталога catch-up дочитывает событие 101 и исправляет имя. Если взять курсор после запроса, можно получить позицию 101, хотя каталог остался со старым именем. События, которые HTTP уже успел отразить, тоже могут прийти при catch-up, поэтому их применение должно сохранять согласованное состояние.

Курсор становится стартовой точкой только после успешного снимка **той же** попытки и сессии. В текущем коде для этого обязательны чаты, темы, пользователи и папки. Превью и черновики загружаются независимо. Если один обязательный запрос упал, частично загруженные данные могут быть видны, а граница realtime не публикуется. При повторе bootstrap получает новый курсор. Для общего runtime Workspace обязательные снимки определяют владельцы обработчиков по тому, какие данные нужны для безопасного применения событий. [Готовность обработчиков](../workspace-runtime.md#общий-курсор-и-ещё-не-готовые-потребители)

Сейчас realtime привязан к маршруту мессенджера. Первый активный запуск использует границу bootstrap, а повторный вход на маршрут в рамках той же попытки продолжает с сохранённой позиции. В целевом плане realtime остаётся у авторизованной сессии при переходе между экранами Workspace. [Хук realtime](../../../../packages/web/src/widgets/layout/layout-workspace-realtime.hook.ts) · [Транспорт](../../../../packages/web/src/shared/lib/workspace-realtime/workspace-realtime-runtime.lib.ts) · [Сценарий realtime](realtime.md)

## 4. Смена аккаунта

1. **A → B.** Оболочка меняет подписку на тёплый стор B. Запросы закрытых экранов A отменяются. Оба runtime продолжают синхронизацию.
2. **B ещё синхронизируется.** Экран получает доступные данные B и его статус готовности. Восстановление B идёт независимо от A.
3. **Поздний ответ A.** Запрос, принадлежащий runtime, может обновить только данные A, пока его запуск актуален. Эффект, принадлежащий прежнему экрану A, проверяет актуальность выбора экрана.

```ts
const requestScope = runtime.captureScope();
const snapshot = await api.loadCatalog(requestScope);

if (!runtime.isCurrent(requestScope)) return;
chats.applyCatalog(requestScope, snapshot);
```

Ключ кеша состоит из аккаунта, инстанса, организации, проекта и пользователя. Поколение защищает асинхронные операции конкретного запуска, в том числе внутри записи в IndexedDB. При выходе из аккаунта его runtime останавливается и теряет право записи. [Правила владения асинхронной работой](../../../ORG_SCOPED_ASYNC_SAFETY.md)

## Проверяемые переходы

| Ситуация                                                          | Ожидаемое поведение                                         |
| ----------------------------------------------------------------- | ----------------------------------------------------------- |
| Кеш готов раньше HTTP                                             | Список появляется до готовности realtime                    |
| Кеш завершился после применения свежего каталога                  | Свежие данные остаются на экране                            |
| Событие произошло между получением курсора и завершением каталога | HTTP catch-up обрабатывает его перед открытием сокета       |
| Обязательный запрос каталога упал                                 | Курсор незавершённой попытки не становится стартовой точкой |
| Превью или черновики ещё грузятся                                 | Их статус меняется независимо от готовности realtime        |
| A → B → A, старый запрос экрана ещё в работе                      | Эффект прежнего выбора A не меняет текущий экран            |
| Выход из A и новый вход, старый запрос runtime ещё в работе       | Старый запуск A теряет право записи                         |
| Переход в другое приложение Workspace                             | Runtime сессий продолжают синхронизацию                     |
