# Realtime мессенджера

[Карта заметок](../README.md) · [Bootstrap](bootstrap.md) · [Владельцы состояния](../modules.md)

После ревью выбрана существующая композиция обработчиков с переносом сборки из `layout` на [уровень сессии Workspace](../workspace-runtime.md). Событие получают все обработчики, каждый выбирает относящуюся к нему работу. Мессенджер обрабатывает свой домен, а общий `users` подключается рядом. [Замечание ревью](../review.md#p1-общие-данные-зависят-от-мессенджера)

Сценарий рефакторинга. Транспорт владеет соединением и курсором. Мессенджер направляет события владельцам данных. `messages` применяет изменения к сообщениям, загруженным окнам и кешу. Timeline подписан на эти данные через тот же интерфейс, которым пользуется при загрузке истории.

## 1. Кто держит соединение и курсор

| Владелец                     | Ответственность                                                                                        |
| ---------------------------- | ------------------------------------------------------------------------------------------------------ |
| Оболочка и менеджер realtime | Решают, для каких сессий запустить и остановить транспорт, какая сессия активна                        |
| Транспорт                    | Держит WebSocket, очередь входящих кадров, позицию обработки в памяти, таймеры повтора и HTTP catch-up |
| Хранилище курсоров           | Сохраняет позицию отдельно для аккаунта, инстанса, организации, проекта и пользователя                 |
| Обработчик мессенджера       | Направляет нормализованное событие в `messages`, `chats` или другому владельцу данных                  |

Курсор — пара `{ epochGeneration, epochVersion }`. Серверное поколение событий определяет, к какому журналу относится позиция. `runtimeGeneration` клиента определяет, вправе ли текущий запуск менять состояние. Оно проверяется перед записью и не входит в постоянный ключ. Маркер страницы истории относится к пагинации сообщений и хранится отдельно.

Сейчас первый активный запуск берёт границу из [bootstrap](bootstrap.md#3-когда-запускается-realtime). В целевом плане каждый runtime выбирает стартовую позицию по состоянию своей сессии. Дальше работа продолжается с последней обработанной позиции. В текущем коде транспорт хранит её в памяти и пишет устойчивый курсор в `localStorage`. Кеш сообщений в IndexedDB обновляется отдельно. При работающей сессии запись из другой вкладки не должна перескочить через события, которые эта вкладка ещё не применила. [Транспорт](../../../../packages/web/src/shared/lib/workspace-realtime/workspace-realtime-runtime.lib.ts) · [Хранилище курсоров](../../../../packages/web/src/shared/lib/workspace-realtime/workspace-realtime-cursor.lib.ts)

## 2. Как событие доходит до сообщений

HTTP catch-up и WebSocket передают нормализованные события одной композиции обработчиков. Транспорт проверяет принадлежность события и позицию. Каждый обработчик выбирает свою работу. Внутри мессенджера можно направлять его события владельцам данных. Сигнатуры условные, классы или функции можно выбрать позже.

```ts
// Внутри мессенджера. Композиция вызывает этот обработчик из REST и WebSocket.
async function applyEvent(scope: RealtimeScope, event: WorkspaceEvent) {
  switch (event.type) {
    case "message":
      return messages.applyEvent(scope, event);
    case "topic":
      return chats.applyTopicEvent(scope, event);
  }
}
```

Пример для `message.created`. `messages` приводит DTO к модели Workspace, обновляет тело и подходящее окно. Лента у конца чата увидит новую строку. При просмотре старого участка лента сохранит позицию, а строка за пределами окна не создаст разрыв. Событие также может подтвердить отправку и обновить указатель списка чатов. Правка меняет тело, перенос меняет принадлежность к разговору, удаление убирает сообщение и его ссылки. В выбранном плане `messages.applyEvent` использует тот же внутренний приём, что HTTP-ответ доставки и история: согласует серверные данные и собственную очередь `outgoing`. Отдельно вызывать `sending` из обработчика мессенджера не нужно. Обновление каталога остаётся у `chats` и связывается сценарием мессенджера. [Применение событий в текущем коде](../../../../packages/web/src/entities/messenger/messenger-realtime-applier.lib.ts) · [Загрузка истории](load-messages.md#3-realtime-и-запоздавший-http) · [Подтверждение отправки](send-message.md#6-согласование-с-сервером)

Обработчик ожидает завершения необходимого согласования исходящей операции перед возвратом транспорту. Если серверное тело уже применено, но подтверждение очереди завершилось ошибкой, повтор того же события должен снова согласовать очередь. Это целевой контракт; общей транзакции для всех частей он не обещает.

Курсор продвигает транспорт после завершения обработчиков. Timeline может получить обновление store до сохранения курсора. Запись кеша, входящая в обработку события, ожидается. В текущем коде часть ошибок кеширования обрабатывается в режиме best effort. Атомарность между IndexedDB и устойчивым курсором транспорта из этого не следует. Для пачек создания есть отдельная транзакция записи сообщений и отметки прогресса в IndexedDB. [Правила кеша](../../../WORKSPACE_MESSENGER_CACHE.md)

```ts
// Упрощённый путь для одного поддерживаемого события.
async function processEvent(event: CursorEvent, connection: Connection) {
  if (!connection.isCurrent()) return;
  if (cursor.hasProcessed(event.position)) return;

  await applier.applyEvent(event.payload, connection.scope);

  if (!connection.isCurrent()) return;
  cursor.commit(connection.owner, event.position);
}
```

После `await` проверяем и сессию, и сам экземпляр соединения. Аккаунт мог смениться или старый сокет мог быть заменён в той же сессии. Владелец данных также проверяет контекст внутри асинхронной записи. Повторы на уже пройденной позиции пропускаются. Неизвестное событие с валидной позицией текущий транспорт может пропустить явно с диагностикой. По [контракту Workspace](../workspace-runtime.md#контракт-продвижения-курсора) у сессии один курсор. Неготовность или сбой нужного обработчика останавливают дальнейшее применение. После готовности или восстановления транспорт повторяет события с последней подтверждённой позиции. [Готовность и сбой обработчика](../workspace-runtime.md#общий-курсор-и-ещё-не-готовые-потребители)

Сейчас фоновый аккаунт использует собственный курсор и обработчик, обновляет часть кеша и ведёт данные для уведомлений. Целевой runtime каждой сессии также поддерживает в памяти тёплый стор первого экрана. Обработчик применяет события к данным своего владельца независимо от того, на какой стор подписан UI. [Жизненный цикл runtime](../workspace-runtime.md#runtime-и-тёплый-стор-на-каждую-сессию) · [Асинхронное владение](../../../ORG_SCOPED_ASYNC_SAFETY.md)

### Входы и порядок до переноса

Сокет вызывает композицию `applyEvent`. REST catch-up использует `applyEvents` при наличии пакетного входа. Композиция ждёт все домены перед сменой типа или операции события. В `createMessengerRealtimeActiveApplier` пачка собирается только для catch-up с выключенными уведомлениями и доступной `writeCreatedMessages`. Буфер принимает соседние `message.created` до 100 событий и сбрасывается перед любым другим событием и в конце входа. При остальных условиях `applyEvents` ждёт каждое `applyEvent` по очереди. [Сборка в layout](../../../../packages/web/src/widgets/layout/layout-workspace-realtime.hook.ts#L434) · [Сокет и курсор](../../../../packages/web/src/shared/lib/workspace-realtime/workspace-realtime-runtime.lib.ts#L528) · [REST catch-up](../../../../packages/web/src/shared/lib/workspace-realtime/workspace-realtime-catch-up.lib.ts#L221) · [Композиция](../../../../packages/web/src/shared/lib/workspace-realtime/workspace-realtime-applier.lib.ts#L15) · [Буфер](../../../../packages/web/src/entities/messenger/messenger-realtime-applier.lib.ts#L664)

- Одиночный `applyMessageRealtimeEvent` адаптирует DTO, накладывает границу прочитанного и запоминает контекст стрима. Затем обновляет тела и окна, подтверждает исходящее, обновляет указатель каталога со снимком `messagesById` до записи и запускает `writeCreatedMessages(ownerKey, [message], undefined, isCurrent)`. После старта записи вызывает `onMessageCreated`, если включены уведомления и разрешены живые побочные эффекты. Например, layout использует этот вызов для входящих звонков в DM. Асинхронный результат вызова не задерживает обработку события. После ожидания кеша и проверки владельца обработчик обновляет проекцию для уведомлений, видимый курсор каталога и ждёт отдельную запись отметки в IndexedDB. Путь с `writeConversationMessagePage` вместо `writeCreatedMessages` также ждёт записи для разговора и стрима, если это разные ключи. [Одиночное принятие](../../../../packages/web/src/entities/messenger/messenger-realtime-applier.lib.ts#L419) · [Кеш](../../../../packages/web/src/entities/messenger/messenger-realtime-applier.lib.ts#L275) · [Завершение](../../../../packages/web/src/entities/messenger/messenger-realtime-applier.lib.ts#L717) · [Политика живых эффектов](../../../../packages/web/src/entities/messenger/messenger-live-effects.lib.ts#L19)
- Пакетный callback в `applyEvents` адаптирует DTO в порядке событий и накладывает границы прочитанного. Он обновляет тела и окна одним действием store, обновляет указатели каталога со снимком `messagesById` после записи, затем подтверждает исходящие по порядку. Он ждёт `writeCreatedMessages(ownerKey, messages, epochVersion, isCurrent)`. Одна транзакция IndexedDB пишет тела, индекс и состояние окон, указатели кеша и отметку последнего события пачки. После проверки владельца обработчик обновляет проекции событий по порядку и выставляет видимый курсор. Отметка уже входит в запись пачки. [Активная пачка](../../../../packages/web/src/entities/messenger/messenger-realtime-applier.lib.ts#L737) · [Транзакция](../../../../packages/web/src/shared/lib/workspace-messenger-cache-db.ts#L2657)

Активный обработчик проверяет поверхность, сигнал, владельца активного store, если он установлен, и `isOwnerCurrent` с `runtimeGeneration`. Тот же предикат передаётся в `writeCreatedMessages` для проверки перед коммитом и повторно используется после ожидания. Активные ошибки кеша остаются best effort. Транспорт продвигает собственный курсор в памяти и устойчивом хранилище после завершения обработчика и проверки актуальности запуска. Отметка IndexedDB принадлежит кешу и записывается отдельно от курсора транспорта. Фоновый приём идёт через свой кеш и проекцию с подтверждением исходящих после записи, без записи в активные message/catalog store. [Проверка владельца](../../../../packages/web/src/entities/messenger/messenger-realtime-applier.lib.ts#L166) · [Фоновый обработчик](../../../../packages/web/src/entities/messenger/messenger-realtime-applier.lib.ts#L827) · [Асинхронное владение](../../../ORG_SCOPED_ASYNC_SAFETY.md)

### Что перенесено

1. Realtime-вход общего `acceptServerMessages` принимает `ownerKey`, существующий `isCurrent`, режим `single | batch`, нормализованные `MessengerMessage` и синхронный callback обновления указателей. Операция проверяет владельца перед записью и после синхронных действий. Результат сообщает, может ли обработчик продолжить остальные эффекты. В одиночном режиме передаётся одно сообщение, в пакетном — непустой массив из буфера. Тела и окна остаются в текущем `useWorkspaceMessageStore`. Общий приём подтверждает исходящие по входным сообщениям, даже если строка в окне уже есть или была удалена. Store сохраняет свои правила для незагруженного разговора и попадания в границы загруженного окна. [Хранилище](../../../../packages/web/src/entities/message/message.model.ts#L581) · [Общий приём](../../../../packages/web/src/entities/messenger/messages-accept-server.lib.ts)
2. Ветка создания `applyMessageRealtimeEvent` и активный callback `applyRealtimeEventBatch` вызывают эту операцию для записи и подтверждения. Адаптация DTO и граница прочитанного остаются на входах, каталог передаёт один callback с текущим `applyMessagePointer` или `applyMessagePointers`. В одиночном вызове `messages` передаёт callback снимок до записи и вызывает его после подтверждения. В пачке передаёт снимок после записи и вызывает его перед подтверждением. Так код каталога остаётся в обработчике, а модель отвечает за запись сообщений и согласование очереди. Существующие cache writers, проекции, курсоры и вызов живых эффектов остаются в обработчике с указанным выше порядком. Публичный контракт ленты `createMessages` сохраняется. При устаревании владельца обработчик завершает обработку до запуска записи кеша и остальных эффектов.

```ts
const applied = acceptServerMessages({
  source: "realtime",
  ownerKey: context.ownerKey,
  isCurrent,
  mode: "batch",
  messages,
  updatePointers: (messages, messagesById) =>
    useMessengerStore.getState().applyMessagePointers(context.ownerKey, messages, messagesById),
});
if (applied.status === "stale-owner") return;
```

## Шаг 5.1. Правки и перемещения

HTTP-ответ `editMessengerMessage` и активное событие `message.updated` передают снимок в `acceptMessageUpdate`. Эта операция внутри `messages` применяет изменение к известному телу и загруженным окнам, возвращает итоговое тело и координирует его запись в кеш. [HTTP-редактирование](../../../../packages/web/src/entities/messenger/messenger-message-actions.lib.ts) · [Активный realtime](../../../../packages/web/src/entities/messenger/messenger-realtime-applier.lib.ts) · [Приём правки](../../../../packages/web/src/entities/messenger/messages-accept-update.lib.ts)

1. HTTP сохраняет запрос, проверку контекста и валидацию Markdown и E2EE. В `messages` передаёт адаптированный снимок и ревизию, захваченную перед запросом. Активный realtime адаптирует событие, накладывает границу прочитанного и передаёт снимок той же операции. В обоих вызовах передаётся проверка актуальности владельца.
2. `messages` использует текущие правила ревизии и границ окон. Обычная правка меняет тело на прежнем месте. Перенос убирает UUID из исходного окна и добавляет в подходящее загруженное окно в пределах пагинации. Неизвестный UUID получает ревизию для защиты от старых ответов без создания тела. Отклонённый HTTP-ответ возвращает актуальное тело с прежним контрактом результата.
3. Кеш получает согласованное тело из store. Операция проверяет владельца и актуальность тела перед записью и в предикате транзакции. Если за время записи изменился флаг прочтения, операция повторяет запись того же тела со свежим флагом. При перемещении существующий cache writer обновляет принадлежность окнам. HTTP сохраняет обновление указателя каталога, активный realtime — синхронизацию реакций по принятому снимку. После записи кеша realtime обновляет лёгкую проекцию с актуальным флагом прочтения и продвигает курсор. Удаление, прочтение, команды опросов и фоновые события обрабатываются отдельно.

## Шаг 5.2. Удаление сообщений

Успешный `DELETE` и активное `message.deleted` передают принятое удаление в `acceptMessageDeletion`. Эта операция внутри `messages` применяет удаление к телу и загруженным окнам и координирует очистку кеша. 1. HTTP владеет запросом, сигналом и проверкой поколения сессии. Активный обработчик передаёт удалённый UUID, серверное размещение и проверку актуальности события. Оба входа передают принятое удаление одной внутренней операции `messages`.
2. `messages` удаляет тело и UUID из загруженных окон, фиксирует ревизию удаления и координирует очистку всех сохранённых вхождений UUID у владельца. Ревизия блокирует тело из истории, запрошенной до удаления. Повторное получение удаления приводит к тому же состоянию ленты, кеша и указателей. Записи и асинхронные продолжения проверяют владельца и поколение.
3. Каталог сохраняет снимок затронутых указателей перед очисткой и учитывает исходное и текущее размещение при перемещении во время HTTP. Восстановление выбирает замену через существующий механизм. Ранний результат может заменить ещё сохранённый указатель на удалённый UUID. Поздний результат сохраняет более новое последнее сообщение. Если у той же замены изменился только флаг прочтения, запись повторяется со свежим флагом. HTTP ждёт запись кеша и восстановление. Realtime ждёт запись удаления перед публикацией проекции и продвижением курсора. Запрос восстановления идёт отдельно. Удаление темы или стрима и фоновые события обрабатываются своими путями. ## 3. Что происходит после разрыва

```ts
// Внутри транспорта, упрощённый путь восстановления.
async function reconnect(run: RealtimeRun) {
  await socket.closeCurrent();
  if (!run.isCurrent()) return;

  const resumeFrom = cursor.current(run.owner);
  const processedThrough = await events.catchUp(run, { after: resumeFrom });
  if (!run.isCurrent()) return;

  await socket.open(run, { after: processedThrough });
}
```

Допустим, транспорт остановился после события 120. Пока связи не было, пришли 121 и 122. Reconnect закрывает прежний сокет, получает страницы событий после 120 по HTTP и применяет их по порядку. Новый WebSocket открывается от 122. Если 123 пришло между последней HTTP-страницей и открытием сокета, сервер доставляет его при начальном воспроизведении на сокете. Уведомления о новых событиях включаются после серверного `ready`, чтобы догрузка не выдавала старые события за новые.

Транспорт объединяет параллельные вызовы переподключения в одну попытку. Повтор после сетевой ошибки идёт с увеличивающейся задержкой. При остановке сессии запросы и таймеры отменяются. Если входящая очередь переполнилась, транспорт завершает текущую обработку и восстанавливает отброшенный хвост по HTTP с последней обработанной позиции. ## 4. Когда курсор истёк

После долгого отсутствия сервер может уже не хранить нужный участок журнала. HTTP 410 с ошибкой истёкшего курсора и соответствующее закрытие WebSocket запускают другое восстановление.

В текущем коде транспорт сбрасывает курсор этого владельца, отключает сокет, вызывает восстановление серверных снимков и планирует повтор через обычную задержку. Обработчик восстановления очищает соответствующий локальный кеш. Для активной сессии он также сбрасывает затронутые активные проекции и запрашивает данные заново. У фонового владельца свой путь восстановления. [Восстановление снимков в текущем коде](../../../../packages/web/src/widgets/layout/layout-workspace-realtime.hook.ts)

Целевой порядок использует тот же контракт, что bootstrap. Runtime берёт свежую точку отсчёта и собирает минимальные снимки, которые владельцы объявили обязательными для применения событий. Владельцы применяют снимки в контексте той же сессии и попытки. После их успеха новая граница становится пригодной для catch-up, затем открывается сокет. При сбое обязательного снимка попытка восстановления завершается ошибкой. Для повтора берём свежую границу и заново согласуем обязательные данные. Доступный кеш и независимые HTTP-запросы могут обслуживать экраны, пока realtime восстанавливается.

## Проверяемые переходы

| Ситуация                                                     | Ожидаемое поведение                                                                 |
| ------------------------------------------------------------ | ----------------------------------------------------------------------------------- |
| Обработчик события ещё пишет данные                          | Курсор этого события ждёт завершения обработки                                      |
| Неготовый обработчик неприменим к событию                    | Нужные обработчики применяют событие, курсор продвигается при успехе                |
| Нужный обработчик не готов или упал на 121                   | Курсор остаётся на 120, событие 122 ждёт, после восстановления повторяется 121      |
| Обязательный снимок при истечении курсора завершился ошибкой | Новая граница не используется, следующая попытка получает свежую точку отсчёта      |
| Одно событие пришло по REST и WebSocket                      | Состояние применяется один раз                                                      |
| После 120 пропущены 121 и 122                                | Пропущенные события применяются до открытия сокета от 122                           |
| 123 пришло между HTTP и сокетом                              | Начальное воспроизведение сокета доставляет 123                                     |
| Произошла смена владельца или сокета во время обработки      | Позднее завершение не продвигает курсор нового запуска                              |
| Курсор истёк                                                 | Для владельца восстанавливаются снимки, затем доставка продолжается с новой границы |
| Событие меняет каталог фонового B                            | Кеш и тёплый стор B обновляются, UI продолжает читать A                             |
