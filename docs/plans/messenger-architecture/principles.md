# Цель и принципы рефакторинга

[Карта заметок](README.md) · [Назначение модулей](modules.md)

Мы проектируем и постепенно реализуем модульную организацию Workspace. Сначала разбираем законченные сценарии на примерах вызовов и переходов состояния, затем переносим согласованную часть в код. В заметках отмечаем реализацию, предложение и открытые решения. Текущие правила импортов описаны в [архитектуре проекта](../../fsd-architecture.md).

## Какую проблему решаем

При разборе мессенджера обнаружилась сложность координации. Страница чата управляет черновиками, отправкой, загрузкой окон и реакциями на их завершение. Оболочка знает подробности bootstrap и realtime. Чтобы изменить один сценарий, приходится учитывать несколько соседних состояний и мест записи. Примеры текущих владельцев и предполагаемые границы разобраны в [отправке](scenarios/send-message.md), [истории](scenarios/load-messages.md), [bootstrap](scenarios/bootstrap.md) и [realtime](scenarios/realtime.md).

Цель разделения — сократить число мест, которые нужно понимать и менять для одного поведения, дать состоянию явного владельца и проверять сценарии отдельно от экранов. Мессенджер, почта и календарь получают собственные операции и данные, а общая платформа предоставляет инфраструктуру. Существующие механизмы защиты от гонок, курсоры и шифрование сохраняют свою необходимость.

Разбор realtime объясняет распределение ответственности при рефакторинге. Конкретный баг WebSocket, который требовал бы именно такого разделения, в обсуждении не установлен. Улучшение плавности проверяем измерениями конкретных операций и рендера.

## Бизнес-модуль владеет поведением

Модуль принимает намерение и управляет связанными данными, проверками, побочными эффектами и жизненным циклом. Его контракт скрывает выбор между HTTP, кешем и другими внутренними механизмами.

```ts
drafts.update(draftRef, { text });
sending.submitDraft({ draftRef, revision });
messages.loadMore({ conversationId, direction: "before" });
```

У каждого изменяемого бизнес-состояния есть владелец. Другие модули читают публичный снимок или вызывают операцию владельца. Проекция для UI и временное состояние операции имеют собственное назначение и правила обновления.

## UI отображает данные и передаёт намерения

Компонент представления получает данные и обработчики. Внутри остаются фокус, раскрытие панели, состояние меню, визуальное выделение, работа клавиатуры и другие локальные взаимодействия.

```tsx
function ComposerView({ text, onTextChange, onSend }) {
  const [emojiOpen, setEmojiOpen] = useState(false);

  return (
    <Editor
      value={text}
      onChange={onTextChange}
      onSend={onSend}
      emojiOpen={emojiOpen}
      onEmojiToggle={() => setEmojiOpen((open) => !open)}
    />
  );
}
```

Тонкая связка или хук подписывается на нужное состояние модуля и передаёт действия в представление.

```tsx
function ComposerConnected({ draftRef }) {
  const draft = useDraft(drafts, draftRef);

  return (
    <ComposerView
      text={draft.text}
      onTextChange={(text) => drafts.update(draftRef, { text })}
      onSend={() => sending.submitDraft({ draftRef, revision: draft.revision })}
    />
  );
}
```

Это абстрактные примеры контракта. Типы и точная форма подписки выбираются при реализации. Страница собирает компоненты и связывает маршрут с намерением открыть разговор. Координация сохранения черновика, шифрования, доставки и очистки отправленной версии живёт у владельцев сценария.

Чекбокс может иметь локальное состояние, пока оно относится к взаимодействию. Если выбор меняет сохраняемую настройку или голос в опросе, компонент передаёт действие в бизнес-модуль. Подписки и селекторы данных можно разместить в связке с UI. Правила получения производных бизнес-данных принадлежат модулю.

## Границы проверяем на поведении

Для каждого модуля фиксируем решаемую проблему, состояние и срок его жизни, публичные операции, потребителей и пользу границы. Сценарий показывает передачу ответственности между модулями на успехе, ошибке и актуальных гонках. Классы, синглтоны, объекты и функции остаются вариантами реализации.

Начинаем с одного согласованного сценария. Оцениваем, стало ли проще проследить действие, изменить его и проверить без загрузки всего экрана. Новую прослойку добавляем, когда она получает понятную ответственность. Стабильные данные и действия могут жить дольше компонента.
