# Общий запуск Workspace и realtime

[Карта заметок](README.md) · [Первое замечание ревью](review.md#p1-общие-данные-зависят-от-мессенджера) · [Bootstrap мессенджера](scenarios/bootstrap.md)

Общий запуск принадлежит сессии Workspace. Приложения и общие бизнес-модули подключаются к ней как потребители. Для первого этапа согласовано, как общий курсор ведёт себя при неготовности или сбое одного обработчика. Конкретные API и состав обязательных снимков уточняются при реализации.

Для доставки выбрана существующая композиция обработчиков `composeWorkspaceRealtimeAppliers`. Сборку переносим из `layout` на уровень Workspace. Отдельный dispatcher и таблица маршрутов для этого шага не требуются.

## Владельцы

| Часть                   | Ответственность                                                                                     |
| ----------------------- | --------------------------------------------------------------------------------------------------- |
| `app/workspace-session` | Держит runtime на владельца, собирает участников и сверяет запуски со списком авторизованных сессий |
| `platform/sessions`     | Предоставляет авторизованные сессии, их актуальность и текущий выбор для UI                         |
| `platform/realtime`     | Доставляет события через HTTP и WebSocket, держит соединение, курсор и повторы                      |
| `modules/users`         | Восстанавливает и обновляет каталог пользователей, применяет их события                             |
| Приложение              | Готовит свой каталог, проекции и обработчики, открывает окна по запросу своих экранов               |

Координатор сессии собирается в `app`, потому что знает конкретные приложения и модули. Платформа получает обработчик через параметр. Сессия здесь включает аккаунт, инстанс, организацию, проект и пользователя. Для разных владельцев создаются отдельные контексты работы.

## Сборка и доставка событий

```ts
// app/workspace-session.ts — абстрактная сборка для одной авторизованной сессии.
function createWorkspaceSession(session) {
  const users = createUsers({ session, http, storage });
  const messenger = createMessenger({ session, users, http, storage });
  const calendar = createCalendar({ session, users, http, storage });

  const activity = createActivity({ session, http, storage });

  const applier = composeWorkspaceRealtimeAppliers([
    users.events,
    messenger.events,
    calendar.events,
    activity.events,
  ]);

  const realtime = createRealtime({
    session,
    applier,
  });

  return { users, messenger, calendar, realtime };
}
```

Имена `calendar` и `events` иллюстрируют будущие контракты. Существование серверных событий календаря ещё нужно подтвердить при его проектировании.

Каждое событие получают все подключённые обработчики. Каждый определяет, относится ли оно к нему. Событие сообщения может обновить мессенджер и активность. Приложение календаря использует тот же `users` и подписывается на его состояние. Обработчики получают контекст сессии и проверяют актуальность перед записью.

Композиция собирается в [runtime Workspace](../../../packages/web/src/app/workspace-session/workspace-session.lib.ts). [Компоновщик](../../../packages/web/src/platform/realtime/workspace-realtime-applier.lib.ts) параллельно вызывает участников текущего события и ждёт завершения этих вызовов. Порядок событий внутри пакета подчиняется [контракту подтверждения](scenarios/realtime.md#шаг-12-общая-координация-и-повтор).

## Контракт обработки события

```ts
interface EventApplier {
  applyEvent(event: WorkspaceEvent, scope: EventScope): Promise<void>;
}

// Внутри обработчика мессенджера.
async function applyEvent(event: WorkspaceEvent, scope: EventScope) {
  if (!isMessengerEvent(event)) return;
  await applyMessengerEvent(event, scope);
}
```

Типы и имена условные. Успешное завершение означает одно из двух:

- Событие осознанно не относится к этому потребителю.
- Необходимая обработка события завершилась, включая ожидаемые записи, входящие в его контракт.

Обработчик проверяет применимость события до проверки готовности своих данных. Если событие ему нужно, а применить его пока невозможно, обработка возвращает отказ с причиной. Ошибка записи тоже считается отказом. Если несколько потребителей применяют событие, композиция ждёт их результаты. Между параллельными обработчиками нет гарантии порядка выполнения. Зависимую последовательность операций определяет владелец бизнес-сценария.

## Контракт продвижения курсора

```ts
// Упрощённый успешный путь одного события внутри транспорта.
async function processEvent(event, connection) {
  if (!connection.isCurrent()) return;
  if (cursor.hasProcessed(event.position)) return;

  await applier.applyEvent(event.payload, connection.scope);

  if (!connection.isCurrent()) return;
  cursor.commit(connection.owner, event.position);
}
```

На первом этапе у каждой авторизованной сессии один общий курсор её серверного журнала. REST и WebSocket доставляют события из этого журнала. Курсор может пройти событие только после успешного завершения всех нужных обработчиков и повторной проверки соединения, владельца и поколения. REST catch-up и WebSocket используют один контракт обработки. Известные дубли отбрасываются с учётом пары поколения журнала и позиции.

При ошибке курсор остаётся на предыдущей успешной позиции. Транспорт должен остановить применение следующих событий и перейти к восстановлению. К примеру, сбой 121 при курсоре 120 исключает продвижение на 122. Уже завершившие обработку потребители могут снова получить 121 при повторе, поэтому применение должно безопасно переносить повторы.

Перед восстановлением запущенные обработчики должны завершиться или потерять право записи. Композиция дожидается исходов вызванных обработчиков. При отмене попытки runtime отзывает право записи её сигналом и проверкой владельца.

Устойчивый курсор транспорта и кеш в IndexedDB сейчас сохраняются раздельно. Этот контракт сам по себе не гарантирует атомарность между хранилищами. На первом этапе сохраняем существующий контракт кеша и меняем координацию вызовов. Изменения гарантий записи и восстановления после перезапуска обсуждаются отдельно. [Граница первого этапа для кеша](platform.md#кеш-indexeddb-на-первом-этапе)

Для неподдерживаемого события возможен осознанный пропуск транспортом с диагностикой, как описано в [сценарии realtime](scenarios/realtime.md).

Обработчики участвующих приложений подключаются при запуске сессии. Отображение экранов, загрузка полной истории и рабочих диапазонов остаются по запросу. Обработчику достаточно состояния, необходимого для применения конкретного события.

## Готовность общего модуля и приложения

```ts
// Независимые задачи. Их реализация согласует снимки с событиями.
users.refresh(scope);
messenger.refreshCatalog(scope);
calendar.loadRange(scope, visibleRange);
```

Этот пример показывает независимость запросов. Конкретный порядок старта транспорта и подготовки проекций должен учитывать раннюю точку отсчёта и применённые события. Проверки согласования остаются внутри владельцев.

Вместо одного признака «всё готово» сохраняются отдельные статусы пользователей, каталога мессенджера, диапазона календаря и соединения. Сбой папок мессенджера остаётся ошибкой его каталога. Он не является условием запуска `users` или открытия календаря.

Для открытия пользователей или календаря сами сообщения, папки и история мессенджера загружаться не обязаны. Ранее описанный барьер полного каталога относится к старому порядку запуска. Его нельзя автоматически переносить на общий runtime Workspace.

## Общий курсор и ещё не готовые потребители

Готовность определяется по событию. Например, `model/chats` может обновить счётчик по известному чату при закрытом экране и недогруженном списке. Каждый владелец определяет, какие данные и записи обязательны для его обработки. UI читает состояния моделей и статус синхронизации.

- **Событие не относится к обработчику.** Он завершает вызов без записи, даже пока его данные загружаются. Продвижение курсора зависит от обработчиков, которым событие нужно.
- **Нужный обработчик не готов.** Он сообщает о неготовности. Транспорт сохраняет последний подтверждённый курсор и останавливает применение следующих событий. Владелец готовит минимальный снимок и согласует его с уже применёнными изменениями. Когда данные готовы, runtime запускает повтор с сохранённой позиции.
- **Применение или обязательная запись завершились ошибкой.** Транспорт так же останавливает дальнейшее применение. Перед повтором запущенные обработчики завершаются или теряют право записи. Runtime восстанавливает нужного владельца, а транспорт дочитывает события с последнего подтверждённого курсора. Для повторяющейся ошибки сохраняется статус сбоя и действует задержка между попытками.

Курсор на `120`. Событие `121` меняет счётчик чата, `122` обновляет профиль в `users`. Если `chats` может применить `121`, поток продолжает работу. Если нужны данные или запись упала, `122` ждёт, пока после восстановления успешно повторим `121`. Повтор может прийти и к обработчику, который уже завершил `121` до сбоя соседа. Применение данных и внешние эффекты должны быть безопасны при повторе. Календарь при этом может открыть доступный снимок и выполнить свои HTTP-запросы. Другие авторизованные сессии продолжают получать события со своих позиций.

При истечении курсора runtime получает свежую точку отсчёта до загрузки снимков. Владельцы готовят данные, обязательные для обработки событий этой сессии. Runtime ждёт их успешного применения, а транспорт дочитывает журнал от новой границы. [Восстановление после истечения](scenarios/realtime.md#4-когда-курсор-истёк)

Если потребителя подключат после старта сессии, его актуальность нужно восстановить отдельным снимком и воспроизведением от подходящей границы. Независимую realtime-доставку внутри сессии можно спроектировать на устойчивом локальном журнале с позициями потребителей, если появится такая потребность. Количество WebSocket само по себе этого решения не определяет.

## Runtime и тёплый стор на каждую сессию

Для рефакторинга выбрали отдельный runtime на каждого владельца авторизованной сессии. Он живёт на уровне Workspace, пока приложение работает и сессия авторизована. У него свои обработчики, курсор, кеш и экземпляры сторов. Модели мессенджера держат в памяти пригодные данные первого экрана: каталог, счётчики и уже загруженные последние сообщения. Сайдбар читает их через публичные подписки и собирает строки и превью для выбранной сессии. Realtime обновляет данные своей сессии в памяти и кеше независимо от выбора аккаунта в UI.

На шаге 12 менеджер запускает realtime runtime каждого владельца независимо от выбранного маршрута. Фоновые обработчики обновляют кеш и данные для уведомлений. Тёплые store добавляются на шаге 13, чтобы сразу показать каталог уже синхронизированной сессии при переключении. [Хост сессий](../../../packages/web/src/app/workspace-session/workspace-session.hook.ts)

```tsx
// Workspace передаёт список при запуске и изменении авторизованных сессий.
workspaceRuntimes.reconcile(auth.sessions);

// Оболочка передаёт runtime выбранного владельца. Имена условные.
function WorkspaceScreen({ activeOwnerKey, route, navigateToChat }) {
  const runtime = useWorkspaceRuntime(activeOwnerKey);
  if (runtime == null) return <WorkspaceLoading />;

  return (
    <MessengerPage runtime={runtime.messenger} route={route} navigateToChat={navigateToChat} />
  );
}
```

`MessengerPage` связывает сайдбар с маршрутом и передаёт ему сервисы выбранной сессии. [Сборка экрана](source-structure.md#экран-и-навигация) · [Владение состоянием и проекциями](principles.md#владение-состоянием-и-проекциями)

`reconcile` переиспользует запуски актуальных сессий, добавляет новые и останавливает выбывшие. При A → B React переключает публичные подписки на модели B. Обе сессии продолжают получать события. Уход с экрана закрывает его подписки и отменяет запросы этого экрана. Выход из аккаунта завершает его runtime и инвалидирует его операции. Выбор аккаунта и поколение запуска различаются. Запрос каталога A может завершиться в принадлежащем A сторе, пока его запуск актуален, а запоздавший UI-эффект от старого выбора A теряет право менять экран после A → B → A.

Bootstrap восстанавливает данные при запуске конкретной сессии. Пригодный снимок и курсор позволяют догнать события этой сессии. Если нужен новый снимок, его получение и воспроизведение событий согласуются в границах того же владельца. Например, если курсор B истёк, B восстанавливает свои данные, а A продолжает принимать события. При активации B интерфейс читает доступный снимок и статус синхронизации; готовый стор повторно загружать из IndexedDB из-за самого переключения не требуется.

Историю открываем по запросу. Недавно открытые окна можно удерживать с лимитом, а вытесненные восстанавливать из кеша с серверным обновлением. Так объём RAM и стоимость обновлений в фоне зависят от ограниченного набора данных, который нужен для быстрого переключения. Размер лимита выбираем по памяти, времени обработки событий и времени до появления списка чатов. [Загрузка истории](scenarios/load-messages.md)

## Шаг 13. Модели владельца и время жизни операций

После шага 12 [хост сессий](../../../packages/web/src/app/workspace-session/workspace-session.hook.ts)
назначает владельца активным store. [Сборка realtime](../../../packages/web/src/app/workspace-session/workspace-session.lib.ts)
использует активные store или фоновую проекцию и кеш. При смене аккаунта
auth меняет поколение входящей сессии, а при удалении фонового аккаунта
меняет поколение текущей сессии. [Модель авторизации](../../../packages/web/src/entities/workspace-auth/workspace-auth.model.ts)

| Точка переключения                  | Владелец и контракт                                                                                                                                                                                                                                         |
| ----------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Хост сессий, bootstrap и realtime   | Runtime создаёт модели при появлении авторизованного владельца. Снимки, обработчики, фоновые записи и восстановление получают фиксированную модель владельца. Один поток и одна позиция на сессию.                                                          |
| Каталог, индекс сообщений и лента   | UI подписывается на модели текущего владельца через `chats` и `messages`. Событие B меняет модели B, пока экран читает A. Открытие окна, запросы страницы и их эффекты проверяют поколение выбора.                                                          |
| Черновики, исходящие и криптография | Модели связывают принятый черновик, доставку и ресурсы с временем жизни авторизованного владельца. Подтверждение удаляет только отправленную ревизию его черновика. Очистка видимого редактора отдельно проверяет выбор и ревизию.                          |
| Выход и повторный вход              | Auth отзывает право записи завершённой сессии до очистки. Runtime останавливает её фоновые операции, освобождает модели и очередь и чистит данные этого владельца. Поздний результат очистки или токен-запроса прежней сессии не касается повторного входа. |

Точки в Messenger —
[каталог](../../../packages/web/src/applications/messenger/model/chats/chats.ts),
[индекс сообщений](../../../packages/web/src/applications/messenger/model/messages/messages-consumers.ts),
[окна](../../../packages/web/src/applications/messenger/model/messages/messages.ts),
[снимки](../../../packages/web/src/applications/messenger/runtime/sync/messenger-session-snapshot.lib.ts),
[доставка](../../../packages/web/src/applications/messenger/model/messages/outgoing/messenger-outbox-delivery.lib.ts)
и [действия с черновиками](../../../packages/web/src/applications/messenger/model/drafts/composer-draft-actions.lib.ts).
После шага 12 выход начинался в [auth](../../../packages/web/src/entities/workspace-auth/workspace-auth.lib.ts)
и удалял кеш до отзыва авторизации.

Ключ владельца по-прежнему включает аккаунт, инстанс, организацию,
проект и пользователя. Живой runtime и запрос выбранного экрана
имеют разную актуальность. На A → B → A новый выбор A заново
подключает UI к той же пригодной модели, а старый эффект экрана A
уже не может записать ответ. Запрос фоновой модели A может
закончиться в A, пока его авторизованный runtime актуален.
Обновление учётных данных ограждает запросы прежней версии той
же сессии и сохраняет её пригодные модели. Выход или замена
учётной сессии завершает конкретный экземпляр.

Публичные вызовы остаются у модели. Например, запрос окна получает
контекст экрана, а обработчик журнала применяет событие к уже
связанным моделям своего владельца. Подписки и запущенные окна
разделены владельцем даже при одинаковых UUID разговора.
Кеш и публикация store проверяют нужный контекст после ожиданий
и перед записью. [Правила отмены](../../ORG_SCOPED_ASYNC_SAFETY.md)

Критерии готовности

- A → B → A возвращает тёплый каталог и пригодное окно. Смена
  выбора сама по себе не запрашивает заново готовый каталог.
  Начальная загрузка истории происходит по запросу ленты.
- Фоновые события для обоих владельцев обновляют их модели и
  кеш. При восстановлении B после 410 A продолжает принимать
  события и сохраняет свои модели, курсор и очередь.
- Запоздалый экранный HTTP после A → B → A пропускает запись.
  Поздний запрос модели может изменить только свою живую
  сессию. Проверь одинаковые UUID у обоих владельцев и переход
  к новому входу того же аккаунта.
- Принятая отправка A может завершиться после переключения на B.
  Выход из B отменяет только операции B и удаляет очередь B.
  Поздний ответ B не создаёт заново удалённые записи и не
  меняет данные нового входа или очередь A.
