# Контракты интеграций между приложениями

[Карта заметок](README.md) · [Зависимости](dependencies.md) · [Структура src](source-structure.md)

Зафиксированный подход к проектированию будущих интеграций. Примеры абстрактные. Сценарий создания встречи из сообщения пока существует как предложение, его функции, типы и файлы ещё предстоит реализовать.

## Задача интеграции

Интеграция связывает публичные операции нескольких приложений. В примере мессенджер готовит данные сообщения, а календарь открывает черновик встречи. Преобразование данных и последовательность действий принадлежат `app/integrations`.

Потребитель получает конкретное действие через свой контракт. Как общий `users` передаётся приложениям при сборке, так и готовая интеграция может передаваться в приложение. Для кнопки достаточно функции, переданной экрану.

## 1. Контракт со стороны мессенджера

Мессенджер определяет, какое внешнее действие его UI умеет вызывать. Тип принадлежит его публичному интерфейсу.

```ts
// applications/messenger/messenger.ts
export interface MessengerActions {
  createMeeting?: (messageId: string) => Promise<void>;
}
```

`createMeeting` обозначает запрос подготовить черновик встречи из сообщения. В этом примере отсутствие обработчика означает недоступность действия. Завершение обещания означает завершение подготовки и открытия черновика. Сохранение самой встречи — последующее действие календаря.

## 2. Сборка абстрактной интеграции

```ts
// app/integrations/create-meeting-from-message.ts
function createMeetingIntegration({ messenger, calendar }) {
  return async function createMeeting(messageId: string) {
    const source = await messenger.prepareMeetingSource(messageId);

    return calendar.openMeetingDraft({
      title: source.title,
      description: source.text,
      sourceUrl: source.messageUrl,
    });
  };
}
```

В примере мессенджер предоставляет `prepareMeetingSource`, календарь — `openMeetingDraft`. Для согласования с `MessengerActions` предполагается, что открытие черновика возвращает `void` или `Promise<void>`. Нужные типы можно описать публичными контрактами приложений и передать интеграции только используемые операции.

Интеграция получает подготовленное содержимое через мессенджер. Тот сам обращается к сообщениям, криптосессии и подготовке отображения по своим правилам доступа. Последовательность подготовки, передачи разрешённых данных и открытия календаря остаётся явной. Точные поля `title`, `text` и `messageUrl` иллюстрируют преобразование и ещё обсуждаются.

## 3. App создаёт приложения и связывает их

```ts
// app/compose-workspace.ts
const messenger = createMessenger({ users, session, http });
const calendar = createCalendar({ users, session, http });

const createMeeting = createMeetingIntegration({
  messenger,
  calendar,
});
```

Сначала создаются бизнес-части приложений. Затем интеграция получает их публичные операции. После этого оболочка передаёт готовое действие экрану мессенджера.

```tsx
// app: сборка экрана.
<MessengerPage
  messenger={messenger}
  actions={{ createMeeting }}
/>;
```

Так обработчик можно собрать после создания обоих приложений и передать туда, где он нужен. Публичная форма `MessengerPage` здесь тоже условная.

## 4. UI вызывает переданное действие

```tsx
// Внутри меню сообщения в applications/messenger.
<MenuItem
  disabled={!actions.createMeeting}
  onClick={() => actions.createMeeting?.(message.id)}
>
  Создать встречу
</MenuItem>;
```

Пример показывает связь обработчика с действием меню. При реализации нужны локализованная подпись, отображение выполнения и обработка ошибки обещания. UI управляет состоянием взаимодействия, а интеграция выполняет последовательность бизнес-вызовов.

## Направление зависимостей

`app/integrations` может импортировать публичные входы приложений и типы их контрактов. Мессенджер получает функцию через собственный интерфейс. Вызов этой функции при нажатии кнопки не создаёт обратного импорта из приложения в `app`.

```text
Сборка
app → создаёт messenger и calendar
app → собирает createMeeting
app → передаёт createMeeting в MessengerPage

Выполнение
кнопка мессенджера → createMeeting(messageId)
createMeeting → messenger.prepareMeetingSource(messageId)
createMeeting → calendar.openMeetingDraft(preparedData)
```

Если совместное действие понадобится бизнес-процессу, контракт callback можно передать ему при сборке. Общий модуль `users` предоставляет каталог и подписки на данные. Интеграция предоставляет конкретный совместный сценарий.

## Что ещё предстоит определить

- Публичные типы приложений и состав передаваемых данных.
- Поведение навигации при открытии календаря и отображение ошибок.
- Актуальность сессии при асинхронной подготовке и передаче данных. Используем существующие [правила владения](../../ORG_SCOPED_ASYNC_SAFETY.md).
- Где конкретному потребителю удобнее получить действие — в props экрана или через контракт бизнес-процесса.
