# Следующие шаги архитектуры Workspace

[Карта заметок](README.md) · [Целевое дерево](source-structure.md) · [Правила импортов](../../fsd-architecture.md#files-and-imports)

После [14 шагов рефакторинга Messenger](README.md#порядок-рефакторинга) каталог пользователей загружается независимо от каталога чатов, а bootstrap и realtime собирает runtime Workspace. Модель пользователей остаётся в `entities/user`. Цель следующего этапа — проверить границы в CI и выделить общий каталог `modules/users`, доступный приложениям через публичный контракт.

## 1. Проверка импортов в CI

Команда `npm run arch:check` проходит на текущем дереве и подключена к локальному `npm run check` и обеим конфигурациям CI. [Проверка](../../../scripts/check-architecture.mjs) · [GitHub Actions](../../../.github/workflows/ci.yml) · [GitLab CI](../../../.gitlab-ci.yml)

- Проверка разбирает производственный TypeScript в `packages/web/src` и разрешает пути по web `tsconfig.json`. Относительные пути, `~/…` и реэкспорты проверяются по целевому файлу.
- Правила охватывают направления зависимостей старых FSD-слоёв и Messenger, а также ленивый вход `messenger.ts`. Проверка внутренних путей Messenger включает хранилища чатов, сообщений и черновиков, историю и исходящую очередь. В `shared/ui` и `shared/lib` внешний код использует установленный публичный `index` модуля, а внутренние файлы обращаются напрямую к конкретным файлам модуля.
- Декларации `import type` и `export type` участвуют только в проверке границ. Циклы определяются по статическим зависимостям исполнения. Формы `import { type X }` и `export { type X }` сохраняют такую зависимость при `verbatimModuleSyntax`.
- Существующие нарушения перечислены по правилу и направленной паре файлов. При исправлении связи удали её запись из списка исключений и повтори `npm run arch:check`. Команда показывает новые нарушения с путями файлов и требует удалить записи, которые больше не нужны. [Список исключений](../../../scripts/check-architecture-baseline.json)

## 2. Разорвать зависимости от Messenger

1. **Готово.** `buildWorkspaceRequestOptions` доступна через Workspace auth. Общая сборка параметров и обновление токена используются запросами Workspace и Messenger. Сессия запроса выбирается по переданному runtime, сигнал отмены передаётся при обновлении токена. [Вход Workspace auth](../../../packages/web/src/entities/workspace-auth/workspace-auth.lib.ts) · [Общая сборка параметров](../../../packages/web/src/entities/workspace-auth/workspace-auth-request-options.lib.ts)
2. **Готово.** `app` подключает очистку Messenger к завершению сессии. Auth отзывает право записи, а Messenger дожидается текущих операций и удаляет свой кеш. Повторный вход с тем же ключом владельца делает прежнее удаление неактуальным. [Контракт, порядок очистки и проверки](scenarios/session-end-cleanup.md)

## 3. Открыть контракт `users`

**Готово.** `entities/user` предоставляет отдельные входы для чтения, обновления профиля и runtime. Подписки UI следуют за выбранным аккаунтом, операции runtime получают владельца явно, а операции профиля согласуют модель и кеш. [Контракт, порядок переноса и проверки](scenarios/users-contract.md)

## 4. Перенести каталог в `modules/users`

Перенести модель, адаптеры, синхронизацию и их тесты за публичные входы `modules/users`. Включить в `arch:check` запрет внешних импортов внутренних файлов `users` и зависимостей `users → applications/*`. Удалить исключения, закрытые переносом. [Место каталога в дереве](source-structure.md#общий-каталог-пользователей)

Проверить `npm run arch:check`, `npm run typecheck` и сценарии `users`, auth и runtime. Критерии готовности — каталог пользователей загружается при сбое каталога Messenger, переключение A → B → A возвращает данные своего владельца, ссылка открывает кешированный профиль, а запоздавший ответ после выхода не записывает данные в store или кеш.
