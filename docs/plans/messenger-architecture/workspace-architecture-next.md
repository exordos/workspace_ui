# Следующие шаги архитектуры Workspace

[Карта заметок](README.md) · [Целевое дерево](source-structure.md) · [Правила импортов](../../fsd-architecture.md#files-and-imports)

После [14 шагов рефакторинга Messenger](README.md#порядок-рефакторинга) каталог пользователей загружается независимо от каталога чатов, а bootstrap и realtime собирает runtime Workspace. Модель пользователей остаётся в `entities/user`. Цель следующего этапа — проверить границы в CI и выделить общий каталог `modules/users`, доступный приложениям через публичный контракт.

## 1. Проверка импортов в CI

- Добавить `npm run arch:check` для `packages/web/src`. Использовать TypeScript и пути из `tsconfig.json`, чтобы относительный импорт и `~/…` вели к одному файлу. Учитывать реэкспорты.
- Проверять направления слоёв по действующей архитектуре и обход уже определённых публичных входов. Зависимости по типам тоже проходят проверку границ. Циклы определять по статическим импортам и реэкспортам значений.
- Зафиксировать существующие нарушения по точным связям файлов с причинами. Новая запрещённая связь или новый цикл должны завершать проверку ошибкой с путями файлов. Удалять записи из списка исключений вместе с исправлением связей.
- Подключить команду к локальному `npm run check`, GitHub Actions и GitLab CI. Проверить на текущем дереве и на примерах с новым запрещённым импортом, обходом публичного входа и циклом. Проверить, что импорт только типа не образует цикл исполнения.

## 2. Разорвать зависимости от Messenger

1. Передать `buildWorkspaceRequestOptions` и общую логику получения токена владельцу Workspace auth. Переключить потребителей на этот вход. Сохранить выбор сессии, обновление токена и отмену запросов. [Текущая сборка параметров](../../../packages/web/src/applications/messenger/model/messenger-request-options.lib.ts)
2. Отдельным изменением подключить очистку ресурсов Messenger через `app`. Auth определяет завершение сессии и отзывает право записи. Messenger дожидается текущих операций и удаляет свой кеш. Повторный вход с тем же ключом владельца делает прежнее удаление неактуальным. [Действующая очистка](../../../packages/web/src/entities/workspace-auth/workspace-auth.lib.ts) · [Правила привязки к сессии](../../ORG_SCOPED_ASYNC_SAFETY.md#selected-screen-and-owner-operations)

## 3. Открыть контракт `users`

Выделить узкие операции поверх действующей модели `entities/user`. UI получает чтение по UUID, выборки и подписки, например `users.useById(userUuid)`. Сценарии профиля передают подтверждённое обновление операции каталога, которая проверяет владельца, актуальность запроса и согласует store с кешем. Через вход для runtime подключаются восстановление кеша, обновление каталога и обработчик realtime. Точные сигнатуры определяем по потребителям. [Текущая модель](../../../packages/web/src/entities/user/user.model.ts) · [Сборка runtime](workspace-runtime.md#сборка-и-доставка-событий)

Порядок переключения — чтение в Messenger и оболочке, записи из профиля, аватара и ссылки на профиль, затем bootstrap и realtime. Каталог использует существующие экземпляры по владельцам сессий, а подписки UI следуют за выбранным аккаунтом. Операции runtime получают владельца явно.

## 4. Перенести каталог в `modules/users`

Перенести модель, адаптеры, синхронизацию и их тесты за публичные входы `modules/users`. Включить в `arch:check` запрет внешних импортов внутренних файлов `users` и зависимостей `users → applications/*`. Удалить исключения, закрытые переносом. [Место каталога в дереве](source-structure.md#общий-каталог-пользователей)

Проверить `npm run arch:check`, `npm run typecheck` и сценарии `users`, auth и runtime. Критерии готовности — каталог пользователей загружается при сбое каталога Messenger, переключение A → B → A возвращает данные своего владельца, ссылка открывает кешированный профиль, а запоздавший ответ после выхода не записывает данные в store или кеш.
