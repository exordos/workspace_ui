# Следующие шаги архитектуры Workspace

[Карта заметок](README.md) · [Целевое дерево](source-structure.md) · [Правила импортов](../../fsd-architecture.md#files-and-imports)

После [14 шагов рефакторинга Messenger](README.md#порядок-рефакторинга) каталог пользователей загружается независимо от каталога чатов, а bootstrap и realtime собирает runtime Workspace. Этот этап закрепил границы в CI и выделил общий каталог `modules/users`, доступный приложениям через публичный контракт.

## 1. Проверка импортов в CI

Команда `npm run arch:check` проходит на текущем дереве и подключена к локальному `npm run check` и обеим конфигурациям CI. [Проверка](../../../scripts/check-architecture.mjs) · [GitHub Actions](../../../.github/workflows/ci.yml) · [GitLab CI](../../../.gitlab-ci.yml)

- Проверка разбирает производственный TypeScript в `packages/web/src` и разрешает пути по web `tsconfig.json`. Относительные пути, `~/…` и реэкспорты проверяются по целевому файлу.
- Правила охватывают направления зависимостей старых FSD-слоёв и Messenger, а также ленивый вход `messenger.ts`. Проверка внутренних путей Messenger включает хранилища чатов, сообщений и черновиков, историю и исходящую очередь. В `shared/ui` и `shared/lib` внешний код использует установленный публичный `index` модуля, а внутренние файлы обращаются напрямую к конкретным файлам модуля.
- Декларации `import type` и `export type` участвуют только в проверке границ. Циклы определяются по статическим зависимостям исполнения. Формы `import { type X }` и `export { type X }` сохраняют такую зависимость при `verbatimModuleSyntax`.
- Существующие нарушения перечислены по правилу и направленной паре файлов. При исправлении связи удали её запись из списка исключений и повтори `npm run arch:check`. Команда показывает новые нарушения с путями файлов и требует удалить записи, которые больше не нужны. [Список исключений](../../../scripts/check-architecture-baseline.json)

## 2. Разорвать зависимости от Messenger

1. **Готово.** `buildWorkspaceRequestOptions` доступна через Workspace auth. Общая сборка параметров и обновление токена используются запросами Workspace и Messenger. Сессия запроса выбирается по переданному runtime, сигнал отмены передаётся при обновлении токена. [Вход Workspace auth](../../../packages/web/src/entities/workspace-auth/workspace-auth.lib.ts) · [Общая сборка параметров](../../../packages/web/src/entities/workspace-auth/workspace-auth-request-options.lib.ts)
2. **Готово.** `app` подключает очистку Messenger к завершению сессии. Auth отзывает право записи, а Messenger дожидается текущих операций и удаляет свой кеш. Повторный вход с тем же ключом владельца делает прежнее удаление неактуальным. [Контракт, порядок очистки и проверки](scenarios/session-end-cleanup.md)

## 3. Открыть контракт `users`

**Готово.** Публичный контракт сначала открыли в `entities/user` отдельными входами для чтения, обновления профиля и runtime. Подписки UI следуют за выбранным аккаунтом, операции runtime получают владельца явно, а операции профиля согласуют модель и кеш. [Контракт, порядок переноса и проверки](scenarios/users-contract.md)

## 4. Перенести каталог в `modules/users`

**Готово.** Модель, адаптеры, синхронизация, presence и их тесты находятся в `modules/users`. Потребители используют публичные входы чтения, профиля, runtime, селекторов и типов. `arch:check` проверяет внешние производственные импорты в каталог и запрещает зависимости `modules/users → applications/*`. [Место каталога в дереве](source-structure.md#общий-каталог-пользователей)

Проверить `npm run arch:check`, `npm run typecheck` и сценарии `users`, auth и runtime. Критерии готовности — каталог пользователей загружается при сбое каталога Messenger, переключение A → B → A возвращает данные своего владельца, ссылка открывает кешированный профиль, а запоздавший ответ после выхода не записывает данные в store или кеш.

## 5. Выделить буфер обмена в платформу

**Готово.** Первый вход платформы `platform/desktop/clipboard` предоставляет операции чтения текста, записи текста и изображений. Вызывающий код передаёт действие копирования в `shared/ui/copyable`. Внутри `src` команда `arch:check` ограничивает зависимости платформы своими файлами и `shared` и блокирует обратные импорты из `shared`. [Буфер обмена и мост Electron](platform.md#буфер-обмена-и-мост-electron)

Проверить браузерную и Electron-ветки адаптера, вызов копирования и отображение результата. Запустить `npm run arch:check`, `npm run typecheck` и целевые тесты адаптера, его потребителей и Electron.

## 6. Перенести системные уведомления в платформу

**Готово.** Оболочка использует `platform/notifications/notifications` для системного показа и закрытия уведомлений, запроса разрешения и обработки событий клика. Она определяет, когда показывать уведомление, как его сгруппировать и куда вести по клику. Точка входа приложения передаёт функцию показа в API плагинов, где доступ к ней проверяется по манифесту. Границу между `shared` и `platform` проверяет существующее правило CI. [Системные уведомления](platform.md#системные-уведомления)

Проверить браузерную и Electron-ветки сервиса, закрытие по тегу, переход по клику и доступ плагинов к показу. Запустить `npm run arch:check`, `npm run typecheck` и целевые тесты.

## 7. Перенести интеграцию с ОС в платформу

**Готово.** Адаптер `osIntegration` и его тесты находятся в `platform/desktop`. Оболочка использует адаптер для бейджа на значке и привлечения внимания к окну. В Electron операции идут через IPC, в веб-версии бейдж использует App Badging API при его наличии. [Интеграция с ОС](platform.md#интеграция-с-ос)

Проверить обе ветки адаптера и вызовы из хуков бейджа и уведомлений. Запустить `npm run arch:check`, `npm run typecheck` и целевые тесты.

## 8. Перенести транспорт realtime в платформу

**Готово.** `platform/realtime` содержит транспорт WebSocket, догрузку событий по HTTP, переподключение, курсоры по владельцам, менеджер runtime и композицию обработчиков. `app/workspace-session` подключает авторизованные сессии, подготовку снимков и обработчики приложений. Каждый обработчик применяет события в своём домене. [Транспорт realtime](platform.md#транспорт-realtime)

Проверить переподключение с последней подтверждённой позиции, восстановление после истечения курсора и смену аккаунта. Запустить `npm run arch:check`, `npm run typecheck` и целевые тесты транспорта и сессий.

## 9. Разместить контекст сессии и загрузку Feed

**Готово.** `workspace-runtime.types.ts`, `workspace-runtime.lib.ts` и `workspace-runtime.lib.test.ts` перемещены из `entities/workspace-runtime` в `platform/sessions` без смены поведения. Модуль содержит контекст владельца и проверку актуальности запроса. IAM-сессия, токен и выбранный контекст принадлежат `entities/workspace-auth`; композиция остаётся в `app/workspace-session`, realtime transport — в `platform/realtime`. `use-cache-first-page.hook.ts` перемещён в `pages/feed` к единственному потребителю Feed. Поведение и ключи сохранены, две устаревшие записи удалены из architecture baseline. [Контракты сессии](platform.md#граница-с-app-и-мессенджером) · [Текущие entrypoints](../../PROJECT_FACTS.md#текущие-entrypoints)

Проверить `npm run docs:check`, `npm run arch:check`, `npm run typecheck` и целевые тесты контекста сессии и Feed. Проверить показ кешированных данных Feed во время обновления, переключение владельца A → B → A и позднюю запись после выхода; подтвердить, что ключи и проверка актуальности сохранены, а Feed остаётся единственным потребителем хука.
