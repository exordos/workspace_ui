# Границы модулей

[Карта заметок](README.md) · [Цель и принципы](principles.md)

Предложенное расположение приложений, сущностей и общего каталога пользователей сохранено в [структуре src](source-structure.md). Начальный граф связей и примеры контрактов — в [зависимостях модулей](dependencies.md). Оба документа фиксируют вариант обсуждения, который ещё может измениться.

Для верхнего уровня выбрано `applications/messenger`, `applications/calendar` и `applications/mail`. Общие бизнес-модули находятся в `modules`, первый кандидат — `modules/users`. Таблица ниже описывает внутренние части приложения мессенджера. Их доменные модели остаются внутри приложения.

Workspace может оставаться одним приложением с модулями мессенджера, календаря и почты. Общая платформа предоставляет контекст сессии, транспорт запросов и событий, системные возможности. Библиотека компонентов общая. Домен сам владеет своими данными, операциями и фоновыми процессами. Оболочка подключает модули и связывает их публичные операции, например передаёт подготовленные данные сообщения в сценарий создания встречи.

Внутри мессенджера группируем код по ответственности. Публичный метод выражает намерение. Владелец состояния выбирает, как это намерение исполнить и какие данные изменить. Хранилище и реализация синхронизации могут оставаться за этой границей.

| Модуль         | Состояние и ответственность                                                                             |
| -------------- | ------------------------------------------------------------------------------------------------------- |
| `chats`        | Каталог чатов и тем, участие, данные для списка чатов                                                   |
| `composer`     | Взаимодействие с редактором: фокус, выделение и панели                                                  |
| `drafts`       | Текст, ответы и цитаты, ссылки на вложения, версия, статус сохранения и конфликты                       |
| `sending`      | Снимок принятой отправки, очередь, подготовка, доставка, ошибки и повтор                                |
| `messages`     | Подтверждённые сообщения, применение обновлений и кеш                                                   |
| `crypto`       | Криптосессии, ключи, шифрование и расшифровка                                                           |
| `presentation` | Подготовленное представление сообщения, в том числе временное расшифрованное содержимое                 |
| `timeline`     | Выбор окна для просмотра, расположение строк, навигация и прокрутка. Данные окна принадлежат `messages` |
| `polls`        | Сценарии опросов и временное состояние интерфейса. Серверный опрос остаётся частью сообщения            |
| `sync`         | Координация запуска, восстановления и обработки событий                                                 |

## Какую проблему решает разделение

| Модуль             | Проблема, которую он берёт на себя                                       | Что упрощается для потребителя                                                                  |
| ------------------ | ------------------------------------------------------------------------ | ----------------------------------------------------------------------------------------------- |
| `chats`            | Согласование каталога, участия, тем и данных для списка чатов            | Экраны читают одну модель и вызывают операции чата                                              |
| `composer`         | Взаимодействие с редактором, фокус и локальные панели                    | Внешний код передаёт данные и обрабатывает намерения ввода и отправки                           |
| `drafts`           | Сохранение версий черновика, приватность и конфликты                     | Composer вызывает `drafts.update` без самостоятельного выбора хранилища и очереди синхронизации |
| `sending`          | Доставка снимка после его передачи из черновика, повтор и подтверждение  | Закрытие экрана не теряет принятую отправку, завершение не очищает новый ввод                   |
| `messages`         | Согласование тел и окон из кеша, HTTP и событий                          | Лента читает снимок, вызывает `openWindow` и `loadMore`, не управляя слиянием данных            |
| `crypto`           | Ключи, криптосессии и допустимость криптографических операций            | Отправка и подготовка содержимого используют общий контракт                                     |
| `presentation`     | Подготовка отображения и инвалидирование временного открытого текста     | Компоненты получают состояния готовности, отсутствия ключа и ошибки                             |
| `timeline`         | Сохранение позиции, навигация и поведение списка при изменении строк     | Данные могут обновляться независимо от положения читателя                                       |
| `polls`            | Голосование, создание и управление опросом                               | Страница и оболочка сообщения вызывают понятные действия опроса                                 |
| `sync`             | Последовательность запуска и восстановления, передача событий владельцам | Оболочка управляет сессией через `start/stop`                                                   |
| Транспорт realtime | Соединение, порядок обработки, курсор и переподключение                  | Доменные обработчики получают события одинаково из catch-up и WebSocket                         |

Границы помогают локально менять и проверять поведение. Названия модулей и форма реализации ещё уточняются. Один сценарий может затрагивать несколько владельцев через явные вызовы. Подробные технические гарантии фиксируем в странице этого сценария.

## Composer и черновики

```ts
function onTextChange(text: string) {
  drafts.update(draftRef, { text });
}

function onSubmit() {
  return sending.submitDraft({ draftRef, revision: draft.revision });
}
```

`draftRef` обозначает черновик в контексте аккаунта, проекта и разговора. `drafts.update` применяет изменение текста, сохраняя остальные поля, и управляет дальнейшим сохранением. Composer подписывается на состояние черновика. Готовность и загрузка файлов имеют своё состояние. В черновике могут храниться ссылки на вложения, а хранение самого `File` требует отдельного решения.

Обычный черновик сохраняется по принятой политике. Для секретных фрагментов и E2EE действует защита приватного содержимого. Позднее завершение сохранения старой версии не должно заменить новую.

Уже существуют [модель черновиков](../../../packages/web/src/entities/composer-draft/composer-draft.model.ts) и [операции синхронизации, удаления и защиты](../../../packages/web/src/entities/composer-draft/composer-draft-sync.lib.ts). Страница чата в `updateWorkspaceComposerDraft` ещё координирует выбор между ними. Черновики зашифрованных чатов исключены из обычного потока серверной синхронизации. Секретные фрагменты в обычном чате получают отдельную защиту. [Страница чата](../../../packages/web/src/pages/chat/chat-page-workspace.ui.tsx)

## Классы как способ представить границы

`Drafts` и `Sender` можно представить как объекты с собственным состоянием и публичными методами. Это помогает понять, кто вправе менять данные и кто может вызвать операцию. Сигнатуры в заметках условные. Реализация может использовать классы, функции или существующие stores.

```ts
const drafts = new Drafts({ session, storage });
const sender = new Sender({ session, drafts, crypto, messages });

drafts.update(draftRef, { text });
await sender.submitDraft({ draftRef, revision });
```

Один экземпляр сервиса тоже возможен, если его время жизни соответствует состоянию. Например, один `Sender` на активную сессию может обслуживать несколько экранов. Если экземпляр один на приложение, нужно явно разделить данные разных владельцев и инвалидировать работу завершившейся сессии. Варианты создания экземпляров и области их жизни остаются открытым вопросом.
