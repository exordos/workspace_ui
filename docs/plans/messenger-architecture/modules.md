# Границы модулей

[Карта заметок](README.md) · [Цель и принципы](principles.md)

Целевое расположение приложений, features, модели и общего каталога пользователей сохранено в [структуре src](source-structure.md). Начальный граф связей и примеры контрактов — в [зависимостях модулей](dependencies.md).

Для верхнего уровня выбрано `applications/messenger`, `applications/calendar` и `applications/mail`. В `modules/users` находится общий каталог пользователей Workspace. Таблица ниже описывает внутренние части приложения мессенджера. Их доменные модели остаются внутри приложения.

Workspace может оставаться одним приложением с модулями мессенджера, календаря и почты. Общая платформа предоставляет контекст сессии, транспорт запросов и событий, системные возможности. Библиотека компонентов общая. Домен сам владеет своими данными, операциями и фоновыми процессами. Оболочка подключает модули и связывает их публичные операции, например передаёт подготовленные данные сообщения в сценарий создания встречи.

Внутри мессенджера `pages` собирает экран, `features` отвечает за самостоятельные блоки, а `model` — за состояние и бизнес-операции. Публичный метод выражает намерение. Владелец выбирает, как его исполнить и какие данные изменить. Хранилище и синхронизация скрыты за его контрактом.

| Модуль                                                  | Состояние и ответственность                                                                                                                    |
| ------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------- |
| `pages/messenger`                                       | Маршрут, выбранный разговор, раскладка и взаимодействие блоков.                                                                                |
| `features/sidebar`                                      | Поиск в списке, раскрытие групп, сортировка и удержание позиции после локального действия. Читает каталог и передаёт выбор чата странице.      |
| `features/conversation-header`, `features/chat-details` | Заголовок и его действия, сведения о выбранном чате и участниках. Публичные операции над чатом остаются в модели.                              |
| `features/composer`                                     | Взаимодействие с редактором, фокус, выделение и панели.                                                                                        |
| `features/timeline`                                     | Выбор окна для просмотра, навигация, строки и прокрутка. Данные окна принадлежат `model/messages`.                                             |
| `features/decrypted-message`                            | Подготовка открытого текста для ленты, цитат и превью. Актуальность попытки, ожидание, отсутствие ключа и повтор.                              |
| `features/polls`                                        | Содержимое бабла, создание и действия опроса, ожидание и ошибки UI. Подтверждённое состояние входит в сообщение.                               |
| `model/chats`                                           | Каталог чатов и тем, участие и состояние закрепления.                                                                                          |
| `model/drafts`                                          | Текст, ответы и цитаты, ссылки на вложения, версии, статус сохранения и конфликты.                                                             |
| `model/messages`                                        | Подтверждённые сообщения, окна, кеш и общий приём. Внутренний `outgoing` отвечает за доставку и повтор, `polls` — за команды и ревизии опроса. |
| `model/crypto`                                          | Криптосессии, ключи и операции шифрования и расшифровки. Потребители передают шифротекст и необходимые поля контекста.                         |
| `runtime/sync`                                          | Координация запуска, восстановления и направления событий владельцам.                                                                          |

## Какую проблему решает разделение

| Модуль              | Проблема, которую он берёт на себя                                                         | Что упрощается для потребителя                                                                                                     |
| ------------------- | ------------------------------------------------------------------------------------------ | ---------------------------------------------------------------------------------------------------------------------------------- |
| `chats`             | Согласование каталога, участия, тем и данных для списка чатов                              | Экраны читают одну модель и вызывают операции чата                                                                                 |
| `composer`          | Взаимодействие с редактором, фокус и локальные панели                                      | Внешний код передаёт данные и обрабатывает намерения ввода и отправки                                                              |
| `drafts`            | Сохранение версий черновика, приватность и конфликты                                       | Composer вызывает `drafts.update` без самостоятельного выбора хранилища и очереди синхронизации                                    |
| `messages`          | Согласование тел, окон и исходящих операций из кеша, HTTP и событий                        | Лента читает данные и вызывает `openWindow`/`loadMore`; Composer вызывает `sendDraft`. Закрытие экрана не теряет принятую отправку |
| `crypto`            | Ключи, криптосессии и допустимость криптографических операций                              | Отправка и подготовка содержимого используют общий контракт                                                                        |
| `decrypted-message` | Общий жизненный цикл подготовки зашифрованного содержимого и инвалидация открытого текста. | Лента, цитаты и превью получают актуальный результат или состояние расшифровки.                                                    |
| `timeline`          | Сохранение позиции, навигация и поведение списка при изменении строк                       | Данные могут обновляться независимо от положения читателя                                                                          |
| `polls`             | Взаимодействие с опросом и оформление его состояния.                                       | Лента подключает `PollBody`, а кнопки вызывают публичные команды `messages`.                                                       |
| `sync`              | Последовательность запуска и восстановления, передача событий владельцам                   | Оболочка управляет сессией через `start/stop`                                                                                      |
| Транспорт realtime  | Соединение, порядок обработки, курсор и переподключение                                    | Доменные обработчики получают события одинаково из catch-up и WebSocket                                                            |

Границы помогают локально менять и проверять поведение. Названия модулей и форма реализации ещё уточняются. Один сценарий может затрагивать несколько владельцев через явные вызовы. Подробные технические гарантии фиксируем в странице этого сценария.

## Отправка как внутренняя часть messages

После второго пункта ревью выбрано оставить отправку внутри `model/messages`. Внутренний `outgoing` хранит снимки исходящих операций, попытки, ошибки и подготовленный payload; часть хранения подтверждённых сообщений владеет серверными телами и кешем. Общий сценарий `messages` согласует их при получении HTTP-ответа, истории или realtime. Они не импортируют друг друга и не создают вторую копию серверной истории.

Отдельный публичный `sending` пока не даёт установленной пользы: его самостоятельное использование и отдельный жизненный цикл не обоснованы, а подтверждение из истории потребовало бы обратной зависимости или внешнего координатора. Внутреннее разделение сохраняет возможность отдельно проверять очередь и историю. [Кейс, варианты и примеры общего приёма](scenarios/send-message.md#решение-отправка-внутри-messages)

## Composer и черновики

```ts
function onTextChange(text: string) {
  drafts.update(draftRef, { text });
}

function onSubmit() {
  return messages.sendDraft({ draftRef, revision: draft.revision });
}
```

`draftRef` обозначает черновик в контексте аккаунта, проекта и разговора. `drafts.update` применяет изменение текста, сохраняя остальные поля, и управляет дальнейшим сохранением. Composer подписывается на состояние черновика. Готовность и загрузка файлов имеют своё состояние. В черновике могут храниться ссылки на вложения, а хранение самого `File` требует отдельного решения.

Обычный черновик сохраняется по принятой политике. Для секретных фрагментов и E2EE действует защита приватного содержимого. Позднее завершение сохранения старой версии не должно заменить новую.

Уже существуют [модель черновиков](../../../packages/web/src/applications/messenger/model/drafts/composer-draft.model.ts) и [операции синхронизации, удаления и защиты](../../../packages/web/src/applications/messenger/model/drafts/composer-draft-sync.lib.ts). Страница чата в `updateWorkspaceComposerDraft` ещё координирует выбор между ними. Черновики зашифрованных чатов исключены из обычного потока серверной синхронизации. Секретные фрагменты в обычном чате получают отдельную защиту. [Страница чата](../../../packages/web/src/applications/messenger/pages/messenger/chat-page-workspace.ui.tsx)

## Шаг 10. Каталог и потребители сообщений

Сайдбар читает каталог и сообщения через подписки владельцев и объединяет их с пользователями. Заголовок и панель деталей используют данные каталога и вызывают его команды. Состояние участия, кеш и очередь остаются у моделей. [Контракт каталога](../../../packages/web/src/applications/messenger/model/chats/chats.ts) · [Чтения сообщений](../../../packages/web/src/applications/messenger/model/messages/messages-consumers.ts) · [Подписка сайдбара](../../../packages/web/src/applications/messenger/features/sidebar/sidebar-projection.hook.ts)

1. `chats` открывает нужные для интерфейса снимки каталога и команды чата, темы, папки и участия. Прежние store, проекции и операции переиспользуются внутри владельца. Подписки и команды сохраняют привязку к владельцу и поколению; переключение аккаунта сразу скрывает снимок прежней сессии.
2. `messages` открывает чтение сообщения по UUID и оставшиеся действия и подписки потребителей. Сайдбар объединяет каталог, превью и пользователей в своей проекции и сохраняет текущую частоту обновления. Заголовок и детали формируют свои представления из данных владельцев. Страница оставляет маршрут, состояние диалогов и действия интерфейса.
3. До переноса дерева сверяем оставшиеся обращения к store, кешу и outbox, включая служебные входы оболочки, bootstrap, realtime, фоновое чтение и очистку аккаунта. Для каждого оставшегося места фиксируем потребителя, владельца и шаг переноса. Снимки данных из тестов и временные внутренние зависимости модели отмечаем отдельно от внешних потребителей.

Проверяем обновление текста превью и счётчика, команды контекстного меню, заголовок и детали при смене темы или участника, а также A → B → A и устаревшие снимки. Используем тесты проекции сайдбара, страницы, панели деталей, bootstrap и realtime, а в браузере — `sidebar.spec.ts`, `thread-read-badge.spec.ts` и `workspace-realtime.spec.ts` с `@mock`.

## Классы как способ представить границы

`Drafts` и `Messages` можно представить как объекты с собственным состоянием и публичными методами. Внутренний `Sender` или `Outgoing` тоже может быть классом, при этом потребители работают с `messages`. Это помогает понять, кто вправе менять данные и кто может вызвать операцию. Сигнатуры в заметках условные. Реализация может использовать классы, функции или существующие stores.

```ts
const drafts = new Drafts({ session, storage });
const messages = new Messages({ session, drafts, crypto, http, storage });

drafts.update(draftRef, { text });
await messages.sendDraft({ draftRef, revision });
```

Один экземпляр сервиса тоже возможен, если его время жизни соответствует состоянию. Например, один `Messages` с внутренней очередью на сессию может обслуживать несколько экранов. Если экземпляр один на приложение, нужно явно разделить данные разных владельцев и инвалидировать работу завершившейся сессии. Варианты создания экземпляров и области их жизни остаются открытым вопросом.
