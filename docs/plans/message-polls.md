# Опросы в сообщениях

Статус: реализация первой итерации в работе. Контракт и решения ниже сохраняют контекст плана; актуальное поведение проверяйте по исходному коду и тестам клиента и сервера.

Технический порядок серверных работ, DM/DTO, миграция и решения замечаний ревью вынесены в [план бэкенда](message-polls-backend.md). Он уточняет серверную реализацию; правила пользователя и примеры ниже сохраняют общий контекст.

## Цель и возможности пользователя

Участник обычного чата Workspace может отправить вопрос с вариантами ответа и собрать голоса других участников прямо в переписке. Один опрос — одно сообщение с одним или несколькими вопросами с выбором вариантов ответа. Форма начинается с одного вопроса, дополнительные добавляет автор. В общих настройках один переключатель режима ответа действует на все вопросы; по умолчанию выбран один вариант. Начальные серверные лимиты — до 20 вопросов и до 20 вариантов в каждом.

| Возможность                    | Поведение первой итерации                                                                                                                                                                                                |
| ------------------------------ | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| Создать опрос                  | От 1 до 20 вопросов, у каждого от 2 до 20 вариантов. Лимиты заданы серверными константами и меняются патчем. Порядок вопросов и вариантов задаёт автор.                                                                  |
| Разрешить добавление вариантов | Общий флаг allow_adding_options. При включении участники с правом голосования могут добавлять варианты к любому вопросу открытого опроса. Флаг можно менять после публикации.                                            |
| Выбрать режим ответа           | Один вариант или несколько; обязательный boolean multiple_answers задаётся в payload опроса и действует одинаково для всех вопросов. Выбор ответов в каждом вопросе независим.                                           |
| Указать правильные варианты    | Необязательные отметки у каждого вопроса. После принятия ответа клиент показывает правильные варианты этого вопроса; до ответа отметки не показывает.                                                                    |
| Настроить анонимность          | В открытом опросе можно посмотреть участников каждого варианта. В анонимном доступны только счётчики и собственный выбор.                                                                                                |
| Разрешить переголосование      | Общая настройка allow_revote проверяется для каждого вопроса отдельно. При false одиночный ответ нельзя менять или снимать; при множественном выборе можно только добавлять варианты. При true разрешены смена и снятие. |
| Настроить показ результатов    | Сразу или после собственного ответа на соответствующий вопрос. Правило отображения на клиенте; сервер может отдавать агрегаты в обоих режимах.                                                                           |
| Проголосовать                  | Каждый клик по варианту сразу отправляет отдельный запрос. Нет общей кнопки отправки, кнопок у вопросов и накопления вариантов перед отправкой. Можно отвечать на вопросы в любом порядке и пропускать их.               |
| Посмотреть результаты          | Число участников, число голосов за каждый вариант и проценты. Проценты и их округление рассчитывает клиент.                                                                                                              |
| Закрыть опрос                  | Автор, владелец, администратор или модератор исходного чата. После закрытия голосовать, менять и отзывать голос нельзя.                                                                                                  |
| Настроить срок закрытия        | Необязательная дата и время завершения. Пока опрос открыт, срок можно назначить, перенести или убрать, даже если уже есть голоса.                                                                                        |
| Переслать результаты           | Копия только для чтения с переходом к исходному сообщению. Голосование возможно в оригинале при наличии доступа к исходному чату.                                                                                        |

Предлагаемые начальные значения формы: один вопрос, общий одиночный выбор (multiple_answers=false), неанонимный режим, переголосование выключено, результаты после голосования. Это предложения, а не утверждённые значения по умолчанию. Клиент явно передаёт обязательные настройки при создании; сервер сохраняет их и проверяет действующие правила, не выбирая поведение по версии приложения. Поле `closes_at` необязательно.

Автоматическое закрытие входит в первую итерацию. Необязательное поле `closes_at` задаёт абсолютную дату и время завершения, а не длительность жизни опроса. Если поле не передано или равно `null`, автоматического закрытия нет — опрос остаётся открытым до ручного закрытия. Срок можно назначить, изменить или убрать после публикации, в том числе после появления голосов, пока опрос открыт. Анонимность после публикации менять нельзя.

## Границы первой итерации

| Сценарий                   | Решение                                                                                                                                                                                                                                                                              |
| -------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| Обычный чат Workspace      | Создание, голосование, результаты и закрытие. Критерий — тип и доступность чата, без отдельного списка приглашённых к голосованию.                                                                                                                                                   |
| E2EE                       | Создание и активные опросы временно недоступны. Сервер также отклоняет создание незашифрованного `poll` в E2EE-чате. Полноценная поддержка требует отдельного протокола для вопроса и голосов.                                                                                       |
| Чат Zulip                  | Создание и активное голосование не поддерживаются. Можно доставить обычное сообщение со снимком результатов; поддержка `poll` самим Zulip не предполагается.                                                                                                                         |
| Пересланное сообщение      | Снимок вопросов, вариантов и результатов на момент пересылки. Предложение: не переносить списки проголосовавших и не обновлять копию автоматически.                                                                                                                                  |
| Анкеты                     | Несколько вопросов с выбором вариантов входят в тот же kind poll. Отдельный survey для этого не нужен. Формы со свободным текстом, ветвлениями и другими типами полей не входят в итерацию.                                                                                          |
| Дополнительные возможности | Полноценные викторины с баллами и таблицей лидеров, свободный текст, изображения, рейтинги, приглашённые группы, напоминания и экспорт не входят в итерацию. Базовые отметки правильных вариантов входят в первую версию. Это кандидаты на развитие без обещанного срока реализации. |

Снимок результатов можно переслать существующим потоком пересылки как `markdown`. Он не создаёт новый активный опрос и не получает записей голосов. Внешний получатель видит именно сохранённый снимок; ссылка на оригинал не предоставляет доступ к закрытому чату.

Анонимность означает отсутствие раскрытия другим пользователям. Сервер хранит автора голоса для уникальности, настройки переголосования и выдачи `my_votes`; криптографической анонимности от сервера эта итерация не обещает.

Скрытие результатов до голосования — намеренно мягкое правило интерфейса. Пользователь, анализирующий API, сможет увидеть доступные ему агрегаты; это допустимо по выбранному продуктовому требованию.

## Формат сообщения

kind находится внутри message.payload. В API содержимое называется payload, физически хранится в JSONB messenger_message_contents.workspace_content; сообщение ссылается на него через content_uuid. Для вопросов, вариантов и настроек не нужны новые колонки корневой таблицы сообщений. Нужно зарегистрировать и валидировать PollPayload; JSONB не означает произвольные поля вне контракта.

### Payload при создании

multiple_answers обязателен на уровне payload; внутри questions[] это неизвестное поле и отклоняется. Режим един для всех вопросов, но собственные ответы хранятся и меняются независимо по каждому вопросу. correct_option_uuids остаётся необязательным полем каждого вопроса.

Все UUID в примерах синтетические. Для одного вопроса используется тот же массив questions с одним элементом; отдельного формата нет. Порядок массивов задаёт порядок показа. UUID вопросов и вариантов не зависят от позиции или текста.

```json
{
  "kind": "poll",
  "multiple_answers": true,
  "questions": [
    {
      "uuid": "55555555-5555-4555-8555-555555555555",
      "text": "В какой день встречаемся?",
      "options": [
        {
          "uuid": "11111111-1111-4111-8111-111111111111",
          "text": "Понедельник"
        },
        {
          "uuid": "22222222-2222-4222-8222-222222222222",
          "text": "Вторник"
        }
      ],
      "correct_option_uuids": ["11111111-1111-4111-8111-111111111111"]
    },
    {
      "uuid": "66666666-6666-4666-8666-666666666666",
      "text": "Где встречаемся?",
      "options": [
        {
          "uuid": "77777777-7777-4777-8777-777777777777",
          "text": "В офисе"
        },
        {
          "uuid": "88888888-8888-4888-8888-888888888888",
          "text": "Онлайн"
        }
      ]
    }
  ],
  "is_anonymous": false,
  "allow_revote": false,
  "results_visibility": "after_vote",
  "closes_at": null,
  "allow_adding_options": true
}
```

| Поле                             | Тип и правило                                                                                                                                                                                                                                               |
| -------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| kind                             | Только poll.                                                                                                                                                                                                                                                |
| questions                        | Обязательный непустой массив вопросов; максимум настраивается на сервере, начальное значение 20. UUID вопросов уникальны внутри сообщения.                                                                                                                  |
| questions[].uuid                 | UUID вопроса.                                                                                                                                                                                                                                               |
| questions[].text                 | Непустой текст; предлагаемый предел 1000 символов, согласовать с бэкендом.                                                                                                                                                                                  |
| questions[].options              | От 2 до серверного максимума вариантов, начальное значение 20. UUID вариантов уникальны внутри вопроса, текст непустой. Предлагаемый предел текста 200 символов.                                                                                            |
| multiple_answers                 | Обязательный boolean в payload опроса, единый для всех вопросов. false — не более одного выбранного варианта в каждом вопросе, true — несколько, не больше числа вариантов соответствующего вопроса. Выбор между вопросами независим.                       |
| questions[].correct_option_uuids | Необязательный массив UUID без повторов, только из options того же вопроса. Отсутствие или пустой массив — без отметок правильности.                                                                                                                        |
| is_anonymous                     | Обязательный boolean, общий для опроса.                                                                                                                                                                                                                     |
| allow_revote                     | Обязательный boolean, общий для опроса; применяется к каждому вопросу отдельно. false запрещает снятие и замену принятых вариантов, но допускает добавления при множественном выборе. true разрешает изменения до закрытия.                                 |
| allow_adding_options             | Необязательный boolean, общий для всех вопросов. При отсутствии в создании сервер сохраняет false; в чтении поле есть всегда. Разрешает добавление вариантов участникам с правом голосования. Меняется после публикации отдельным действием.                |
| results_visibility               | Обязательное always или after_vote. При after_vote клиент показывает результаты конкретного вопроса после принятия собственного ответа на него; пропущенные вопросы до закрытия остаются скрыты.                                                            |
| closes_at                        | Необязательная абсолютная дата ISO 8601 с часовым поясом либо null. Отсутствие при создании равнозначно null. Нормализуется в UTC, должна быть в будущем. В чтении поле есть всегда. Пока опрос открыт, срок меняется через общее действие update_settings. |

### Лимиты опроса

Количество вопросов и вариантов ограничено серверными константами: максимум 20 вопросов и 20 вариантов на вопрос. Для изменения значений нужен патч кода, миграция БД не нужна. Новые лимиты применяются к созданию опросов и добавлению вариантов; чтение и голосование по старым опросам используют сохранённую структуру даже после снижения лимитов. Если текущих вариантов уже не меньше нового лимита, новые не добавляются, существующие не удаляются.

Лимиты задаются константами и проверяются бэкендом. Отдельный API объявления поддержки опросов или выдачи их лимитов в первую версию не добавляется.

Текущий максимум — 20 вопросов по 20 вариантов, всего 400 вариантов. Это не требование создать 20 вопросов или ответить на каждый: автор может добавить один или несколько, пользователь отвечает на любые вопросы независимо.

### Изменение после публикации и закрытие

Серверное поле payload.closed_at: datetime | null хранит только ручное закрытие. Его нет в создании, в чтении оно присутствует. При создании сервер устанавливает null, при ручном закрытии — серверную дату и время. Истечение closes_at не записывает closed_at. Клиент не может переоткрыть опрос обычным PUT.

Закрытие, изменение срока, переключение allow_adding_options и добавление вариантов используют существующий механизм неизменяемых content pages и ревизий, а не UPDATE workspace_content. Обычный PUT запрещён, если исходный или целевой kind — poll: нельзя ни менять опубликованный опрос, ни обходить POST-проверки превращением markdown в poll, ни менять poll на другой kind. Голосование не меняет payload, content_uuid и ревизию содержимого.

Вопросы, существующие варианты, правильные ответы, общий multiple_answers и прочие правила фиксируются при публикации. До отправки автор редактирует форму свободно. Согласованные исключения после публикации: изменение closes_at, переключение allow_adding_options и добавление новых вариантов при включённом флаге. Они не разрешают менять текст или UUID старых вариантов, правильные ответы либо добавлять вопросы.

Опрос закрыт при closed_at != null или при непустом closes_at <= server_now. Если срока и ручного закрытия нет, время само по себе опрос не закрывает. Истечение срока определяется по полям при чтении и каждой попытке изменения: отдельная запись закрытия, cron или фоновое задание не требуются. Сервер возвращает вычисляемый poll_state.is_closed и остаётся источником истины; клиент использует оба поля для отображения, таймера и обновления после пробуждения вкладки. Закрытый опрос не переоткрывается изменением или удалением closes_at.

### Правильные варианты как клиентское отображение

Правильные варианты задаются отдельно у каждого вопроса того же kind poll. Новая таблица, баллы, рейтинг и серверное поле оценки не требуются. API и realtime сразу отдают правильные UUID читателю с доступом к опросу. Сервер не скрывает их до голосования или закрытия. Подглядывание через инспектор допустимо в этой версии.

После успешного принятия ответа на конкретный вопрос клиент показывает его правильные варианты по соответствующему элементу my_votes и correct_option_uuids этого вопроса. Само закрытие не раскрывает отметки на неотвеченный вопрос. Анонимность поведения не меняет. При results_visibility=after_vote скрытые агрегаты раскрываются по каждому вопросу отдельно после принятого ответа на него; после закрытия агрегаты видны всем читателям.

Добавленные участниками варианты автоматически не включаются в correct_option_uuids; эти отметки остаются частью исходных данных вопроса. Добавление доступно и в вопросах с правильными ответами, отдельного ограничения этого режима нет.

Переголосование работает по обычному allow_revote, без отдельного запрета после раскрытия. Поведение после отзыва нужно согласовать: предлагается снова скрывать отметки при отсутствии собственного ответа, без истории участия. Пересланный текстовый снимок содержит вопросы, варианты и счётчики без отметок правильности.

## Таблица голосов и индексы

Предлагаемое имя — `messenger_poll_votes`. Одна строка соответствует одному выбранному пользователем варианту. У пользователя, выбравшего два варианта первого вопроса и один второго, три строки: три клика и три запроса, каждый в собственной транзакции. Пакетные изменения в первой версии не поддерживаются.

| Поле            | Тип            | Назначение                                                     |
| --------------- | -------------- | -------------------------------------------------------------- |
| `project_id`    | UUID, NOT NULL | Существующая изоляция Workspace по проекту; берётся из сессии. |
| `message_uuid`  | UUID, NOT NULL | Внутренний канонический UUID опроса.                           |
| `user_uuid`     | UUID, NOT NULL | Текущий пользователь из сессии.                                |
| `question_uuid` | UUID, NOT NULL | Вопрос внутри payload данного сообщения.                       |
| `option_uuid`   | UUID, NOT NULL | Вариант из payload опроса.                                     |

Проект DDL по существующим именам таблиц:

```sql
CREATE TABLE messenger_poll_votes (
    project_id uuid NOT NULL,
    message_uuid uuid NOT NULL,
    user_uuid uuid NOT NULL,
    question_uuid uuid NOT NULL,
    option_uuid uuid NOT NULL,
    PRIMARY KEY (project_id, message_uuid, user_uuid, question_uuid, option_uuid),
    FOREIGN KEY (project_id, message_uuid)
        REFERENCES messenger_messages (project_id, uuid)
        ON DELETE CASCADE,
    FOREIGN KEY (project_id, user_uuid)
        REFERENCES messenger_project_users (project_id, user_uuid)
        ON DELETE CASCADE
);
```

Логическая уникальность расширяется до `(message_uuid, user_uuid, question_uuid, option_uuid)` внутри проекта: повтор варианта запрещён в рамках конкретного вопроса. В физический ключ добавлен `project_id` по существующей схеме бэкенда. `PRIMARY KEY` создаёт один составной уникальный B-tree; отдельный такой же `UNIQUE` или индекс на его префикс не нужен. Отдельного surrogate UUID строки на первом этапе не предлагается.

Все запросы указывают `project_id`. Ключ поддерживает получение всех голосов опроса и собственного набора пользователя. Дополнительный индекс для списка участников конкретного варианта добавляется только после проверки соответствующего SQL и объёма данных.

Отдельных таблиц вопросов и вариантов нет: они хранятся в JSONB. Сервер проверяет принадлежность question_uuid сообщению, option_uuid именно этому вопросу и размер набора по общему payload.multiple_answers, отдельно для каждого вопроса. Обычного внешнего ключа на элементы JSONB нет.

Публичный UUID сообщения может обозначать placement, а не корневую запись. API принимает существующий публичный UUID, разрешает его через доступное пользователю представление в канонический UUID и проверяет исходный чат. Внутренние идентификаторы и детали размещения не становятся новым клиентским контрактом. Голоса привязаны к сообщению, а не к дедуплицируемому `content_uuid`.

Выход пользователя из чата сохраняет голоса; новые изменения после выхода запрещены. Для удаления проектного аккаунта выбран простой вариант: его голоса удаляются каскадно, без отдельной истории или обезличивания. Очистка также увеличивает версии затронутых опросов, чтобы старые снимки не восстанавливали прежние счётчики.

Удаление самого сообщения в текущем backend — soft delete через deleted_at, FK ON DELETE CASCADE здесь не сработает. Предложение из плана бэкенда: database-owned очистка голосов триггером на переход deleted_at в той же транзакции; при физическом purge действует каскад. Контроллер не собирает отдельную SQL-цепочку удаления зависимостей.

Для сравнения REST и realtime согласована дополнительная служебная колонка messenger_messages.poll_state_revision в строке сообщения-опросника, а не в строках голосов и не внутри JSONB payload. Это отдельное изменение схемы сверх таблицы голосов; поля вопросов остаются в JSONB. Счётчик возвращается как poll_state.revision, не требует индекса и не меняет content_revision при голосовании.

## Проект REST API

Все новые имена действий и полей ниже требуют согласования и регистрации в публичной схеме. Используется существующий IAM bearer token, проект и базовый путь `/api/workspace/v1/messenger`.

        "options": [
          {
            "uuid": "11111111-1111-4111-8111-111111111111",
            "text": "Понедельник"
          },
          {
            "uuid": "22222222-2222-4222-8222-222222222222",
            "text": "Вторник"
          }
        ],

В примере closes_at не передан: сервер сохраняет и возвращает closes_at: null, автоматического закрытия нет. Явный null даёт тот же результат.

GET /messages/, GET /messages/{message_uuid}, создание и действия голосования возвращают обычное сообщение с poll_state рядом с payload. Для других kinds предлагается poll_state: null. Добавляемый фрагмент:

```json
{
  "poll_state": {
    "revision": 42,
    "is_closed": false,
    "voter_count": 12,
    "questions": [
      {
        "question_uuid": "55555555-5555-4555-8555-555555555555",
        "voter_count": 12,
        "option_counts": {
          "11111111-1111-4111-8111-111111111111": 7,
          "22222222-2222-4222-8222-222222222222": 8
        }
      },
      {
        "question_uuid": "66666666-6666-4666-8666-666666666666",
        "voter_count": 12,
        "option_counts": {
          "77777777-7777-4777-8777-777777777777": 5,
          "88888888-8888-4888-8888-888888888888": 7
        }
      }
    ],
    "my_votes": [
      {
        "question_uuid": "55555555-5555-4555-8555-555555555555",
        "option_uuids": ["11111111-1111-4111-8111-111111111111"]
      },
      {
        "question_uuid": "66666666-6666-4666-8666-666666666666",
        "option_uuids": ["88888888-8888-4888-8888-888888888888"]
      }
    ]
  }

```

Верхний voter_count — число уникальных пользователей, ответивших хотя бы на один вопрос. В questions возвращаются все вопросы в порядке payload, у каждого свой voter_count и option_counts с явными нулями. Числа могут различаться: вопросы независимы, пропуски разрешены и каждый клик сохраняется отдельно.

my_votes — массив собственных ответов читателя, одинаково доступный в открытом и анонимном режиме. Для вопроса без ответа элемента нет; пустой массив — нет голосов во всём опросе. Чужие списки пользователей не включаются.

Состояния формируются пакетно для страницы сообщений, без отдельного запроса клиента и SQL на каждый опрос или вопрос. Агрегаты и собственный набор соответствуют согласованному снимку данных. Первоначально считаем их по таблице голосов без отдельной таблицы счётчиков; необходимость материализации определяют измерения.

Процент на клиенте: option_count / voter_count соответствующего вопроса \* 100; при нулевом числе ответивших — 0. Для множественного выбора сумма может превышать 100%. Общий voter_count всего опроса не используется как знаменатель вопроса.

### Немедленное сохранение выбора

Каждый клик сразу отправляет намерение выбрать или снять конкретный вариант. Клиент не накапливает набор перед отправкой, не ждёт заполнения остальных вопросов и не использует кнопку подтверждения.

Предлагаемое действие:

```http
POST /api/workspace/v1/messenger/messages/{message_uuid}/actions/vote/invoke
```

Один клик — один запрос с одним изменением:

```json
{
  "question_uuid": "55555555-5555-4555-8555-555555555555",
  "option_uuid": "11111111-1111-4111-8111-111111111111",
  "selected": true
}
```

selected=true означает выбрать вариант, selected=false — снять его. Это желаемое состояние, а не toggle: точный повтор уже применённого намерения не переворачивает выбор и не создаёт дубль.

Каждое изменение адресует пару question_uuid + option_uuid внутри одного сообщения. Вопросы, не упомянутые в запросе, и их голоса остаются без изменений. Не передаются полный набор ответов пользователя и чужой user_uuid.

Для одиночного выбора selected=true при разрешённом переголосовании атомарно заменяет предыдущий вариант того же вопроса. Для множественного выбора добавляется или удаляется только указанный вариант, остальные сохраняются. Сервер сам читает текущее состояние под блокировкой, поэтому два запроса добавления разных вариантов не перезаписывают набор устаревшей клиентской копией.

Согласованное правило: при multiple_answers=true и allow_revote=false добавление ещё не выбранных вариантов разрешено, снятие принятых — запрещено. При одиночном выборе после первого принятого ответа смена и отзыв требуют allow_revote=true. При allow_revote=true разрешены добавление, смена и снятие в рамках общего режима опроса, независимо для каждого вопроса. Первый ответ на другой вопрос не считается переголосованием. Все разрешения действуют только до закрытия опроса.

| Общий режим опроса  | allow_revote=false                                                      | allow_revote=true                          |
| ------------------- | ----------------------------------------------------------------------- | ------------------------------------------ |
| Один вариант        | Первый выбор сохраняется; заменить или снять его нельзя.                | Можно выбрать, заменить или снять вариант. |
| Несколько вариантов | Можно добавлять ещё не выбранные варианты, снимать уже принятые нельзя. | Можно добавлять и снимать варианты.        |

После закрытия любые изменения запрещены. Точный повтор текущего состояния предлагается считать успешным без изменений после повторной проверки доступа; история переголосований не хранится. Ошибка запроса сохраняет прежние голоса, ответ на успех — актуальное сообщение с poll_state. Правильные варианты раскрываются клиентом только после принятия собственного выбора сервером.

При быстрых кликах клиент сохраняет порядок действий по одному вопросу, не склеивая их в пакет и не откладывая ради накопления. Особенно важно не переставлять выбор и снятие одного варианта или два одиночных выбора. Разные вопросы не требуют ожидания полного заполнения опроса. Состояние ожидания и ошибка относятся к отправленному действию; устаревший ответ не отменяет более новое подтверждённое состояние.

### Пакетные операции отложены

Первая версия принимает одно намерение по одному варианту одного вопроса одного сообщения. Массив changes, обновление нескольких вопросов или разных сообщений одним запросом не поддерживаются. Для основного сценария они не нужны; накопление и кнопки подтверждения также не вводятся.

### Независимые вопросы

Обязательных и необязательных вопросов в первой версии нет. Пользователь может ответить на любой вопрос, пропустить остальные, вернуться к ещё не отвеченному вопросу позже, пока опрос открыт. Принятый клик немедленно учитывается в счётчиках соответствующего вопроса, независимо от остальных ответов.

Верхний voter_count считает пользователей с хотя бы одним принятым вариантом во всём опросе, каждый вопрос имеет собственный voter_count. Если разрешён отзыв и снят последний собственный вариант вопроса, пользователь перестаёт учитываться в его voter_count. Снятие последнего варианта во всём опросе убирает его и из общего voter_count. Это не означает удаления голосов других участников.

### Закрытие

```http
POST /api/workspace/v1/messenger/messages/{message_uuid}/actions/close_poll/invoke
```

Тело — `{}`. Автор или пользователь с ролью `owner`, `administrator` или `moderator` в исходном чате закрывает опрос. Доступ к исходному чату обязателен, в том числе для автора. Повторное закрытие идемпотентно; переоткрытия в первой итерации нет. Ответ — актуальное сообщение.

### Изменение настроек опубликованного сообщения

Изменяемые настройки poll сохраняются одной общей ручкой настроек сообщения, а не отдельными действиями для каждого поля:

```http
POST /api/workspace/v1/messenger/messages/{message_uuid}/actions/update_settings/invoke
```

```json
{
  "settings": {
    "closes_at": "2026-12-12T09:00:00Z",
    "allow_adding_options": true
  }
}
```

Пользователь открывает настройки опросника, меняет поля формы и нажимает «Сохранить». Форма отправляет всю текущую редактируемую конфигурацию одним запросом; переключение поля формы само по себе не отправляет запрос. Это относится только к настройкам, голосование по-прежнему сохраняет каждый клик немедленно.

Для poll объект settings содержит ровно два обязательных поля: closes_at (абсолютный момент с часовым поясом либо null) и allow_adding_options (boolean). Null явно снимает срок; false явно запрещает новые варианты. Отсутствующее или неизвестное поле отклоняется с 400: это сохранение всей редактируемой конфигурации, не частичный patch. При первоначальном создании closes_at и allow_adding_options остаются необязательными, с null и false соответственно.

Settings — отдельная форма входного DTO, а не замена payload целиком. В хранении closes_at и allow_adding_options остаются полями payload. Сервер берёт актуальный payload под блокировкой, меняет только эти два поля и сохраняет остальные данные. Новые варианты, добавленные участниками после открытия формы, не теряются. Вопросы, старые варианты, правильные ответы, анонимность, allow_revote и серверный closed_at этим запросом изменить нельзя.

Можно назначить срок впервые, перенести его или убрать после появления голосов, пока опрос открыт. Новый непустой срок должен находиться в будущем; дата без часового пояса отклоняется. Пользователь выбирает дату и время в своём часовом поясе, клиент передаёт абсолютный момент, сервер нормализует его в UTC. TTL в контракт не вводится. Выключение allow_adding_options не удаляет уже добавленные варианты и голоса.

Используются общие права управления: автор, owner, administrator или moderator исходного чата при действующем доступе. Сервер проверяет открытое состояние по прежнему closes_at и closed_at до применения новой конфигурации: закрытый опрос нельзя переоткрыть переносом или удалением срока.

Два поля проверяются и сохраняются атомарно одной транзакцией через content resolver. Ошибка любого поля сохраняет прежнюю конфигурацию целиком. Для одновременного сохранения двумя управляющими пользователями применяется последняя успешно принятая конфигурация, без нового протокола редактирования форм. Она не заменяет вопросы, варианты или голоса. Тот же конфиг на открытом опросе — no-op без новых ревизий и событий.

Ответ — актуальное сообщение с payload и poll_state, включая новые значения и revision. Realtime обновляет карточку, таймер и доступность добавления вариантов без новой непрочитанности. Обычная ручка редактирования содержимого сообщения для этих настроек не используется. Общий маршрут может поддержать другие kinds позднее с явно заданными схемами; в первой версии определены только настройки poll.

### Добавление вариантов участниками

allow_adding_options — общая настройка всех вопросов опросника. При true новый вариант может добавить любой текущий участник с правом голосования в исходном чате. Дополнительных ролей, списка приглашённых, запрета для анонимного режима или вопросов с правильными ответами не вводится. Наличие предыдущего голоса и allow_revote не меняют право добавить вариант; сами голоса изменяются по прежним правилам.

Добавление разрешено в открытом опросе в пределах серверного лимита вариантов конкретного вопроса — 20, включая исходные и добавленные. Новый объект дописывается в конец questions[].options через content resolver. Отдельной таблицы вариантов не требуется. Старые UUID и голоса сохраняются; новый вариант имеет нулевой счётчик, добавление не означает автоматического голосования за него.

Предлагаемое действие:

```http
POST /api/workspace/v1/messenger/messages/{message_uuid}/actions/add_poll_option/invoke
```

```json
{
  "question_uuid": "55555555-5555-4555-8555-555555555555",
  "option": {
    "uuid": "99999999-9999-4999-8999-999999999999",
    "text": "Среда"
  }
}
```

Клиент создаёт UUID варианта вместе с текстом один раз и сохраняет UUID при повторе запроса. После проверки сессии, проекта, доступа и текущего участия в исходном чате сервер под общей блокировкой находит вопрос и проверяет UUID варианта внутри этого вопроса. Если такой UUID уже есть и текст совпадает, возвращает 200 с актуальным сообщением без изменения, новой revision или события — даже если лимит уже достигнут, allow_adding_options выключен либо опрос закрыт. Это повтор, а не новое добавление. Тот же UUID с другим текстом — 409 без перезаписи. Если UUID отсутствует, только тогда проверяются открытое состояние, allow_adding_options и лимит, затем выполняется append. Позиция варианта в списке и совпадение только текста не заменяют проверку UUID.

Текст проходит те же проверки, что исходные варианты. Действие не меняет существующие варианты, вопросы или correct_option_uuids. Публичные поля варианта остаются uuid и text; UUID добавившего участника не включается в payload или общую рассылку, поэтому сценарий поддерживается и в анонимном опросе без нового раскрытия личности.

Флаг allow_adding_options задаётся при создании и меняется после публикации через общее действие update_settings выше. Право добавлять варианты при включённом флаге есть у всех участников с правом голосования, а не только у пользователей с правом управления.

add_poll_option возвращает актуальное сообщение с payload и poll_state и рассылает обновление через realtime без новой непрочитанности. Проверка флага после получения общей блокировки задаёт порядок между выключением флага и конкурирующим добавлением.

### Список проголосовавших

Предлагаемый read-only маршрут для одного варианта конкретного вопроса открытого опроса:

```http
GET /api/workspace/v1/messenger/messages/{message_uuid}/poll_voters/?question_uuid={question_uuid}&option_uuid={option_uuid}&page_limit=50
```

Ответ — коллекция элементов `{ "uuid": "<user_uuid>" }`. Сохраняются параметры и заголовки RESTAlchemy: page_limit, page_marker, X-Pagination-Limit и X-Pagination-Marker. Порядок по UUID пользователя, page_marker — позиционная граница, а не требование текущего существования голоса: следующая страница выбирает user_uuid > marker. Отзыв голоса пользователя-маркера не ломает обход. Каждый запрос отдельно проверяет проект, доступ, вопрос, вариант и анонимность; маркер не расширяет выборку за эти границы. Предлагаемый серверный предел страницы — 100; отсутствие лимита не выгружает всех участников сразу.

Маршрут требует доступа к исходному чату и не выдаёт участников анонимного опроса, даже автору или модератору. Пользовательские карточки загружаются существующим потоком; endpoint не добавляет имена, почту и другую профильную информацию. Пагинация отражает живые данные, а не зафиксированный на время обхода список.

Точное оформление коллекции и вложенного маршрута согласуется с исполнителем API; логическое требование — пагинация списка участников конкретного варианта конкретного вопроса без загрузки всех голосов.

### Ошибки

Предлагается различать следующие причины в существующем формате ошибок Workspace; числовые коды не назначаются этим планом.

| Случай                                                                        | Предлагаемый HTTP статус                                         |
| ----------------------------------------------------------------------------- | ---------------------------------------------------------------- |
| Нет доступного сообщения в текущем проекте                                    | 404, без раскрытия содержимого или участия других пользователей. |
| Неверный kind, UUID варианта, размер набора, повтор UUID или длина текста     | 400.                                                             |
| Создание или активное действие в неподдерживаемом типе чата                   | 400 с отдельной причиной недоступности.                          |
| Недостаточно прав для закрытия, запрос участников анонимного опроса           | 403.                                                             |
| Опрос закрыт, переголосование запрещено, попытка изменить опубликованный poll | 409.                                                             |

Прошлая дата, дата без часового пояса, отсутствие обязательного поля settings и неизвестные поля дают 400. Изменение настроек закрытого опроса даёт 409; отсутствие прав — 403.

Клиент после конфликта получает или обновляет актуальное состояние, сохраняет понятное объяснение и не показывает успешное голосование локально.

## Транзакции и одновременные действия

Уникальный индекс предотвращает дубли одного варианта, но сам не обеспечивает одиночный выбор, запрет переголосования или закрытие. Эти правила проверяются одной серверной транзакцией.

Предлагаемый простой механизм первой итерации — блокировка корневой строки опроса `FOR UPDATE` для голосования, закрытия, изменения срока, переключения allow_adding_options и добавления вариантов. После блокировки повторно читаются актуальные размещение, доступ, payload и собственный набор. Затем проверяется весь запрос и атомарно применяется изменение. Срок проверяется по фактическому серверному времени после ожидания блокировки, а не только по времени начала транзакции. При голосовании изменения вычисляются сервером из текущего набора и выбранных или снимаемых вариантов, а не из полной устаревающей копии ответов клиента.

Одна и та же блокировка должна использоваться всеми путями изменения, включая обычный `PUT`, удаление и перенос, если они влияют на возможность голосования. Проверка доступа использует действующие механизмы членства бэкенда. Сетевые вызовы и внешние операции внутри этой транзакции не выполняются.

Блокировка всего опроса последовательно обрабатывает его записи; это простой начальный вариант, а не утверждение о высокой пропускной способности. До релиза проверить ожидаемую конкуренцию. Если она неприемлема, согласовать блокировки на уровне пользователя с координацией закрытия, сохранив те же инварианты.

## Realtime и актуальность состояния

Предпочтительно расширить существующее событие `message.updated` актуальным `poll_state` и сохранить имеющийся transport событий, epoch/catch-up и проверку доступа. Новые доменные websocket-соединения не нужны.

Голосование не создаёт сообщения, не меняет время отправки или порядок переписки, не добавляет непрочитанность, не поднимает чат и не вызывает уведомления на каждый голос. Закрытие, добавление вариантов и переключение allow_adding_options обновляют существующую карточку. Доставка обновления активного опроса не должна случайно пропускаться из-за возраста исходного сообщения.

При загрузке опроса с `closes_at` клиент ставит таймер к моменту завершения и обновляет состояние с сервера. После изменения срока таймер пересоздаётся, после снятия — отменяется. После пробуждения вкладки и восстановления связи срок проверяется заново, поэтому карточка и показ результатов не зависят от нового голоса. Это предлагаемый механизм актуализации UI первой версии; разрешение на голосование всегда проверяет сервер.

Событие персонализируется для каждого получателя: `my_votes` относится к читателю, а не к проголосовавшему. Агрегаты можно разделять между получателями, собственный набор — нельзя. В частности, нельзя добавить выбор автора события в общий broadcast. Изменение собственного голоса должно обновляться на всех сессиях этого пользователя без отдельного запроса на каждый опрос.

Клиент сравнивает poll_state.revision в REST, ответах мутаций и событиях только для payload опроса и poll_state. Меньшая версия не перезаписывает большую в этой части. Независимые прочитанность, избранное и реакции обрабатываются по существующим правилам своих обновлений; весь снимок сообщения из-за старой ревизии опроса не отбрасывается. При равной версии голоса одинаковы; вычисляемое по сроку закрытие не откатывается из true в false старым снимком. Ревизия, payload, счётчики и my_votes должны соответствовать одному серверному снимку. Подробности служебного счётчика — в плане бэкенда.

Дополнительно сохраняются owner/generation, отмена запросов и текущий catch-up/refresh. Эти защиты контекста не заменяют сравнение свежести состояния. При чтении из кэша результаты могут быть устаревшими, а любое действие повторно проверяет сервер.
