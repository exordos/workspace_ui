# План реализации опросов на бэкенде

Статус: проект реализации для передачи разработчику бэкенда. Код и миграции ещё не написаны. Продуктовые правила и полные примеры payload находятся в [плане опросов](message-polls.md); этот документ задаёт порядок серверных изменений и закрывает технические пробелы ревью.

Проверенная база: локальный backend master, commit `14963ca0c78359104d16fc40b70608f13f2e81b1`. Перед реализацией сверить актуальный HEAD и его AGENTS.md. Документ хранится в репозитории UI как общий артефакт проектирования; команды ниже выполняются только при реализации в репозитории бэкенда.

## Результат первой версии

Сервер принимает новый payload kind poll, хранит текущие голоса отдельно, обрабатывает каждый клик и возвращает пользователю актуальный poll_state вместе с сообщением. Поддерживаются несколько независимых вопросов, анонимность, переголосование, срок, ручное закрытие и добавление вариантов участниками по изменяемому флагу.

Серверные константы ограничивают опрос 20 вопросами и 20 вариантами на вопрос. Лимиты меняются патчем кода. Обязательных вопросов, накопления ответа и кнопок отправки нет. E2EE и активные poll в Zulip запрещены. Пересылка — обычный markdown-снимок без собственного голосования; нового серверного механизма переноса опросов этот план не вводит.

Имена новых действий — проект контракта. При регистрации согласовать их с текущими routes/controllers и OpenAPI, не добавляя отдельный browser-facing backend или websocket.

Один клик — один запрос. Массив changes и пакет нескольких вопросов или сообщений в первую версию не входят. Перед записью проверяется намерение целиком; ошибка сохраняет предыдущие голоса.

### Явная установка и снятие голоса

Оба запроса отправляются на POST /messages/{uuid}/actions/vote/invoke. UUID сообщения задаётся в URL, вопрос и вариант — в теле. Во всех примерах UUID синтетические.

Выбрать вариант:

```json
{
  "question_uuid": "55555555-5555-4555-8555-555555555555",
  "option_uuid": "11111111-1111-4111-8111-111111111111",
  "selected": true
}
```

Снять тот же вариант:

```json
{
  "question_uuid": "55555555-5555-4555-8555-555555555555",
  "option_uuid": "11111111-1111-4111-8111-111111111111",
  "selected": false
}
```

Сервер проверяет доступ, состояние опроса, общий payload.multiple_answers и allow_revote. Успешный ответ содержит целое актуальное сообщение, а не только переданный selected или признак успеха. В poll_state приходят revision, is_closed, счётчики и my_votes текущего читателя. Ниже только фрагмент собственного выбора после успешного selected=true; остальные поля сообщения и poll_state опущены:

```json
{
  "poll_state": {
    "revision": 2,
    "my_votes": [
      {
        "question_uuid": "55555555-5555-4555-8555-555555555555",
        "option_uuids": ["11111111-1111-4111-8111-111111111111"]
      }
    ]
  }
}
```

После разрешённого selected=false этот UUID отсутствует в my_votes соответствующего вопроса; если собственных ответов больше нет, my_votes=[]. Запрещённое снятие возвращает 409 и не меняет голоса. Повтор selected=true для уже выбранного варианта не снимает его; повтор selected=false для уже отсутствующего голоса не создаёт новый. Одинаковое текущее состояние не меняет revision и не создаёт события.

### Общее изменение настроек сообщения

Отдельная ручка настроек не заменяет редактирование самого сообщения. Для первого поддерживаемого kind poll она принимает полную редактируемую конфигурацию формы:

```http
POST /api/workspace/v1/messenger/messages/{message_uuid}/actions/update_settings/invoke
```

```json
{
  "settings": {
    "closes_at": null,
    "allow_adding_options": true
  }
}
```

Оба поля обязательны: null снимает срок, false запрещает добавление. Пропуск поля не означает «оставить старое значение» — запрос неполной конфигурации отклоняется. Любые иные поля, включая вопросы, варианты, анонимность, multiple_answers, allow_revote и closed_at, отклоняются. Тип настроек определяется существующим kind сообщения, клиент не может сменить kind этим запросом. Для других kinds схема пока не определена.

Клиент открывает форму, локально изменяет поля и отправляет конфигурацию кнопкой «Сохранить». Это исключение относится к форме настроек, а не к голосованию: голос по-прежнему отправляется на каждый клик без накопления. Ответ — целое актуальное сообщение, в payload которого отражены настройки, а в poll_state — свежая revision и состояние опроса.

В той же request transaction сервер берёт актуальный payload под блокировкой, проверяет общие права управления и закрытие по прежнему сроку, валидирует оба поля и меняет только их. Варианты, добавленные участниками после открытия формы, сохраняются. Если одно поле неверно, другое тоже не применяется. Для двух одновременных сохранений настроек используется последняя успешно принятая конфигурация; специальный протокол конфликтов формы не добавляется.

При реальном изменении создаётся одна новая content page/revision и увеличивается poll_state_revision, затем публикуется message.updated. Тот же конфиг на открытом опросе — no-op. Закрытый опрос не переоткрывается изменением настроек. Для обоих полей используется одна схема редактируемых настроек.

### Структуры DM и DTO

Названия ниже обозначают новые типы; точные Python-классы следуют текущему стилю RESTAlchemy.

| Тип                          | Поля и ответственность                                                                                                                                        |
| ---------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------- |

| PollQuestion                 | uuid, text, options, необязательный correct_option_uuids. multiple_answers внутри вопроса запрещён.                                                           |

| PollVoteRequest              | question_uuid, option_uuid, selected:boolean. Одно намерение, selected задаёт желаемое состояние, а не toggle.                                                |
| PollEditableSettings         | closes_at: datetime с часовым поясом либо null; allow_adding_options:boolean. Оба обязательны при сохранении формы.                                           |
| MessageSettingsUpdateRequest | Обязательный settings с PollEditableSettings для текущего kind=poll. Прочие поля не принимаются, payload не заменяется целиком.                               |
| PollQuestionState            | question_uuid, voter_count, option_counts со всеми вариантами и явными нулями.                                                                                |
| PollOwnAnswer                | question_uuid, option_uuids текущего читателя. Для вопроса без ответа элемента нет.                                                                           |
| PollState                    | revision, is_closed, voter_count всего опроса, questions, my_votes. Только серверные данные.                                                                  |
| PollVoter                    | uuid пользователя; профиль загружается существующим потоком.                                                                                                  |

Предлагаемые пределы текста: вопрос 1000 символов, вариант 200. Это технические значения для проверки с исполнителем, не основание откладывать проектирование API. Лимиты вопросов и вариантов заданы серверными константами; оба максимума равны 20 и меняются патчем кода. Не понижать допустимость чтения и голосования старого опроса при снижении лимитов создания.

Лимиты проверяются по константам бэкенда. Отдельного API поддержки опросов или получения лимитов в этой итерации нет.

multiple_answers обязателен на уровне payload опроса и задаёт единый режим всех вопросов: false — не более одного выбранного варианта на вопрос, true — несколько в пределах вариантов этого вопроса. Пропуск, null и неверный тип отклоняются; поле внутри questions[] отклоняется как неизвестное. Выбор и снятие независимы между вопросами; общий режим после публикации не меняется. correct_option_uuids остаётся необязательным полем каждого вопроса.

Правильные варианты всегда выдаются читателю вместе с payload. Сервер проверяет формат и принадлежность UUID соответствующему вопросу, но не оценивает правильность голоса и не скрывает ответ. Проценты и results_visibility также остаются клиентскими правилами.

Проверить нормализацию nullable-полей: текущий resource_projection.simple пропускает свойства DM со значением None. Для poll явно сохранять и возвращать closes_at=null и closed_at=null, а для других kinds возвращать poll_state=null по контракту. Это локальная нормализация нового ресурса, не изменение сериализации всех существующих kinds.

### Ошибки и повторение действий

Использовать существующий error envelope и определить машиночитаемые причины: неверный payload/UUID/набор — 400, отсутствие доступного сообщения — 404, нехватка прав управления или запрос участников анонимного опроса — 403, закрытие/запрещённое переголосование/запрещённое изменение — 409. Числовые коды назначает бэкенд по своему реестру.

Повтор desired-state операции, которая уже соответствует сохранённому состоянию, возвращает его без новых голосов и событий. Это не обещает вечную идемпотентность после любых последующих изменений.

Для add_poll_option согласован следующий порядок: после проверки доступа и текущего участия, kind, отсутствия soft delete и существования вопроса найти option_uuid внутри этого вопроса. Совпали UUID и текст — 200 с текущим сообщением, без изменения, новой revision и события. Достигнутый лимит, выключенный allow_adding_options или закрытие не мешают такому no-op. Совпавший UUID с другим текстом — 409. Только для ещё отсутствующего UUID проверять открытое состояние, текущий флаг и лимит. Клиент генерирует UUID вместе с текстом один раз, повтор не создаёт новый UUID. Потеря доступа не обходится повтором.

## Хранение и миграция

### Таблица голосов

Одна строка — один выбранный вариант одного вопроса одного пользователя. Вопросы и варианты остаются в JSONB; отдельные таблицы для них не создаются.

```sql
CREATE TABLE messenger_poll_votes (
    project_id uuid NOT NULL,
    message_uuid uuid NOT NULL,
    user_uuid uuid NOT NULL,
    question_uuid uuid NOT NULL,
    option_uuid uuid NOT NULL,
    PRIMARY KEY (project_id, message_uuid, user_uuid, question_uuid, option_uuid),
    FOREIGN KEY (project_id, message_uuid)
        REFERENCES messenger_messages (project_id, uuid)
        ON DELETE CASCADE,
    FOREIGN KEY (project_id, user_uuid)
        REFERENCES messenger_project_users (project_id, user_uuid)
        ON DELETE CASCADE
);
```

FK пользователя каскаден: новая таблица не блокирует удаление проектного аккаунта. Миграция и тесты должны обеспечить увеличение revision и обновление результатов затронутых опросов при этой очистке. Выход из чата не удаляет проектную учётную запись и не очищает голоса.

PRIMARY KEY сразу создаёт один составной уникальный B-tree. Дополнительные дублирующие UNIQUE или индексы по его префиксам не нужны. Все запросы включают project_id. Дополнительные индексы добавляются только после измерения списка участников и очистки по FK пользователя на ожидаемом объёме. В частности, текущий ключ не даёт префикса project_id+user_uuid без message_uuid; если каскадное удаление пользователя требует его, отдельно обосновать индекс (project_id, user_uuid).

### Версия состояния опроса

Согласованное решение для порядка REST/realtime: добавить одну служебную колонку в строку сообщения-опросника. Это счётчик текущего состояния, а не история и не ревизия каждой строки голоса.

```sql
ALTER TABLE messenger_messages
    ADD COLUMN poll_state_revision bigint NOT NULL DEFAULT 0
    CHECK (poll_state_revision >= 0);
```

Это изменение схемы сверх новой таблицы голосов, которое нужно учесть в оценке. Колонка нужна для порядка состояния, а не для хранения вопросов. Для других kinds остаётся 0; poll создаётся с 1. Реальное изменение голосов, включая каскадное удаление при удалении аккаунта, закрытие вручную, смена срока или флага и добавление варианта увеличивают её. Значение монотонно, но не обязано расти ровно на единицу за запрос: переход между вариантами может затронуть несколько строк. No-op не увеличивает. Отдельного индекса колонки нет.

Для голосов предпочтительны database-owned INSERT/DELETE триггеры, которые увеличивают счётчик затронутого root message и учитывают FK-каскады. Действия метаданных увеличивают счётчик в своей транзакции. Не увеличивать его повторно в service после уже сработавшего триггера. Очистка аккаунта также должна enqueue обновление затронутых опросов существующим механизмом, без событий на каждую строку.

При голосовании меняется этот счётчик и таблица голосов, но не content_uuid, content_revision, время отправки или порядок чата. Обновление служебного счётчика не должно запускать упоминания, summary, доставку провайдеру или уведомления. Проверить текущие триггеры и проекции, не полагаясь на общее обновление root message как на готовую семантику голосования.

API возвращает revision внутри poll_state, одинаково в REST, ответе мутации и событии. Ревизия, агрегаты, my_votes и payload соответствуют одному согласованному снимку, а не нескольким SELECT с возможными изменениями между ними. Для обычного чтения предпочтительно одно SQL-выражение после выбора ключей страницы.

Клиент не применяет меньшую revision к payload опроса и poll_state, но не отбрасывает вместе с ними независимые read/star/reactions: для этих полей сохраняются существующие правила обновления. При равной revision голоса и настройки одинаковы; вычисляемый по времени is_closed не должен откатываться с true на false из-за старого снимка. Истечение closes_at не меняет ревизию и не требует записи или cron: клиент также проверяет срок и обновляется по таймеру. Новая revision после своевременного переноса срока отражает новое сохранённое ограничение.

Для первой реализации выбран один счётчик poll_state_revision в корневой таблице, без отдельной таблицы метаданных и сложных клиентских watermark-протоколов. Content_revision и только глобальный epoch не заменяют его автоматически. Owner/generation клиента защищают контекст, а не сравнение свежего HTTP-ответа с задержанным старым событием.

### Удаление сообщения

Текущий delete_message устанавливает deleted_at, поэтому одного ON DELETE CASCADE недостаточно. Рабочее предложение с учётом backend AGENTS.md: миграционный DB-триггер при переходе root message в deleted_at != null удаляет его poll_votes в той же транзакции. При физическом purge действует FK-каскад.

Контроллер не собирает raw SQL-цепочку удаления зависимых записей. Изменение API удаления, root tombstone и очистка зависимостей используют общую блокировку сообщения. Клиент получает message.deleted; отдельные события удаления каждой строки голоса не нужны. Проверить удаление через все существующие пути, включая lifecycle темы и чата.

## Реализация запросов и действий

### Создание и изменение содержимого

1. Добавить PollOption, PollQuestion и PollPayload в существующий selector message_payloads. Структурную валидацию держать в DM, как требует backend AGENTS.md. PollCreatePayload/PollReadPayload — логические формы записи и чтения: не регистрировать два разных kind-класса с одним KIND=poll в одном selector; серверные поля защищает write boundary.
2. При POST разрешать только поддерживаемый native чат без E2EE, с обычными правами создания сообщения. Нормализовать пропущенный closes_at в null и allow_adding_options в false, серверный closed_at — в null.
3. Сохранять через messenger_resolve_message_content и существующую каноническую запись/placement. Не менять JSONB content page на месте.
4. Обычным PUT запрещать переходы в poll и из poll, а также редактирование уже опубликованного poll. Проверять исходный и целевой kind: иначе markdown→poll обходит POST-ограничения.
5. Срок и allow_adding_options изменять только общим update_settings, append новых вариантов — add_poll_option. Они создают новую content page/ревизию существующим механизмом и увеличивают poll_state_revision.
6. Server-side poll drafts не включать автоматически: текущий helper отдельно допускает только MarkdownPayload. До отдельного требования форма poll не использует серверный draft API.

### Общая транзакция мутации

1. В существующей request transaction разрешить доступный публичный UUID и взять FOR UPDATE канонической root message. Не открывать отдельную session_manager внутри helper/controller.
2. После ожидания блокировки заново проверить размещение, текущие доступ и участие, kind, отсутствие soft delete, структуру входа и существование целевого вопроса. Для управляющих действий проверить общие роли. Потеря доступа запрещает и повтор без изменения.
3. До запрета реального изменения распознать разрешённый no-op: vote уже соответствует selected, close_poll уже закрыт, add_poll_option имеет тот же UUID и текст. Они возвращают актуальное сообщение без изменения, даже если состояние уже закрыто. Для add_poll_option другой текст при том же UUID — конфликт. Settings имеет no-op на открытом опросе, как описано в контракте формы.
4. Для реального изменения проверить ручное закрытие и closes_at по фактическому серверному времени после ожидания блокировки, не только времени начала транзакции.
5. Для голоса загрузить текущие строки пользователя по вопросу и применить selected к серверному состоянию, не трогая другие вопросы. Общий payload.multiple_answers=false с allow_revote=false запрещает замену и снятие; payload.multiple_answers=true с allow_revote=false разрешает только добавление. allow_revote=true разрешает изменения до закрытия в рамках общего режима. Первый ответ на другой вопрос не считается переголосованием.
6. Для нового варианта только после проверки отсутствия UUID проверить allow_adding_options, право участия, текст и лимит. Append не голосует за вариант и не меняет старые позиции или correct_option_uuids.
7. Для update_settings применить всю допустимую конфигурацию атомарно к актуальному payload. Прежний истёкший срок и ручное закрытие не позволяют переоткрыть опрос, выключение флага не удаляет варианты.
8. Если состояние реально изменилось, сохранить запись, обеспечить увеличение poll_state_revision без дублирования database-owned обновления и enqueue согласованные события в той же транзакции. Вернуть актуальное сообщение. Сетевые действия под блокировкой не выполняются.

Одна блокировка на опрос — рабочий вариант первой версии. Она упрощает корректность, но сериализует его записи. Проверить конкуренцию и время SQL до релиза; более узкие блокировки требуют отдельного доказательства тех же инвариантов.

Открытое замечание повторного ревью: каскад удаления аккаунта и DELETE-триггер голосов могут брать vote-row → root, тогда как обычная мутация берёт root → vote-row. До реализации определить единый порядок блокировок lifecycle либо безопасный повтор всей отменённой транзакции; проверить гонки удаления аккаунта с голосованием и удалением опроса. Одного уникального индекса для этого недостаточно.

### Чтение и список участников

После отбора ключей страницы пакетно получить для poll актуальные payload/revision, COUNT по вариантам, COUNT DISTINCT пользователей по вопросам и опросу, а также my_votes текущего читателя. Не выполнять SQL на каждый вопрос или каждого получателя. Отсутствующие варианты дополнить нулями по payload.

Список участников выдаётся только для доступного неанонимного опроса, с обязательными question_uuid и option_uuid. Предлагаемый лимит страницы 50, максимум 100. Возвращаются только UUID пользователей.

Исправление замечания ревью: page_marker трактовать как позиционную UUID-границу user_uuid > marker, не требуя, чтобы проголосовавший до сих пор оставался в этой выборке. На каждой странице независимо проверять проект, доступ к сообщению, вопрос, вариант и анонимность. Фильтр ограничен текущим опросом и вопросом; UUID-маркер не предоставляет доступ к другому ресурсу. Результаты живые, отзыв голоса не обрывает обход ошибкой исчезнувшего маркера.

### Realtime

Расширить существующий message.updated; не создавать отдельный websocket. Все серверные состояния несут revision. Если worker формирует более свежий снимок, его revision должна соответствовать именно этому снимку, а не исходной задаче.

Персонализировать my_votes для каждого читателя. Общий broadcast не содержит выбора проголосовавшего или его UUID как автора голоса. Даже автор/модератор анонимного опроса не получает список чужих голосов. Проверять доступ действующим механизмом и учитывать отзыв членства до доставки.

Голос не создаёт unread, уведомления, новую активность или новый элемент истории. Обновлять и старые активные опросы: существующий возрастной фильтр message events не должен подавить их изменения. Закрытие по сроку определяется без события; UI уже имеет closes_at и обновляет состояние по таймеру, пробуждению и reconnect.

### Файлы и владельцы изменений

Пути ниже относительны репозиторию workspace_backend; это проверенные точки входа, а не требование складывать всё в существующие большие файлы.

- workspace/messenger_api/dm/message_payloads.py — kind и вложенные модели.
- workspace/messenger_api/dm/models.py, dm/v2_models.py и dm/base.py — поля ресурса, read views и ограничения обычного PUT.
- workspace/messenger_api/api/routes.py и controllers.py — actions, коллекция участников и DM-backed boundary.
- workspace/messenger_api/api/store.py, sql_canonical_store.py, v2_store.py — интерфейс и существующие реализации store; выбрать актуальный owning path, не дублировать бизнес-правила между ними.
- workspace/messenger_api/api/resource_projection.py — public поля, poll_state и запрет утечек внутренних данных.
- Серверные константы лимитов вопросов и вариантов хранятся в коде опросов и меняются патчем.
- workspace/messenger_api/publication.py, workspace/messenger_api/events.py и workspace/services/messenger_workers/v2_projection.py — существующие outbox, персонализация и snapshots.
- migrations/ и migrations/immutable_message_contents.py — owning механизмы хранения; новую миграцию генерирует CLI, общие опубликованные миграции не переписываются.

Следовать backend AGENTS.md: импорты модулей, валидация в DM, текущая request session, database-owned cleanup. Никаких изменений сервера этот документ сам не выполняет.

## Проверки и критерии завершения

| Проверка             | Что должно быть доказано                                                                                                                                                                                                                                                                     |
| -------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Payload и лимиты     | Обязательный boolean multiple_answers в payload: пропуск, null, неверный тип и поле внутри вопроса отклоняются; correct_option_uuids остаётся на уровне вопроса. 1/20 вопросов, 2/20 вариантов, отказ за пределами и по неверным UUID; изменение констант патчем не ломает старые сообщения. |
| Клики                | Каждый selected-запрос сохраняется независимо; нет потери соседних вариантов, очистки других вопросов или двойного учёта повтора.                                                                                                                                                            |
| Правила изменения    | Общий payload.multiple_answers × allow_revote, одинаковый режим всех вопросов и независимость их ответов; первый ответ другого вопроса; запрет после ручного закрытия или срока.                                                                                                             |
| Форма настроек       | Оба поля сохраняются атомарно; пропуск, неизвестное поле и невалидная дата отклоняются. Ошибка даты не переключает флаг. Новые варианты, добавленные после открытия формы, сохраняются. Повтор конфигурации — no-op, две одновременные конфигурации имеют определённый порядок.              |
| Добавление вариантов | Включение флага, допустимые участники, анонимность, лимит и неизменность старых голосов. UUID+текст повторяются успешно после заполнения лимита, выключения флага и закрытия; UUID с другим текстом даёт 409, потеря доступа не обходится.                                                   |
| Конкуренция          | Голос/голос, голос/закрытие, голос/срок, append/append и append/выключение флага; срок проверяется после ожидания блокировки.                                                                                                                                                                |
| Граница доступа      | Другой проект, неучастник, вышедший участник, роли управления; невозможность обойти ограничения переходом kind через PUT.                                                                                                                                                                    |
| Жизненный цикл       | Soft delete удаляет голоса в той же транзакции; purge каскаден; удаление проектного аккаунта каскадно удаляет его голоса с обновлением версий затронутых опросов.                                                                                                                            |
| Анонимность          | Чужие личности отсутствуют в REST/realtime, список участников недоступен; my_votes персональны на всех сессиях пользователя.                                                                                                                                                                 |
| Свежесть             | Ответ мутации V2 и задержанное событие V1 сравнимы; данные одного ответа имеют одну revision; истечение срока не требует отдельной записи.                                                                                                                                                   |
| Пагинация            | Удаление/отзыв голоса последнего UUID страницы не ломает продолжение; нет выдачи участников другого вопроса/проекта.                                                                                                                                                                         |
| Побочные эффекты     | Голоса не меняют content pages, время отправки, unread, уведомления, summary и provider delivery.                                                                                                                                                                                            |
| SQL и масштаб        | Нет N+1 на вопросы; измерены COUNT DISTINCT, персонализация и длительность общей блокировки на ожидаемом объёме.                                                                                                                                                                             |

Команды будущей проверки из backend README/tox.ini:

```bash
# In workspace_backend; use a disposable PostgreSQL database.
tox -e 3.12-nocoverage -- -k poll
WORKSPACE_REQUIRE_INTEGRATION_TESTS=1 tox -e 3.12-integration-nocoverage -- -k poll
tox -e ruff-check,mypy
tox -e docs-build
```

Имена тестовых модулей выбрать при реализации; фильтр poll должен действительно собирать новые случаи, а не завершаться без тестов. База интеграционных тестов задаётся WORKSPACE_TEST_DB_URL по backend README. Миграции создавать `.tox/develop/bin/ra-new-migration --path migrations --depend HEAD`; точный вызов проверить по CLI help. Здесь эти команды не запускались: пока изменена только документация UI.
