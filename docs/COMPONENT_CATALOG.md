# Component catalog and responsibility map

This map identifies entry points rather than enumerating every component or duplicating props. Follow [FSD architecture](fsd-architecture.md) and [PROJECT_FACTS.md](PROJECT_FACTS.md); the entries below point to current module entries and concrete files. Read the [module policy](fsd-architecture.md#files-and-imports) when selecting imports.

## Choose existing UI first

1. Find the responsibility below and inspect the component's stories, source, tests and current callers. Stories show representative use; source and tests own exact props and behavior.
2. Reuse the existing component when its contract fits. Extend it when callers share the same responsibility; avoid adding another button, dialog or picker implementation for a single screen.
3. Add a new component only when the existing contract cannot own the behavior cleanly, and explain that boundary. Similar appearance alone does not establish a shared responsibility. Domain presentation and workflows keep their FSD owner even when they have stories.

## Run and maintain Storybook

From the repository root, run `npm run storybook` to open the local catalog on port 6006. Use `npm run build-storybook` to create the static catalog in `packages/web/storybook-static`.

The [preview](../packages/web/.storybook/preview.tsx) uses application CSS and the real [theme engine](../packages/web/src/shared/lib/themes/engine.ts). The toolbar selects a palette from the [theme registry](../packages/web/src/shared/lib/themes/registry.ts), light/dark mode and English/Russian locale. Inspect affected states in the relevant themes and locales, including portal content such as dialogs and menus.

Stories use local, synthetic fixtures and callbacks. They do not start the app, authenticate, or prove backend integration. Keep visible labels on the existing i18n path. For a new shared component or a change to its public behavior/appearance, add or update the adjacent story and revise this selection guide when its responsibility changes. Domain components can have stories in their own FSD layer; this catalog is an initial shared set, not an exhaustive UI inventory.

A static build checks bundling. Visual comparison, accessibility checks and interaction execution are separate checks; do not infer they ran from a successful build. See [verification commands](PROJECT_FACTS.md#verification) and the [integration guide](INTEGRATION_GUIDE.md).

## Reuse and boundaries

The [external account dialog](../packages/web/src/features/connect-external-account/connect-external-account-dialog.ui.tsx) collects only the provider and credentials. New connections always synchronize all chats and full history, with no manual chat selection step or chat configuration action in the right panel. The account row menu also opens this dialog for editing the server URL, email and optional API key. Editing reads the latest settings before PUT so an empty key field preserves the existing credential; raw credentials stay outside the domain store and durable cache.

Look in [shared/ui](../packages/web/src/shared/ui) for existing primitives before creating one. Shared components receive data and callbacks; they must not import entity stores. Domain-specific presentation belongs in an entity, an interaction in a feature, and composed screens in widgets/pages.

[AppTooltip](../packages/web/src/shared/ui/app-tooltip.ui.tsx) wraps a focusable trigger and accepts React content for reusable hover/focus explanations. It uses a rounded theme surface in a portal, stays inside the viewport, and dismisses with Escape. Chat-specific copy belongs in the header, not in the shared tooltip.

[SearchableCheckboxList](../packages/web/src/shared/ui/searchable-checkbox-list.ui.tsx) filters visible options while the caller owns the complete selection. Search must never determine the submitted selection. [UserPickerList](../packages/web/src/shared/ui/user-picker-list.ui.tsx) adds user rows and searches display names, usernames and email addresses; channel creation and member addition share this component.

Preserve the visible messenger shell unless redesign is part of the task. New visible text goes through [i18n](../packages/web/src/i18n), with both English and Russian keys. Use the existing keyboard, focus and accessible-name patterns of the chosen primitive.

Message HTML uses the established [render path](../packages/web/src/shared/lib/workspace-message-render/workspace-message-render.lib.ts) and sanitization. Component reuse must not bypass that boundary. UUIDs remain UUIDs throughout callbacks; do not adapt Workspace identity to obsolete numeric Zulip identifiers.

For exact props and examples, inspect the linked component and its adjacent tests. Add only the files needed by the change; no mandatory component/store/API bundles. Behavioral and visual validation requirements are described in [the integration guide](INTEGRATION_GUIDE.md).
