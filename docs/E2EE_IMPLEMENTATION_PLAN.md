# E2EE: этапы реализации

Дата: 2026-10-01. Основание: [подготовительная записка](E2EE_IMPLEMENTATION_PLANNING.md) и [контрактный черновик](E2EE_CHAT_DRAFT.md).

## Границы и принятый подход

Реализация начинается с представления и независимой модели. Backend на проверенном revision `7604087` принимает только `markdown`; расширение рабочих DTO, истории и realtime требует отдельно подтверждённого серверного контракта. Выбор криптографической библиотеки и постоянного хранилища остаётся отложенным.

Для локальной интеграционной проверки выбран [backend PR #180](https://github.com/exordos/workspace_backend/pull/180), head `77f2ced5030271c075d6b09b35e7a267e954601b`. Это отдельный тестовый checkout, а не изменение рабочего backend. PR содержит пять новых `kind` с `device_name`, неизменяемый признак стрима `encryption` и `current_encryption_key: { key_uuid, public_key }`. Первоначальный ключ обязателен при создании зашифрованного стрима; `key_announced` обновляет его атомарно и доступен только владельцу стрима. Это подтверждённый контракт выбранного стенда; окончательное принятие PR ещё не означает готовую frontend-интеграцию.

UI максимально переиспользует существующие `Button`, `SelectableRow`, `Icon`, `Avatar`, `ScrollArea`, `Spinner` и семантические токены темы. Pixel Perfect не требуется. Новый компонент нужен только для отсутствующего представления; общие примитивы не дублируются. Для карточек служебных сообщений подходящей общей оболочки пока нет: `AttachmentCard` имеет файловую семантику и сюда не подходит.

Макеты прочитаны через Figma Bridge MCP: общий блок `10879:26030`, основная панель `11026:27080`, служебные сообщения `11026:27023`. Основной объём — панель информации справа: ключ, запросы доступа и участники. Заголовок панели, аватар защищённого чата, имя устройства и действия передачи/отказа передаются через presentation props. Из Figma экспортированы только отсутствующие иконки; аватары участников остаются динамическими.

## 1. Представление и локальный preview

Владелец панели — UI-субагент; закрытых и служебных сообщений — отдельный UI-субагент. Оркестратор владеет страницей, маршрутом и переводами.

- [EncryptedChatInfo](../packages/web/src/widgets/encrypted-chat-info/encrypted-chat-info.ui.tsx): информация о чате, текущий ключ, запросы, участники. Все права и операции приходят через props; без API, криптографии и обращения к хранилищам.
- [Закрытое сообщение](../packages/web/src/widgets/encrypted-chat-messages/encrypted-message-placeholder.ui.tsx): `locked`, `loading`, `error`. Блюр строится из пустых декоративных полос; plaintext не принимается.
- [Служебное сообщение](../packages/web/src/widgets/encrypted-chat-messages/encrypted-chat-service-message.ui.tsx): четыре отдельных `kind`, готовые строки и разрешённые действия.
- [Preview](../packages/web/src/pages/encrypted-chat/encrypted-chat-preview.ui.tsx): локальные примеры без записи в message store/cache. Маршрут `/login/e2ee-preview` доступен только при `import.meta.env.DEV`, вне рабочего Layout, с авторизацией и без неё. Проверка панели возможна до подключения backend.

Критерии: повторное использование UI-примитивов; переключение представлений с правами/без прав, с ключом/без ключа; loading блокирует действия; закрытие возвращает фокус; операции явно показывают отсутствие интеграции, не имитируют выдачу ключа. Имена ключа и дата в макете пока являются входными display metadata: источник этих данных отсутствует в `key_announced` и требует согласования.

## 2. Независимая модель доступа и корреляции

Владелец — контрактный субагент. [Типы](../packages/web/src/entities/messenger/chat-e2ee.types.ts) отделены от текущего live API. [Корреляция](../packages/web/src/entities/messenger/chat-e2ee.lib.ts) проверяет стрим, внешний UUID запроса, поколение, адресата и разрешение автора ответа. Отсутствующий запрос означает неполную историю. Полученный контейнер выдачи не открывает доступ автоматически. Наличие ключа считается для точного адреса owner/device/stream/generation.

Критерии: пять payload без универсальной системной оболочки; отдельные `missing`, `public-only`, `ready` для поколения; grant/reject другому запросу/устройству не меняет доступ; повторная обработка детерминирована. Focused tests проверяют эти инварианты.

## 3. Контроллер сценариев и рабочая композиция

Следующий этап после представления. Оркестратор согласует props и отдаёт одному агенту сценарную логику, другому — подключение панели; общие composition-файлы имеют одного владельца.

Перед подключением разрешить продуктовые вопросы: отдельный раздел или режим текущего мессенджера; соответствие права выдачи ролям; политика отправки с одним публичным ключом; выбор поколения; источник первоначального объявления; обработка нескольких ответов. Визуальные варианты автоматической выдачи в макете не являются принятой политикой.

Контроллер использует `ChatCryptoProvider` и `ChatKeyStorage`, проверяет права до операции, сохраняет ключ только после успешной расшифровки. Async результаты принадлежат runtime owner и generation; смена owner отменяет возможность записать старый результат. Расшифрованное содержимое не сохраняется автоматически в общий durable message cache.

Критерии: явные unavailable/loading/error состояния; корректность смены runtime, повторных событий и ответов не по порядку; отсутствие бизнес-логики в представлении. Тестовая реализация провайдера допускается только в изолированной тестовой среде.

## 4. API, история и realtime

Зависимость: backend поддерживает пять новых `kind` и признак защищённого стрима. По отдельному разрешению пользователя локальный стенд поднят на PR #180; рабочий backend-репозиторий не изменяется. Для разработки контракт проверяется на этом стенде, а перед выпуском — на принятой серверной версии.

Один владелец обновляет DTO/guards и адаптеры; затем существующий путь parse → domain → message store → render расширяется одинаково для REST/истории/realtime. Байты провайдера преобразуются в обычный padded Base64 в `content`/`public_key`; новых полей версии/схемы или wire `bytes` нет. Служебные сообщения не становятся Markdown.

Критерии: контрактные fixtures, корректность неполной истории/корреляции и async ownership, отсутствие регрессий обычных чатов. Рендер расшифрованного содержимого идёт через существующий безопасный render path. Подтверждённая поддержка API предшествует включению отправки.

## 5. Настоящая криптография и постоянное хранение

Зависимость: отдельное решение по схеме, библиотеке и платформенным секретам. Не реализовывать шифрование по текущему черновику.

Провайдер и хранилище заменяют абстракции без переноса криптографии в UI. Генерация device ID/name, восстановление и совместимость между клиентами решаются в этом этапе. Смена поколения не обещает отзыв старых ключей.

Критерии: проверенные test vectors выбранной схемы; совместимость клиентов; проверка адресации выдачи; сохранение приватного ключа при обновлении публичной части; отделение ключей от очистки message cache.

## Проверка и текущий результат

### Локальный backend-стенд PR #180

Checkout и инфраструктурные скрипты находятся в `/private/tmp/workspace-e2ee-pr180/stand`. Gateway: `http://127.0.0.1:23190`; отдельная PostgreSQL — `127.0.0.1:5436`. Основной backend checkout и ранее существовавший DB volume сохраняются. REST, модели, миграции и WebSocket-сервис взяты из PR; IAM для тестового проекта заменён локальным stub. Постоянное хранилище ключей и настоящая криптография на стенде не реализованы.

Фронт из текущего UI checkout запущен на `http://127.0.0.1:5176`; команда повторного запуска — `sh /private/tmp/workspace-e2ee-pr180/stand/start-frontend.sh`. Локальные учётные данные находятся в `stand/credentials.json` с правами `0600` и не копируются в документацию. `isValidRealmUrl` допускает HTTP loopback только в DEV; без явного backend адреса HTTP origin Vite не используется для автоматического подключения. Preview компонентов на порту `5175` остаётся отдельной страницей.

Проверено: вход через форму с выбором проекта; появление серверного стрима в списке; создание encrypted stream (`201`); сохранение пяти новых payload (`201`) и история (`200`); реальный WebSocket catch-up, `ready` и получение нового `e2ee` события после REST POST. Повторяемые API проверки и результаты сохраняются рядом со скриптами стенда. Это проверка контрактов и подключения: рабочие frontend DTO/render/controller для новых kinds ещё не подключены.

Команды запуска, остановки, повторяемых проверок и границы IAM stub описаны в `/private/tmp/workspace-e2ee-pr180/stand/RUNBOOK.md`. Python-окружение использует отдельную версию RestAlchemy и остальные зависимости из существующего read-only окружения backend; это локальная конфигурация этой машины, не заявление о совпадении с CI.

Подтверждены ограничения PR: `GET streams/?encryption=true` возвращает `500`; создание encrypted direct для существующей plaintext-пары возвращает прежний незашифрованный стрим. Review также отмечает несоответствие OpenAPI drafts фактическим Markdown-only drafts; принятие этих API решений остаётся отдельной задачей. При повторной браузерной проверке одна вкладка перестала отвечать; новая вкладка успешно загрузила рабочий inbox. Полный браузерный сценарий E2EE не считается проверенным.

### UI и независимая модель

Первый этап представления и чистая корреляция реализованы. Preview не означает работающий E2EE-мессенджер. Настоящие provider/storage, отправка, рабочий shell и API-интеграция остаются следующими этапами.

Проверки: focused tests модели/preview и существующих маршрутов, Web/Electron typecheck, scoped ESLint/Prettier, локальные ссылки и `git diff --check`. UI проверяется отдельно в браузере: состояния, кнопки, локализация, фокус и отображение панели. Pixel Perfect и native Electron QA не являются выполненными проверками.
