# E2EE: этапы реализации

Дата: 2026-10-02. Основание: [подготовительная записка](E2EE_IMPLEMENTATION_PLANNING.md) и [контрактный черновик](E2EE_CHAT_DRAFT.md).

Актуализация 2026-10-02: решение «пара ключей чата и постоянная пара устройства, библиотека отложена» заменено на `GroupKey` + ChaCha20-Poly1305 и HPKE с отдельной устойчивой парой каждого запроса. [План реальной криптографии](E2EE_REAL_CRYPTO_PLAN.md) содержит текущие этапы и контрактную развилку обязательного `public_key`. Provider/storage foundation не означает подключение настоящего шифрования к обычному UI; до согласования mapping рабочая интеграция не заявляется.

## Границы и принятый подход

Реализация начинается с представления и независимой модели. Backend на проверенном revision `7604087` принимает только `markdown`; расширение рабочих DTO, истории и realtime требует отдельно подтверждённого серверного контракта. Этот первоначальный этап выбора библиотеки и хранения заменён [новым планом](E2EE_REAL_CRYPTO_PLAN.md).

Для локальной интеграционной проверки выбран [backend PR #180](https://github.com/exordos/workspace_backend/pull/180), head `77f2ced5030271c075d6b09b35e7a267e954601b`. Это отдельный тестовый checkout, а не изменение рабочего backend. PR содержит пять новых `kind` с `device_name`, неизменяемый признак стрима `encryption` и `current_encryption_key: { key_uuid, public_key }`. Первоначальный ключ обязателен при создании зашифрованного стрима; `key_announced` обновляет его атомарно и доступен только владельцу стрима. Это подтверждённый контракт выбранного стенда; окончательное принятие PR ещё не означает готовую frontend-интеграцию.

UI максимально переиспользует существующие `Button`, `SelectableRow`, `Icon`, `Avatar`, `ScrollArea`, `Spinner` и семантические токены темы. Pixel Perfect не требуется. Новый компонент нужен только для отсутствующего представления; общие примитивы не дублируются. Для карточек служебных сообщений подходящей общей оболочки пока нет: `AttachmentCard` имеет файловую семантику и сюда не подходит.

Макеты прочитаны через Figma Bridge MCP: общий блок `10879:26030`, основная панель `11026:27080`, служебные сообщения `11026:27023`. Основной объём — панель информации справа: ключ, запросы доступа и участники. Заголовок панели, аватар защищённого чата, имя устройства и действия передачи/отказа передаются через presentation props. Из Figma экспортированы только отсутствующие иконки; аватары участников остаются динамическими.

## 1. Представление и локальный preview

Владелец панели — UI-субагент; закрытых и служебных сообщений — отдельный UI-субагент. Оркестратор владеет страницей, маршрутом и переводами.

- [EncryptedChatInfo](../packages/web/src/features/encrypted-chat-info/encrypted-chat-info.ui.tsx): информация о чате, текущий ключ, запросы, участники. Все права и операции приходят через props; без API, криптографии и обращения к хранилищам.
- [Закрытое сообщение](../packages/web/src/features/encrypted-chat-message/encrypted-message-placeholder.ui.tsx): `locked`, `loading`, `error`. Блюр строится из пустых декоративных полос; plaintext не принимается.
- [Служебное сообщение](../packages/web/src/features/encrypted-chat-message/encrypted-chat-service-message.ui.tsx): четыре отдельных `kind`, готовые строки и разрешённые действия.
- [Preview](../packages/web/src/pages/encrypted-chat/encrypted-chat-preview.ui.tsx): локальные примеры без записи в message store/cache. Маршрут `/login/e2ee-preview` доступен только при `import.meta.env.DEV`, вне рабочего Layout, с авторизацией и без неё. Проверка панели возможна до подключения backend.

Критерии: повторное использование UI-примитивов; переключение представлений с правами/без прав, с ключом/без ключа; loading блокирует действия; закрытие возвращает фокус; операции явно показывают отсутствие интеграции, не имитируют выдачу ключа. Имена ключа и дата в макете пока являются входными display metadata: источник этих данных отсутствует в `key_announced` и требует согласования.

## 2. Независимая модель доступа и корреляции

Владелец — контрактный субагент. [Типы](../packages/web/src/entities/messenger/chat-e2ee.types.ts) отделены от текущего live API. [Корреляция](../packages/web/src/entities/messenger/chat-e2ee.lib.ts) проверяет стрим, внешний UUID запроса, поколение, адресата и разрешение автора ответа. Отсутствующий запрос означает неполную историю. Полученный контейнер выдачи не открывает доступ автоматически. Наличие ключа считается для точного адреса owner/device/stream/generation.

Критерии: пять payload без универсальной системной оболочки; отдельные `missing`, `public-only`, `ready` для поколения; grant/reject другому запросу/устройству не меняет доступ; повторная обработка детерминирована. Focused tests проверяют эти инварианты.

## 3. Контроллер сценариев и рабочая композиция

Следующий этап после представления. Оркестратор согласует props и отдаёт одному агенту сценарную логику, другому — подключение панели; общие composition-файлы имеют одного владельца.

Перед подключением разрешить продуктовые вопросы: отдельный раздел или режим текущего мессенджера; соответствие права выдачи ролям; политика отправки с одним публичным ключом; выбор поколения; источник первоначального объявления; обработка нескольких ответов. Визуальные варианты автоматической выдачи в макете не являются принятой политикой.

Контроллер использует `ChatCryptoProvider` и `ChatKeyStorage`, проверяет права до операции, сохраняет ключ только после успешной расшифровки. Async результаты принадлежат runtime owner и generation; смена owner отменяет возможность записать старый результат. Расшифрованное содержимое не сохраняется автоматически в общий durable message cache.

Критерии: явные unavailable/loading/error состояния; корректность смены runtime, повторных событий и ответов не по порядку; отсутствие бизнес-логики в представлении. Тестовая реализация провайдера допускается только в изолированной тестовой среде.

## 4. API, история и realtime

Зависимость: backend поддерживает пять новых `kind` и признак защищённого стрима. По отдельному разрешению пользователя локальный стенд поднят на PR #180; рабочий backend-репозиторий не изменяется. Для разработки контракт проверяется на этом стенде, а перед выпуском — на принятой серверной версии.

Один владелец обновляет DTO/guards и адаптеры; затем существующий путь parse → domain → message store → render расширяется одинаково для REST/истории/realtime. Байты провайдера преобразуются в обычный padded Base64 в `content`/`public_key`; новых полей версии/схемы или wire `bytes` нет. Служебные сообщения не становятся Markdown.

Критерии: контрактные fixtures, корректность неполной истории/корреляции и async ownership, отсутствие регрессий обычных чатов. Рендер расшифрованного содержимого идёт через существующий безопасный render path. Подтверждённая поддержка API предшествует включению отправки.

## 5. Настоящая криптография и постоянное хранение

Зависимость: отдельное решение по схеме, библиотеке и платформенным секретам. Не реализовывать шифрование по текущему черновику.

Провайдер и хранилище заменяют абстракции без переноса криптографии в UI. Генерация device ID/name, восстановление и совместимость между клиентами решаются в этом этапе. Смена поколения не обещает отзыв старых ключей.

Критерии: проверенные test vectors выбранной схемы; совместимость клиентов; проверка адресации выдачи; сохранение приватного ключа при обновлении публичной части; отделение ключей от очистки message cache.

Checkout и инфраструктурные скрипты находятся в `/private/tmp/workspace-e2ee-pr180/stand`. Gateway: `http://127.0.0.1:23190`; отдельная PostgreSQL — `127.0.0.1:5436`. Основной backend checkout и ранее существовавший DB volume сохраняются. REST, модели, миграции и WebSocket-сервис взяты из PR; IAM для тестового проекта заменён локальным stub. Постоянное хранилище ключей и настоящая криптография на стенде не реализованы.

Фронт из текущего UI checkout запущен на `http://127.0.0.1:5176`; команда повторного запуска — `sh /private/tmp/workspace-e2ee-pr180/stand/start-frontend.sh`. Локальные учётные данные находятся в `stand/credentials.json` с правами `0600` и не копируются в документацию. `isValidRealmUrl` допускает HTTP loopback только в DEV; без явного backend адреса HTTP origin Vite не используется для автоматического подключения. Проверено: вход через форму с выбором проекта; появление серверного стрима в списке; создание encrypted stream (`201`); сохранение пяти новых payload (`201`) и история (`200`); реальный WebSocket catch-up, `ready` и получение нового `e2ee` события после REST POST. Повторяемые API проверки и результаты сохраняются рядом со скриптами стенда. Это проверка контрактов и подключения. Frontend DTO и отображение новых kinds реализованы во втором этапе; подключение криптографического контроллера к рабочему shell остаётся отдельным этапом.

Команды запуска, остановки, повторяемых проверок и границы IAM stub описаны в `/private/tmp/workspace-e2ee-pr180/stand/RUNBOOK.md`. Python-окружение использует отдельную версию RestAlchemy и остальные зависимости из существующего read-only окружения backend; это локальная конфигурация этой машины, не заявление о совпадении с CI.

Подтверждены ограничения PR: `GET streams/?encryption=true` возвращает `500`; создание encrypted direct для существующей plaintext-пары возвращает прежний незашифрованный стрим. Review также отмечает несоответствие OpenAPI drafts фактическим Markdown-only drafts; принятие этих API решений остаётся отдельной задачей. При повторной браузерной проверке одна вкладка перестала отвечать; новая вкладка успешно загрузила рабочий inbox. Полный браузерный сценарий E2EE не считается проверенным.

### UI и независимая модель

Первый этап представления и чистая корреляция реализованы. Preview не означает работающий E2EE-мессенджер. Настоящие provider/storage, зашифрованная отправка и подключение действий с ключами к рабочему shell остаются следующими этапами.

Проверки: focused tests модели/preview и существующих маршрутов, Web/Electron typecheck, scoped ESLint/Prettier, локальные ссылки и `git diff --check`. UI проверяется отдельно в браузере: состояния, кнопки, локализация, фокус и отображение панели. Pixel Perfect и native Electron QA не являются выполненными проверками.

### Рабочее представление истории — второй этап

Frontend принимает новые payload выбранного стенда в настоящей истории чата. `WorkspaceMessageBubble` выбирает представление по `payload.kind` до запуска Markdown-рендерера и загрузчиков файлов. Четыре служебных вида переиспользуют `features/encrypted-chat-message`; `e2ee` показывает декоративный закрытый placeholder без передачи зашифрованного `content` в DOM. UUID-якоря, границы прочтения, группировка автора, время и состояние выбора остаются частью существующего списка.

Header и sidebar показывают защищённый чат по серверному `stream.encryption`; одна SVG-иконка используется в обоих местах и информационной панели. В encrypted stream вместо редактора и upload-компонента показано явное отсутствие подключённого криптографического провайдера. Обработчик отправки также блокирует plaintext; криптография и успешная выдача ключа не имитируются.

Feed/activity показывают текстовые названия служебных видов и закрытого сообщения, не Base64. Меню, редактирование, reply/forward и media-gallery не используют криптографические payload как Markdown. Информационная панель в рабочем shell и действия с ключами требуют следующего подключения контроллера; локальный preview остаётся отдельным инструментом.

Проверено focused UI: 4 файла / 334 теста (история, composer, header, preview), затем 6 файлов / 210 тестов (quote, media-gallery, feed/activity, sidebar, история). Тест истории проверяет все пять новых payload, отсутствие encoded content/URN в DOM и отсутствие загрузки preview; тест чата проверяет отсутствие plaintext composer в encrypted stream. Повторные файлы в двух запусках не означают дополнительные уникальные тесты. Проверка браузера и native Electron в этом этапе не выполнялась.

### Независимый контроллер — третий этап

`ChatE2eeController` объединяет загрузку ключа, запрос, выдачу, отказ, обработку объявлений и ответов, шифрование и расшифровку через переданные provider/storage/send-адаптеры. Его экземпляр принадлежит одному runtime owner, устройству, чату и поколению ключа; при смене scope владелец должен закрыть экземпляр и создать новый. Рабочие реализации provider/storage и подключение к UI не входят в этот этап.

Ответ на запрос проверяется по чату, поколению, UUID запроса, аккаунту получателя, ID устройства и его публичному ключу. Получение `key_grant` само по себе не означает доступ: приватный ключ сохраняется только после расшифровки и проверки публичной части. Контроллер ждёт отсутствующий запрос или публичный ключ, обрабатывает повторную доставку и продолжает очередь после некорректного ответа. Права повторно проверяются перед отправкой и записью. Storage-адаптер обязан проверить переданный guard непосредственно при durable commit; runtime generation не становится частью постоянного адреса ключа.

Focused проверки контроллера: 21 тест, включая смену owner A→B→A, устройства/чата/поколения, отложенную запись, отзыв прав, несовпадение публичного ключа, дубликаты, перестановку доставки и восстановление после ошибки provider. Это проверка оркестрации с тестовыми зависимостями, не проверка настоящей криптографии.

Исторический результат проверки второго и третьего этапов: 5283 теста прошли, один тест иконок выявил фиксированный fill новой SVG. Иконка переведена на `currentColor` и общий реестр; последующий focused запуск 215 тестов прошёл. Более поздние проверки описаны ниже.

### Правая панель реального шифрованного чата

После базового контроллера (`b5eef8ae`) панель информации каналов и личных чатов подключена к существующему Workspace drawer. Презентационные компоненты перенесены в `features/encrypted-chat-info`, чтобы сохранить допустимые зависимости слоёв. Панель берёт текущий UUID ключа из `stream.currentEncryptionKey`, участников из привязок каталога и запросы текущего ключа из загруженной истории. Это список запросов в загруженной истории, а не полный реестр ожидающих запросов. Дата ключа показывается только при наличии соответствующего `key_announced`; дата создания чата её не заменяет.

Каталог, сообщения и пользователи проверяются относительно текущего runtime owner и проекта. Данные старого владельца не используются; пользовательские имена и аватары не берутся из чужого user store. Копирование актуального публичного ключа выполняется явно через существующий clipboard helper с проверкой runtime до операции и после завершения. Выдача, отказ и перевыпуск остаются недоступными до подключения провайдера и хранения ключей; UI не имитирует успешные операции. Callback существующего drawer закрывает панель; обычные панели чатов сохраняют прежний маршрут.

### DEV-стенд контроллера с реальным API

[Страница стенда](../packages/web/src/pages/encrypted-chat/encrypted-chat-sandbox.ui.tsx) доступна по `/login/e2ee-sandbox` только в DEV. На текущем локальном frontend это `http://127.0.0.1:5176/login/e2ee-sandbox`. Нужна активная Workspace-сессия с корректным loopback origin backend: `localhost`, `127.0.0.1` или `[::1]`. API использует фиксированный путь Vite proxy и явный локальный target; адреса с credentials, path, query или fragment отклоняются до создания mock-провайдера, чтобы не использовать другой target по умолчанию.

Перед действиями постоянно показано «ЭТО НЕ НАСТОЯЩЕЕ ШИФРОВАНИЕ». [Фабрика стенда](../packages/web/src/features/chat-e2ee-dev-sandbox/chat-e2ee-dev-sandbox.lib.ts) создаёт новый encrypted stream с меткой `INSECURE E2EE TEST`; она не принимает UUID существующего чата. Запросы создания, публикации пяти kinds и загрузки истории проходят через обычный REST API и Base64-адаптеры. В message store и durable cache рабочего shell тестовые состояния не записываются.

Два устройства имитируются внутри одной страницы и одной пользовательской сессии. Права выдающего устройства — фиксированные возможности стенда, не выбранная политика ролей продукта. Ключи находятся только в памяти; mock-гранты также работают только в пределах этого запуска страницы. Перезагрузка страницы или смена runtime удаляет локальные ключи и данные стенда; созданный тестовый stream остаётся на backend. Это не обмен между двумя браузерами и не постоянное восстановление ключей.

Порядок проверки: создать тестовый чат, отправить фиксированное сообщение, переключиться на получающее устройство и запросить ключ, вернуться к выдающему и выдать либо отклонить запрос, переключиться обратно и загрузить историю. До выдачи сообщение закрыто; после проверенного гранта контроллер допускает расшифровку фиксированного примера. Поля для произвольного plaintext нет. Production и обычная панель чата не подключают mock-провайдер.

Проверки новой страницы, фабрики и маршрутов: 27 focused тестов прошли; scoped ESLint/Prettier и `git diff --check` прошли. Сценарии включают production/remote-origin запрет, ограничение собственным новым stream, request/grant/reject/history/decrypt, A→B→A во время инициализации, позднюю историю после cleanup и подавление устаревшего React update. Результат полного Web запуска на этой волне: 481 файл, 5290 тестов прошли. Новые sandbox tests добавлены после начала этого полного запуска; итоговый focused запуск текущих изменений дополнил его проверкой 7 файлов и 84 тестов. Web/Electron typecheck прошёл после последних изменений.

В браузере подтверждены рабочая история пяти kinds и API-запросы с корректными заголовками. ### Создание в обычном интерфейсе — локальная проверка

Флажок шифрования добавлен в существующий диалог создания канала. При выборе сбрасываются и блокируются конфликтующие параметры invite-only, announce и announcement-only. Создание проходит через обычный domain action и настоящий API; созданный encrypted stream появляется в sidebar, открывается обычная история и информационная панель защищённого чата. Серверный `stream.encryption` определяет состояние интерфейса. Закрытие панели сохраняется после обновления страницы; открыть её снова можно штатной кнопкой.

Backend требует initial key одновременно с `encryption: true`. [Контракт подготовки ключа](../packages/web/src/entities/messenger/chat-initial-key-bootstrap.lib.ts) отделён от создания: будущая реализация отвечает за генерацию и хранение, action передаёт только UUID и Base64 публичных байтов. До подключения такой реализации production возвращает явную ошибку; обычный канал вместо encrypted не создаётся. Ответ с неверным флагом шифрования или другими initial-key metadata не попадает в store.

Для текущей локальной проверки интерфейса DEV-адаптер подставляет явно тестовые публичные metadata `DEV_ONLY_NO_CRYPTO_PUBLIC_KEY`. Диалог показывает соответствующее предупреждение. Это только выполнение обязательного поля API: приватного ключа, доступа создателя к расшифровке и настоящего криптографического алгоритма оно не предоставляет. Адаптер работает исключительно с loopback organization origin и явным локальным proxy target; путь API фиксируется, remote/credentials/arbitrary-base overrides запрещены. Обычная отправка plaintext в encrypted chat остаётся заблокированной. Криптографический провайдер, схема и постоянное хранение ключей ещё не выбраны.

Focused domain tests: 19 прошли, включая production/remote запрет, небезопасные routing overrides, canonical Base64, проверку ответа, A→B→A во время подготовки и запрет поздней сетевой отправки после смены runtime. Полный Web запуск на этой волне: 484 файла, 5323 теста прошли до последних focused дополнений; это снимок полного запуска, а не повторный запуск после каждого изменения. Web/Electron typecheck прошёл. В браузере подтверждён обычный сценарий создания: конфликтующие флажки выключены и недоступны, POST создания вернул 201, новая encrypted строка показывает замок, обычный чат открывает новую панель с одним заголовком, close → refresh сохраняет закрытое состояние, ручное повторное открытие работает. Это локальная UI/API-проверка; настоящая криптография и native Electron QA не заявляются.

### Временный mock-провайдер в обычном чате

По явному запросу пользователя локальный обычный encrypted chat теперь допускает ввод, отправку и чтение текста через временный mock-провайдер, без выбора криптографической библиотеки. Предыдущее ограничение «обычная панель не подключает mock» заменено этим DEV-сценарием. Интерфейс постоянно предупреждает, что это тестовая имитация, а не настоящее шифрование. Attachments, выдача ключей и production-реализация в этот сценарий не входят.

[Mock-провайдер и presentation decoder](../packages/web/src/entities/messenger/chat-dev-crypto.lib.ts) работают только в DEV, с loopback organization и публичными metadata из точного allowlist: `DEV_ONLY_NO_CRYPTO_PUBLIC_KEY` либо старый известный fixture `FIX` (`RklY`). Другие ключи остаются недоступными. [Явное действие отправки](../packages/web/src/entities/messenger/chat-dev-message-actions.lib.ts) использует обычный message action с отдельным opt-in; generic Markdown send и forward не обходят запрет encrypted stream. API target обязан совпадать с текущим локальным organization, путь proxy фиксируется.

Mock кодирует текст в помеченный тестовый envelope, привязанный к UUID чата и поколению ключа, затем Base64 в существующий `e2ee.content`. Это обратимое представление plaintext без криптографической защиты. В API, message store и durable cache остаётся только encoded `e2ee` payload; decoded текст существует только в presentation и проходит обычный безопасный renderer. После обновления страницы такие тестовые сообщения читаются статeless decoder без постоянного приватного ключа. Произвольные legacy ciphertext и malformed envelopes остаются закрытыми.

Перед отправкой загружаются актуальные серверные metadata чата; смена runtime, удаление известного чата и смена его ключа блокируют позднюю отправку либо применение ответа. Ответ проверяется по автору, пользователю, проекту, чату, topic, UUID сообщения и точному payload до записи в store/cache. Реальное шифрование, управление устройствами, ключами и их выдача по правам остаются отдельным следующим этапом.

### Локальный стенд: согласованная идентичность сообщений REST и realtime

При проверке mock в обычном чате обнаружено расхождение локальной конфигурации: стенд использует `SQLCanonicalMessengerStoreFactory` с публичными compatibility UUID в REST/history, а migration 0152 преобразует UUID событий в внутренние v2 placement UUID. Один POST поэтому временно давал два разных сообщения в UI; после обновления страницы оставалось одно. Frontend не должен угадывать соответствие этих UUID или скрывать дубли по содержимому.

В изолированном checkout PR #180 (`77f2ced5030271c075d6b09b35e7a267e954601b`, `/private/tmp/workspace-e2ee-pr180`) добавлен только адаптер стенда `stand/legacy_event_contract.py`. Его event store применяет существующую backend-функцию `messenger_v2_rewrite_event_payload(project, object_type, payload, true, false)` к читаемой проекции события. `stand/server.py` и `stand/gateway.py` выбирают эту фабрику, согласованную с REST стенда. Core source PR, таблицы, сохранённые сообщения, triggers и внутренние placement UUID не изменены. Это исправление локальной конфигурации; оно не означает изменения согласованного frontend API и не должно переноситься в production без проверки выбранного backend store.

После перезапуска проверен обычный UI: создание собственного тестового encrypted channel, одна отправка `kind=e2ee`, одинаковый публичный UUID в POST response, WebSocket и history, один bubble до и после reload. Открытый текст отсутствует в JSON запроса; тестовый текст читается в UI после reload. Ошибок браузера/API нет. Патч адаптера сохранён отдельно в `stand/e2ee-event-public-uuid.patch`; существующие 16 backend projection runtime tests прошли. Текущий пользовательский чат с известным fixture key `FIX` проверен только на доступность composer и видимое предупреждение о mock; сообщения в него проверка не отправляла.
