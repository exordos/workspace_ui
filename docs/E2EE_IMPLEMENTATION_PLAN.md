# E2EE: этапы реализации

Дата: 2026-10-02. Основание: [подготовительная записка](E2EE_IMPLEMENTATION_PLANNING.md) и [контрактный черновик](E2EE_CHAT_DRAFT.md).

Актуализация 2026-10-05: чат использует `GroupKey` + ChaCha20-Poly1305 и HPKE с отдельной парой на запрос; поколения адресуются через `key_uuid` без отпечатка. [План реальной криптографии](E2EE_REAL_CRYPTO_PLAN.md) содержит выбранную схему. Обычный UI подключён к real provider: создание, отправка, запрос и выдача ключа, расшифровка истории после reload проверены в браузере на локальном стенде. Старые этапы ниже сохраняются как история.

## Границы и принятый подход

Реализация начинается с представления и независимой модели. Backend на проверенном revision `7604087` принимает только `markdown`; расширение рабочих DTO, истории и realtime требует отдельно подтверждённого серверного контракта. Этот первоначальный этап выбора библиотеки и хранения заменён [новым планом](E2EE_REAL_CRYPTO_PLAN.md).

Для локальной интеграционной проверки выбран [backend PR #180](https://github.com/exordos/workspace_backend/pull/180), head `77f2ced5030271c075d6b09b35e7a267e954601b`. Это отдельный тестовый checkout, а не production backend. Тестовый контракт содержит пять новых `kind`, `device_name`, признак стрима `encryption` и `current_encryption_key: { key_uuid }`; `key_request.public_key` остаётся ключом X25519-запроса. Начальное поколение задаётся при создании стрима, `key_announced` объявляет новый UUID поколения.

UI максимально переиспользует существующие `Button`, `SelectableRow`, `Icon`, `Avatar`, `ScrollArea`, `Spinner` и семантические токены темы. Pixel Perfect не требуется. Новый компонент нужен только для отсутствующего представления; общие примитивы не дублируются. Для карточек служебных сообщений подходящей общей оболочки пока нет: `AttachmentCard` имеет файловую семантику и сюда не подходит.

Макеты прочитаны через Figma Bridge MCP: общий блок `10879:26030`, основная панель `11026:27080`, служебные сообщения `11026:27023`. Основной объём — панель информации справа: ключ, запросы доступа и участники. Заголовок панели, аватар защищённого чата, имя устройства и действия передачи/отказа передаются через presentation props. Из Figma экспортированы только отсутствующие иконки; аватары участников остаются динамическими.

### Менеджер локальных ключей — 2026-10-08

Экран «Ключи шифрования» сохраняет актуальный UUID стрима и перевыпуск в верхнем блоке. Аккордеон ниже показывает только секреты, реально сохранённые для текущего аккаунта, устройства и чата; актуального UUID среди них может не быть. В этом случае отдельная кнопка запрашивает актуальное поколение и остаётся доступной при свёрнутом списке.

Компактная строка показывает UUID, актуальное/историческое поколение и дату добавления. Подробности открываются внутри существующего drawer: дата объявления берётся из загруженного `key_announced`, дата первого локального сохранения — из IndexedDB. Отсутствующая дата показывается явно, без подстановки даты чата. В UI передаются только метаданные, без байтов ключа.

Повторное получение сохраняет `key_uuid` и имеющийся секрет. Если доступно сообщение этого поколения, ручное восстановление проверяет отличающийся кандидат на нём; без проверочного сообщения отличающийся секрет не перезаписывается. Перевыпуск создаёт новый UUID и остаётся отдельной операцией всего чата.

Удаление локального ключа требует подтверждения, атомарно убирает секрет и незавершённые запросы этого поколения, обновляет открытые сообщения и выбор ключа отправки. Запись без секрета хранит счётчик удаления: подготовленная до удаления заявка не может сохраниться после него даже до доставки уведомления другой вкладке. Повторное явное получение после удаления разрешено.

## 1. Представление и локальный preview

Владелец панели — UI-субагент; закрытых и служебных сообщений — отдельный UI-субагент. Оркестратор владеет страницей, маршрутом и переводами.

- [EncryptedChatInfo](../packages/web/src/features/encrypted-chat-info/encrypted-chat-info.ui.tsx): информация о чате, текущий ключ, запросы, участники. Все права и операции приходят через props; без API, криптографии и обращения к хранилищам.
- [Закрытое сообщение](../packages/web/src/features/encrypted-chat-message/encrypted-message-placeholder.ui.tsx): `locked`, `loading`, `error`. Блюр строится из пустых декоративных полос; plaintext не принимается.
- [Служебное сообщение](../packages/web/src/features/encrypted-chat-message/encrypted-chat-service-message.ui.tsx): четыре отдельных `kind`, готовые строки и разрешённые действия.
- [Preview](../packages/web/src/pages/encrypted-chat/encrypted-chat-preview.ui.tsx): локальные примеры без записи в message store/cache. Маршрут `/login/e2ee-preview` доступен только при `import.meta.env.DEV`, вне рабочего Layout, с авторизацией и без неё. Проверка панели возможна до подключения backend.

Критерии: повторное использование UI-примитивов; переключение представлений с правами/без прав, с ключом/без ключа; loading блокирует действия; закрытие возвращает фокус; операции явно показывают отсутствие интеграции, не имитируют выдачу ключа. Имена ключа и дата в макете пока являются входными display metadata: источник этих данных отсутствует в `key_announced` и требует согласования.

## 2. Независимая модель доступа и корреляции

Владелец — контрактный субагент. [Типы](../packages/web/src/entities/messenger/chat-e2ee.types.ts) отделены от текущего live API. [Корреляция](../packages/web/src/entities/messenger/chat-e2ee.lib.ts) проверяет стрим, внешний UUID запроса, поколение, адресата и разрешение автора ответа. Отсутствующий запрос означает неполную историю. Полученный контейнер выдачи не открывает доступ автоматически. Наличие ключа считается для точного адреса owner/device/stream/generation.

Критерии: пять payload без универсальной системной оболочки; отдельные `missing`, `public-only`, `ready` для поколения; grant/reject другому запросу/устройству не меняет доступ; повторная обработка детерминирована. Focused tests проверяют эти инварианты.

## 3. Контроллер сценариев и рабочая композиция

Следующий этап после представления. Оркестратор согласует props и отдаёт одному агенту сценарную логику, другому — подключение панели; общие composition-файлы имеют одного владельца.

Перед подключением разрешить продуктовые вопросы: отдельный раздел или режим текущего мессенджера; соответствие права выдачи ролям; политика отправки с одним публичным ключом; выбор поколения; источник первоначального объявления; обработка нескольких ответов. Визуальные варианты автоматической выдачи в макете не являются принятой политикой.

Контроллер использует `ChatCryptoProvider` и `ChatKeyStorage`, проверяет права до операции, сохраняет ключ только после успешной расшифровки. Async результаты принадлежат runtime owner и generation; смена owner отменяет возможность записать старый результат. Расшифрованное содержимое не сохраняется автоматически в общий durable message cache.

Критерии: явные unavailable/loading/error состояния; корректность смены runtime, повторных событий и ответов не по порядку; отсутствие бизнес-логики в представлении. Тестовая реализация провайдера допускается только в изолированной тестовой среде.

## 4. API, история и realtime

Зависимость: backend поддерживает пять новых `kind` и признак защищённого стрима. По отдельному разрешению пользователя локальный стенд поднят на PR #180; рабочий backend-репозиторий не изменяется. Для разработки контракт проверяется на этом стенде, а перед выпуском — на принятой серверной версии.

Один владелец обновляет DTO/guards и адаптеры; затем существующий путь parse → domain → message store → render расширяется одинаково для REST/истории/realtime. Байты провайдера преобразуются в обычный padded Base64 в `content`/`public_key`; новых полей версии/схемы или wire `bytes` нет. Служебные сообщения не становятся Markdown.

Критерии: контрактные fixtures, корректность неполной истории/корреляции и async ownership, отсутствие регрессий обычных чатов. Рендер расшифрованного содержимого идёт через существующий безопасный render path. Подтверждённая поддержка API предшествует включению отправки.

## 5. Настоящая криптография и постоянное хранение

Зависимость: отдельное решение по схеме, библиотеке и платформенным секретам. Не реализовывать шифрование по текущему черновику.

Провайдер и хранилище заменяют абстракции без переноса криптографии в UI. Генерация device ID/name, восстановление и совместимость между клиентами решаются в этом этапе. Смена поколения не обещает отзыв старых ключей.

Критерии: проверенные test vectors выбранной схемы; совместимость клиентов; проверка адресации выдачи; сохранение приватного ключа при обновлении публичной части; отделение ключей от очистки message cache.

Backend не хранит секреты: real provider и durable key storage реализованы в frontend по новому плану.

Повторяемые API проверки и результаты сохраняются рядом со скриптами стенда. Это проверка контрактов и подключения. Frontend DTO и отображение новых kinds реализованы во втором этапе; подключение криптографического контроллера к рабочему shell остаётся отдельным этапом.

Python-окружение использует отдельную версию RestAlchemy и остальные зависимости из существующего read-only окружения backend; это локальная конфигурация этой машины, не заявление о совпадении с CI.

Подтверждены ограничения PR: `GET streams/?encryption=true` возвращает `500`; создание encrypted direct для существующей plaintext-пары возвращает прежний незашифрованный стрим. Review также отмечает несоответствие OpenAPI drafts фактическим Markdown-only drafts; принятие этих API решений остаётся отдельной задачей. При повторной браузерной проверке одна вкладка перестала отвечать; новая вкладка успешно загрузила рабочий inbox. Полный браузерный сценарий E2EE не считается проверенным.

### UI и независимая модель

На том этапе реализованы представление и чистая корреляция; последующее подключение real provider/storage и shell описано в актуализации выше.

Проверки: focused tests модели/preview и существующих маршрутов, Web/Electron typecheck, scoped ESLint/Prettier, локальные ссылки и `git diff --check`. UI проверяется отдельно в браузере: состояния, кнопки, локализация, фокус и отображение панели. Pixel Perfect и native Electron QA не являются выполненными проверками.

### Рабочее представление истории — второй этап

Frontend принимает новые payload выбранного стенда в настоящей истории чата. `WorkspaceMessageBubble` выбирает представление по `payload.kind` до запуска Markdown-рендерера и загрузчиков файлов. Четыре служебных вида переиспользуют `features/encrypted-chat-message`; `e2ee` показывает декоративный закрытый placeholder без передачи зашифрованного `content` в DOM. UUID-якоря, границы прочтения, группировка автора, время и состояние выбора остаются частью существующего списка.

Header и sidebar показывают защищённый чат по серверному `stream.encryption`; одна SVG-иконка используется в обоих местах и информационной панели. В encrypted stream вместо редактора и upload-компонента показано явное отсутствие подключённого криптографического провайдера. Обработчик отправки также блокирует plaintext; криптография и успешная выдача ключа не имитируются.

Feed/activity показывают текстовые названия служебных видов и закрытого сообщения, не Base64. Меню, редактирование, reply/forward и media-gallery не используют криптографические payload как Markdown. На том этапе информационная панель и действия ожидали подключения контроллера; локальный preview остаётся отдельным инструментом.

Проверено focused UI: 4 файла / 334 теста (история, composer, header, preview), затем 6 файлов / 210 тестов (quote, media-gallery, feed/activity, sidebar, история). Тест истории проверяет все пять новых payload, отсутствие encoded content/URN в DOM и отсутствие загрузки preview; тест чата проверяет отсутствие plaintext composer в encrypted stream. Повторные файлы в двух запусках не означают дополнительные уникальные тесты. Проверка браузера и native Electron в этом этапе не выполнялась.

### Независимый контроллер — третий этап

`ChatE2eeController` объединяет загрузку ключа, запрос, выдачу, отказ, обработку объявлений и ответов, шифрование и расшифровку через переданные provider/storage/send-адаптеры. Его экземпляр принадлежит одному runtime owner, устройству, чату и поколению ключа; при смене scope владелец должен закрыть экземпляр и создать новый. Рабочие реализации provider/storage и подключение к UI не входят в этот этап.

Ответ на запрос проверяется по чату, поколению, UUID запроса, аккаунту получателя, ID устройства и его публичному ключу. Получение `key_grant` само по себе не означает доступ: приватный ключ сохраняется только после расшифровки и проверки публичной части. Контроллер ждёт отсутствующий запрос или публичный ключ, обрабатывает повторную доставку и продолжает очередь после некорректного ответа. Права повторно проверяются перед отправкой и записью. Storage-адаптер обязан проверить переданный guard непосредственно при durable commit; runtime generation не становится частью постоянного адреса ключа.

Focused проверки контроллера: 21 тест, включая смену owner A→B→A, устройства/чата/поколения, отложенную запись, отзыв прав, несовпадение публичного ключа, дубликаты, перестановку доставки и восстановление после ошибки provider. Это проверка оркестрации с тестовыми зависимостями, не проверка настоящей криптографии.

Исторический результат проверки второго и третьего этапов: 5283 теста прошли, один тест иконок выявил фиксированный fill новой SVG. Иконка переведена на `currentColor` и общий реестр; последующий focused запуск 215 тестов прошёл. Более поздние проверки описаны ниже.

### Правая панель реального шифрованного чата

После базового контроллера (`b5eef8ae`) панель информации каналов и личных чатов подключена к существующему Workspace drawer. Презентационные компоненты перенесены в `features/encrypted-chat-info`, чтобы сохранить допустимые зависимости слоёв. Панель берёт текущий UUID ключа из `stream.currentEncryptionKey`, участников из привязок каталога и запросы текущего ключа из загруженной истории. Это список запросов в загруженной истории, а не полный реестр ожидающих запросов. Дата ключа показывается только при наличии соответствующего `key_announced`; дата создания чата её не заменяет.

Каталог, сообщения и пользователи проверяются относительно текущего runtime owner и проекта. Данные старого владельца не используются; пользовательские имена и аватары не берутся из чужого user store. Копирование актуального публичного ключа выполняется явно через существующий clipboard helper с проверкой runtime до операции и после завершения. Выдача, отказ и перевыпуск остаются недоступными до подключения провайдера и хранения ключей; UI не имитирует успешные операции. Callback существующего drawer закрывает панель; обычные панели чатов сохраняют прежний маршрут.

### Текущие пути создания и проверки

Обычный диалог создания канала использует [реальный bootstrap](../packages/web/src/entities/messenger/chat-real-key-bootstrap.lib.ts): ключ создаётся и сохраняется на устройстве, в API передаётся UUID поколения. Ответ с неверным флагом шифрования или UUID поколения не применяется к каталогу. Обычная Markdown-отправка в encrypted stream запрещена; отправка ciphertext проходит через реальный crypto runtime и отдельный opaque-payload action.

Временные DEV bootstrap, mock-провайдер, decoder и insecure sandbox `/login/e2ee-sandbox` удалены после подключения реальной криптографии. Они не обеспечивали защиту и дублировали продуктовые пути. Для UI-проверки остаётся DEV-only `/login/e2ee-preview`: локальные presentation fixtures без обращения к API и записи ключей или сообщений в store/cache. Для проверки протокола используются regression tests реального provider/controller/runtime/storage и обычный encrypted chat.

Следующие записи о локальном backend-стенде описывают историческую проверку; они не являются текущими инструкциями подключения mock-провайдера.

### Локальный стенд: согласованная идентичность сообщений REST и realtime

При проверке mock в обычном чате обнаружено расхождение локальной конфигурации: стенд использует `SQLCanonicalMessengerStoreFactory` с публичными compatibility UUID в REST/history, а migration 0152 преобразует UUID событий в внутренние v2 placement UUID. Один POST поэтому временно давал два разных сообщения в UI; после обновления страницы оставалось одно. Frontend не должен угадывать соответствие этих UUID или скрывать дубли по содержимому.

Core source PR, таблицы, сохранённые сообщения, triggers и внутренние placement UUID не изменены. Это исправление локальной конфигурации; оно не означает изменения согласованного frontend API и не должно переноситься в production без проверки выбранного backend store.
