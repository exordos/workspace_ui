# Encrypted chats

Current for the client implementation on this branch as of 2026-10-23. This is a reference to implemented code, not a development plan or confirmation of production deployment. Related issue: [workspace_ui #177](https://github.com/exordos/workspace_ui/issues/177).

## Capabilities

- Create a stream with `encryption: true`, generating and durably storing the creator's key before the network request.
- Send and edit encrypted text and read history after reload when the local key is available. Editing an own readable message uses the shared menu and composer, including ArrowUp, and re-encrypts with the original message generation. Removing its key clears the editor. Messages without a key remain locked; decryption errors allow retrying and requesting the message's key.
- Sidebar last-message previews use the same local decryption and the message's exact key UUID. Available text is summarized in presentation memory only; missing keys show "Key required", while encrypted service messages use their standard labels. Key changes refresh mounted previews without persisting plaintext in the message store or cache.
- Request a current or historical generation's key; grant, reject, or grant in bulk with individual request outcomes. Owners and administrators can grant and reject requests; granting requires the requested generation's local key.
- Rotate the key as the owner, with confirmation: a new generation does not rewrite existing history. Participants request the new key themselves.
- View local keys and delete a selected key with confirmation. Deletion removes available plaintext from mounted messages and notifies other tabs.
- Until the current key is received, sending can use the last available local key and its UUID. Receiving the current key automatically switches subsequent sends; sending is unavailable when no keys are available.
- Start calls from the shared chat header or encrypted chat sidebar through the existing Jitsi flow. The invitation link is sent through the crypto session and requires an available local sending key.

Ordinary Markdown send/edit/forward operations and saving ordinary server drafts are blocked for encrypted chats. Text and attachment references are encrypted together in the message. Attachments use the existing Workspace file upload flow; their bytes and file metadata are not E2EE-encrypted. Both ordinary and encrypted sends enter the shared in-memory outbox before the composer clears and restores focus. Failed sends retain their text and uploaded attachment references in the outgoing row for retry, while the editor remains available for the next message. Converting an existing chat to encrypted mode and automatically granting keys to a new device are not implemented by this flow.

Decrypted attachment references use the existing inline image/video previews and file download actions. Locking a message after local key deletion or an owner change removes inline previews, aborts their pending loads, and releases their display URLs. Plaintext references remain in scoped presentation memory; the message store retains the encrypted payload. Deleting a chat key does not revoke access to unencrypted media already opened in the viewer, downloaded files, or previously learned file references.

Successfully decrypted text uses the same segmented message renderer as ordinary Markdown, including quote components, mentions, code controls, and Jitsi cards. A referenced encrypted original is decrypted independently with its own exact key UUID, including historical generations. Without that key, the quote shows the decorative blurred placeholder; selected quote text does not bypass the key check. Removing the original's key clears its quote content and media while leaving a separately readable reply visible. Plaintext is never written back into the canonical message store or durable cache. Forward snapshots remain self-contained content of their enclosing message.

## Protected fragments in ordinary native chats

The ordinary native-chat composer can protect selected text using its encrypted-spoiler action. Public text stays ordinary Markdown; each protected range becomes a neutral-label link with `urn:secret:v1:<source-stream-uuid>:<key-uuid>:<base64url-envelope>`. Multiple ranges use the same existing chat sending key and independent envelopes. The source stream stays in the URN so forwarded ciphertext uses the original crypto context and key storage address. A missing key locks only the affected fragment; the remaining message remains readable. Reusing a key grants access to every fragment encrypted with that generation that the recipient can obtain.

Readable fragments start visually hidden for everyone, including the author. Each fragment has a keyboard-accessible control to reveal and hide its content; reloading closes it again. This local spoiler state does not change key access.

This uses the same session, controller, storage, requests, HPKE grants, history, and deletion notifications as an encrypted chat. Keys have no author or purpose classification. Any participant with send permission can prepare a key through the same provider and storage, reuse the last available local key (including a received key), or choose a new key with the optional composer checkbox. Fragment key creation does not announce or change the channel's current key. Ordinary messages without protected ranges do not require a key.

Fragment requests use the existing `key_request` wire format, addressed by the source stream and key UUID, just like encrypted-chat requests. They are not bound to an individual message or its author: the same key can decrypt multiple messages and fragments. Pending requests and retries are shared for that key generation. In ordinary native chats, a current participant with send permission and the exact local generation key can grant or reject another current participant's request. Owners and administrators can still reject without that key. Received responses require a current source-chat participant and retain the request, device, generation, and cryptographic checks; unrelated or departed participants cannot issue accepted responses. Membership changes retry responses that arrived before participant hydration. Fully encrypted chats keep the owner/administrator policy. Forwarded fragments request the key from their original stream without resolving an original message.

Protected editor ranges use paired client-only `:::` delimiters: `:::private text:::` works inline and the content may span multiple lines. Delimiters pair from left to right without nesting; every `:::` starts or closes a protected range. The encrypted-spoiler button wraps selected text or inserts an empty block with the caret inside. Its hover/focus hint tells users to enable it before entering secret text because earlier ordinary input may already have reached a server draft. The first `:::` immediately disables durable and remote draft saving, including for an unfinished or empty `::::::` range. Protected ranges are replaced before POST/PATCH; empty, whitespace-only, or unmatched ranges block sending. While a draft contains a protected range, its text and reply state stay in the existing composer-draft store's memory-only shadow, scoped by account owner and conversation, and are not saved to IndexedDB or server drafts. These shadows survive navigation and switching between signed-in accounts without mixing their content; reloading the page or removing the account clears them. Sending or clearing a draft removes its shadow without clearing a newer draft. Promoting a previously ordinary draft scrubs queued local content and deletes the remote draft using a metadata-only tombstone. A draft request already dispatched before the selection was marked private may have sent its earlier ordinary text; its response is followed by deletion, without restoring that body into the local draft. Uncertain creates recover only their ETag with a single-draft GET by UUID instead of repeating the previous plaintext POST.

Editing an own mixed message restores its encrypted links as `:::private text:::` in composer memory, including multiline content and reply answers. Every original fragment must be readable; unavailable keys or ambiguous delimiters leave editing unavailable. Code literals stay unchanged, and attachments are extracted before decryption so references inside a secret cannot become public attachments. Saving encrypts all remaining protected ranges with the session's sending generation before updating the Markdown payload; removing the delimiters explicitly makes that text public. The same editor can add protected ranges to an ordinary message. Edit text is not saved as a draft, and removing any original fragment key or changing the source message clears the editor. Rotation alone preserves the edit; stale decryption after navigation or runtime changes cannot reopen it.

Partial sends use the common in-memory outbox. After key preparation and enqueueing, the composer clears and delivery continues in the outbox. The final Markdown and encrypted envelopes are retained before dispatch, so a lost response retries the same message UUID and ciphertext without another key rotation. Editing preserves existing encrypted URNs and encrypts newly marked ranges. Quotes and forwards preserve encrypted references rather than automatically persisting selected revealed plaintext. The ordinary 40,000-character limit applies to the final Markdown, including the URNs. File bytes remain outside this protection; selecting a Markdown file reference encrypts only its reference.

## Device-specific key requests

In ordinary chats, the message feed hides general key announcements and service events unrelated to the viewing account. It keeps the account's own requests and responses, incoming requests it can manage, and grants/rejections linked to these requests, including those addressed to another device of the account. Recipient identity comes from the matching request (project, stream, key, and device); requests outside the current history window use the existing scoped message resolver. Visible events retain the existing disclosure and action rules. Hidden events do not contribute to event counts or date/topic/author groups. This is presentation-only: service-event storage and crypto processing are unchanged, and encrypted chats retain their full service history.

Request titles name the requesting account and target device: "You requested a security key for device…" for the current account, or the other person's name. Device names come from the request; IDs determine device equality. Separate tabs sharing the same secrets database represent the same device. Blank names display "Unknown device"; existing installations default to "Workspace browser".

The following table describes fully encrypted-chat requests. "Manager" means an owner or administrator; having the key or sharing an account never grants this role. Ordinary native-chat fragment requests instead allow current participants with the exact requested generation key to respond, including the fragment author or someone who previously received that key. Such requests and their correlated responses remain visible to these key holders in the account-filtered feed. A different local generation does not grant response rights. Owners and administrators retain rejection without the key. On the requesting device itself, grant/reject actions remain hidden.

| Request author  | Viewing device    | Viewer role | Requested generation's local key | Presentation                                                                                     |
| --------------- | ----------------- | ----------- | -------------------------------- | ------------------------------------------------------------------------------------------------ |
| Current account | Requesting device | Manager     | Either                           | Suggest approval on another device with the key, or waiting for access. No grant/reject actions. |
| Current account | Requesting device | Member      | Either                           | Existing wait-for-access text. No grant/reject actions.                                          |
| Current account | Another device    | Manager     | Available                        | Send key and reject actions. No wait-for-access text.                                            |
| Current account | Another device    | Manager     | Unavailable                      | Explain that the requested key is missing here. Reject remains available.                        |
| Current account | Another device    | Member      | Either                           | Existing wait-for-access text. No grant/reject actions.                                          |
| Another account | Viewer's device   | Manager     | Available                        | Send key and reject actions.                                                                     |
| Another account | Viewer's device   | Manager     | Unavailable                      | Explain that the requested key is missing here. Reject remains available.                        |
| Another account | Viewer's device   | Member      | Either                           | Author and target device only; no grant/reject actions.                                          |

Completed requests show "Key sent" or "Request rejected" without waiting text or response actions. Actions are disabled during operations. Until the scoped session is available, the UI does not suggest approving on another device. Historical requests use their exact generation; a newer local key is insufficient.

Grants and rejections name the actor, recipient, and target device. The same account on another device does not imply local receipt. "The key is available on this device" requires both the matching recipient account/device and a locally available generation key. Retry after rejection is shown on the requesting device when allowed by the existing session rules. A response whose request is unavailable or mismatched does not infer its recipient.

The [service-message tests](../packages/web/src/widgets/workspace-message-list/workspace-encrypted-message-bubble.ui.test.tsx) cover these display states. [Runtime tests](../packages/web/src/entities/messenger/chat-crypto-runtime.lib.test.ts) cover owner, administrator, and member accounts across two device scopes. [Chromium tests](../e2e/workspace-local-keys.spec.ts) exercise one account across isolated browser contexts, persisted requests, real cryptography, and mocked REST history: owner transfer succeeds and member transfer remains unavailable.

The [outbox delivery](../packages/web/src/entities/messenger/messenger-outbox-delivery.lib.ts) keeps a session lease until each encrypted attempt completes, independently of the open route. Each outgoing message retains its canonical UUID, exact sending key UUID, device ID, and, once prepared, encrypted envelope. An ambiguous POST retries the same UUID and envelope; retries still check the live runtime, permissions, local key and deletion revision. A different sending key or device fails the existing row instead of silently rebinding it. Uploaded files transfer to the outbox when enqueue succeeds and are not deleted when the composer unmounts.

The messenger store owns the stream, current key UUID, and roles. The session does not fetch them through a separate HTTP flow; it relies on shared bootstrap and participant loading. The page and drawer share a session for the same owner/runtime generation/stream; the final consumer releases it. The shared session manager alone ingests service messages from the message store. Consumers can await that same ingestion before an action, and ingestion errors remain visible through the session hook. A generation change preserves the session and editor text. Session state notifications are separate from key change notifications.

## Wire contract and cryptography

Exact DTOs and validation are in [messenger.types.ts](../packages/web/src/shared/api/messenger.types.ts); byte conversion is in the [payload adapter](../packages/web/src/entities/messenger/chat-e2ee-payload-adapters.lib.ts). The client expects `current_encryption_key_uuid`. Messages use `e2ee`, `key_request`, `key_grant`, `key_reject`, and `key_announced`; an announcement contains only `kind` and `key_uuid`.

`key_uuid` addresses a generation of a random 32-byte symmetric `GroupKey`; it is not its fingerprint. `key_request.public_key` is the public X25519 key of an individual request. `e2ee.content` and `key_grant.content` contain binary envelopes encoded as standard padded Base64. `GroupKey` and private request keys are never sent to the backend in plaintext. The composer checks the 40,000-character plaintext limit before encryption. The backend validates the final opaque payload size; failed sends preserve the outgoing text and attachment references in the outbox.

The provider defines the format; library versions belong to [package.json](../packages/web/package.json) and the lockfile.

- Message envelopes are random salt32 + ChaCha20-Poly1305 ciphertext/tag16, without a magic prefix or framing-version byte. The reader supports only this format; previous test messages are not migrated. HKDF-SHA256 derives a separate key32 from `GroupKey`, the salt, and the UTF-8 JSON array `["workspace-chat-crypto-v1", "message", streamUuid, keyUuid]`. The nonce is 12 zero bytes; each operation uses a fresh salt and derived key. AAD consists of the array's bytes followed by the salt.
- Grant: `WSCG` + version byte `1` + HPKE `enc32` + ciphertext48 containing `GroupKey` and the tag. HPKE Base uses DHKEM(X25519, HKDF-SHA256), HKDF-SHA256, and ChaCha20-Poly1305. `info` is UTF-8 JSON `["workspace-chat-crypto-v1", "grant", streamUuid, keyUuid, requestMessageUuid, senderDeviceId, recipientDeviceId]`; AAD consists of `info` followed by magic/version and the request's public key bytes.

This is a client format built on library primitives. Topic, author, local owner, and runtime generation are not part of the message's cryptographic context. Format changes require an explicit compatibility decision for persisted history.

## Storage and recovery

Secrets are stored separately from the message cache in IndexedDB `workspace-chat-secrets-v1`. A key address includes owner, device, stream, and key UUID; runtime generation guards live operations rather than forming part of the durable address. Device ID and name are durable metadata; there is no permanent asymmetric device key pair.

The X25519 pair and canonical request UUID (`localRequestId`) are persisted before POST. The backend returns a public placement UUID, derived as UUIDv5(topic UUID, canonical UUID); this binds `requestMessageUuid` and is referenced by grants and rejections. Retrying always sends the canonical UUID again. Own history can restore an unbound request or repair an older canonical binding after checking its author, device, generation, and public key. Closing the page does not delete its secret, and there is no TTL. A verified grant atomically stores `GroupKey`, records a receipt, and deletes the private request key. A rejection completes only the corresponding request. The controller checks author, permissions, generation, request UUID, and recipient device; history and realtime messages can arrive repeatedly or out of order.

Creation and rotation use durable staging. The create dialog retains one encrypted creation intent and its prepared secret across retries, closure, and return to the same owner. After dispatch, retries reconcile a visible native stream owned by the current user with the exact prepared key UUID, then fetch its default topic, finalize the same staged secret, and retry invitations. Recovery scans all stream pages and checks owner/runtime validity after each request. Accepted bundles survive finalization or invitation failures. Changing the unresolved form does not authorize another POST; closing and reopening restores its original settings.

Native stream creation has no confirmed server idempotency contract. Once a creation POST may have been sent, an empty recovery result remains uncertain and the client does not replay the POST. The user can repeat the recovery check; another intentional creation after success gets a separate attempt and key. The attempt is scoped to the dialog instance, while staged secrets remain durable and can be recovered when opening a matching stream after reload. This does not guarantee idempotence across page reloads, devices, or independent dialogs.

Inbound service messages load existing generation keys without creating persistent metadata for arbitrary UUIDs. Explicit local requests can initialize their chosen historical generation; verified grants still persist real key material atomically. Rotation retries retain their prepared secret and operation UUID. Historical messages always select their exact `key_uuid`. Async guards prevent an old owner/runtime from writing results into a new session. Persistent storage failure is not silently replaced with temporary storage.

## Security boundaries

- Attachment bytes and file metadata are stored without E2EE. Only their Markdown references inside the message are encrypted. The existing file API checks stream membership; E2EE does not protect the stored file from the server or storage access. The protected-chat label in the header includes a small information icon and explains this boundary and the need for a local chat key on hover or keyboard focus.
- Account authorship and roles are trusted as backend data. HPKE Base does not independently authenticate the sender; device ID is an addressing label, not proof of identity. A UUID does not independently verify the expected `GroupKey`.
- A shared key does not provide forward secrecy, cryptographic proof of an individual participant's authorship, or revocation of previously granted secrets. Rotation does not revoke access to old history or messages sent with an old key.
- The client does not serialize rotation across devices; live scope checks do not guarantee resolution of conflicts between devices. If an intermediate generation stops being current before the operation completes, its staged secret does not automatically become an available historical key.
- IndexedDB is not hardware-backed storage: code running in the origin and access to the device can expose secrets. Key export/import and backup are not implemented. Losing every copy of a key makes that generation's history inaccessible.
- Metadata, participants, and service messages remain visible to the server. Plaintext exists in presentation/editor memory and the owner-scoped in-memory outbox, and passes through the existing safe renderer; the canonical message store and durable message cache retain ciphertext. The outbox is not persisted across reloads. This flow does not provide encrypted push notifications or server-side plaintext search.
- Old mock envelopes are not migrated automatically. The DEV mock and insecure sandbox have been removed; only the [static UI preview](../packages/web/src/pages/encrypted-chat/encrypted-chat-preview.ui.tsx) remains.

## Verification and integration

Regression tests live alongside the provider, storage, controller, runtime, and session hook. The [Chromium E2E test](../e2e/workspace-local-keys.spec.ts) checks the local key manager using real client cryptography and a mock API. Commands are in [Project Facts](PROJECT_FACTS.md#verification); general security boundaries are in [Security architecture](SECURITY_ARCHITECTURE.md).

The client flow is implemented. Current automated checks do not confirm a complete live UUID-only flow with independent devices or a native Electron smoke test. Deployed backend support must be verified separately against the [contract sources](PROJECT_FACTS.md#backend-contracts): the local PR180 test environment is not a production migration.

Previous drafts and plans have been removed from active documentation; Git retains the history of decisions and local verification.
