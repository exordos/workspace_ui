# E2EE-чаты — рабочий черновик

Статус на 2026-10-02: выбраны симметричный `GroupKey` поколения, ChaCha20-Poly1305 для сообщений и HPKE для выдачи ключа отдельному запросу устройства. Подробные этапы и текущая готовность — в [плане реальной криптографии](E2EE_REAL_CRYPTO_PLAN.md). Семантика обязательного backend `public_key` чата ещё согласуется; нельзя передавать в нём секрет или фиктивный ключ. Связанная задача: [workspace_ui #177](https://github.com/exordos/workspace_ui/issues/177).

[Подготовка окончательного плана после компакта](E2EE_IMPLEMENTATION_PLANNING.md): макеты, принятые решения, открытые вопросы и работа оркестратора через субагентов.

## Цель

- Содержимое защищённого чата шифруется и расшифровывается на устройствах участников. Backend хранит и доставляет сообщения, но не получает открытый текст и секреты чата.
- Создатель чата становится первым администратором. По продуктовой политике ключи через приложение выдают администраторы чата; какие из существующих ролей сюда входят, ещё нужно уточнить.
- Секретный ключевой материал остаётся на устройствах. Каталог публичных ключей на backend пока не планируется. Шифрование push-уведомлений — отдельная задача.

## Признак E2EE у стрима

- В локальном PR180 стрим имеет `encryption: boolean`, задаваемый при создании и неизменяемый после него. У самого Workspace-стрима сейчас нет отдельного типа `group`: значение `group` есть только у `chat_type` элемента папки. Групповой разговор может быть приватным стримом с несколькими участниками; флаг `private` обозначает доступ к стриму, а не шифрование сообщений.
- Для encrypted стрима клиент показывает защищённый чат и запрещает обычные Markdown send/edit/forward; отправляет `e2ee` и служебные сообщения о ключах. Backend PR180 принимает все kind независимо от признака: клиентская защита от открытой отправки обязательна.
- Служебные сообщения видны backend. Поэтому режим обещает шифрование содержимого пользовательских сообщений, но не скрывает события о ключах и метаданные.
- Признак предлагается не менять после создания, чтобы не смешивать открытую и зашифрованную историю. Поддержку E2EE для существующих и прямых чатов нужно решить отдельно.

## Алгоритмы и протокол

- На каждое поколение создаётся случайный 32-байтный `GroupKey`. Сообщения шифруются ChaCha20-Poly1305; получив ключ, участник может читать и отправлять сообщения этого поколения.
- Для каждого нового `key_request` устройство создаёт отдельную пару X25519, сохраняет приватный ключ до отправки запроса и использует её для HPKE DHKEM(X25519, HKDF-SHA256)/HKDF-SHA256/ChaCha20-Poly1305. Администратор шифрует `GroupKey` для публичного ключа этого запроса. Постоянной пары устройства нет.
- После проверки ответа и устойчивого сохранения `GroupKey` приватный ключ запроса удаляется в одной транзакции. Проверенный отказ завершает только соответствующий запрос. TTL не вводим; закрытие страницы и перезагрузка не удаляют pending secret.
- HPKE Base не удостоверяет отправителя: авторству аккаунта доверяем по backend, права выдачи проверяет клиент. Доставка администратором без запроса устройства не предусмотрена; клиент может инициировать запрос автоматически позднее.
- Nonce сообщений имеет 12 байт. Для каждого сообщения из `GroupKey` через HKDF-SHA256 и свежий случайный 32-байтный salt выводится отдельный message key, используемый один раз с нулевым nonce. Это приложение поверх стандартных примитивов, не XChaCha и не random 96-bit nonce под неизменным общим ключом. Подробности контекста/envelope закреплены в [новом плане](E2EE_REAL_CRYPTO_PLAN.md).
- Эта модель не даёт forward secrecy для сохранённой истории при утечке `GroupKey`. MLS/ratchet потребуют другого lifecycle и остаются отдельной архитектурной задачей.

## Контракт провайдера и хранение ключей

- [ChatCryptoProvider](../packages/web/src/entities/messenger/chat-crypto-provider.types.ts) отделяет `ChatCryptoGroupKey`, request `ChatCryptoKeyPair` и `ChatCryptoKeyFingerprint`. Он создаёт ключи, шифрует сообщения и выдачи; не проверяет роли, не выполняет API-запросы и не сохраняет секреты.

  | `kind`          | Операция провайдера                             | Логика чата                                                                                 |
  | --------------- | ----------------------------------------------- | ------------------------------------------------------------------------------------------- |
  | `e2ee`          | `encryptMessage` / `decryptMessage`             | Получить `GroupKey` поколения; ciphertext в API, plaintext только в presentation            |
  | `key_request`   | `createRequestKeyPair` для нового запроса       | Сохранить pair до POST; retry того же pending request использует сохранённую pair           |
  | `key_grant`     | `encryptGroupKeyGrant` / `decryptGroupKeyGrant` | Проверить права, correlation и fingerprint; атомарно сохранить key и удалить request secret |
  | `key_announced` | `createGroupKey` + `fingerprintGroupKey`        | Объявить публичные metadata после согласования legacy `public_key` mapping                  |
  | `key_reject`    | Не требуется                                    | Проверить автора/права/correlation; завершить только свой запрос                            |

- Внутренние `{ bytes: Uint8Array }` не добавляют отдельное поле backend. [Payload adapter](../packages/web/src/entities/messenger/chat-e2ee-payload-adapters.lib.ts) использует обычный padded Base64 для `content` и request `public_key`, одинаково для REST/history/realtime. Формат бинарного envelope принадлежит клиенту; backend version/suite поля не добавляются.
- Симметричный ключ не имеет публичной половины. PR180 требует `current_encryption_key.public_key` и `key_announced.public_key`; предложение использовать domain-separated fingerprint в этом поле меняет семантику API и требует явного решения пользователя. До него working create/announce не подключают real provider.
- [ChatKeyStorage](../packages/web/src/entities/messenger/chat-key-storage.types.ts) хранит устойчивые device labels, group keys/fingerprints, отдельные pending request pairs и terminal receipts. [IndexedDB storage](../packages/web/src/entities/messenger/chat-key-storage-idb.lib.ts) находится отдельно от message cache. Owner/device/stream/key образуют durable address; runtime generation используется только для проверки live callbacks.
- Request UUID можно задать до POST через существующий optional `uuid` API. Pair и UUID сохраняются до dispatch; ответ проверяется на точное совпадение. Ambiguous timeout сохраняет secret; история помогает проверить доставку, а не создавать новые пары вслепую.
- Однотипные повторные user actions возобновляют старейший pending request; все устойчивые запросы, включая появившиеся параллельно в разных вкладках, могут принять свой ответ. Atomic receipt не позволяет гонке grant/reject удалить другой secret или откатить доступ.
- Provider/library и durable storage foundation реализуются по новому плану. До интеграционной проверки обычного UI это не означает, что рабочий чат уже использует настоящую криптографию. Legacy mock fixtures не превращаются в защищённые сообщения и не мигрируются автоматически.

## Сообщения и поколения ключей

- На текущем этапе опираемся на стандартную валидацию backend API. Дополнительные ограничения длины и отдельные правила валидации для `device_name`, `device_id`, `public_key` и зашифрованного `content` сейчас не проектируем. Это не блокирует интерфейс провайдера и каркас клиентской логики.
- Обычный payload сейчас имеет вид `{ "kind": "markdown", "content": "..." }`. Добавляем пять `kind`: `e2ee`, `key_request`, `key_grant`, `key_announced` и `key_reject`. У каждого своя структура payload:

  ```json
  {
    "kind": "e2ee",
    "key_uuid": "<uuid ключа>",
    "content": "<ChaCha20-Poly1305 envelope сообщения, base64>"
  }
  ```

  ```json
  {
    "kind": "key_request",
    "key_uuid": "<uuid ключа>",
    "device_id": "<строковый ID запрашивающего устройства>",
    "device_name": "<читаемое имя устройства, например MacBook или iPhone 16>",
    "public_key": "<публичный X25519 ключ отдельного запроса, base64>"
  }
  ```

  ```json
  {
    "kind": "key_grant",
    "key_uuid": "<uuid ключа>",
    "request_message_uuid": "<uuid запроса>",
    "sender_device_id": "<строковый ID устройства, выдавшего ключ>",
    "recipient_device_id": "<строковый ID устройства получателя>",
    "content": "<HPKE-конверт с GroupKey, base64>"
  }
  ```

  ```json
  {
    "kind": "key_announced",
    "key_uuid": "<uuid нового ключа>",
    "public_key": "<legacy public_key: семантика metadata поколения согласуется>"
  }
  ```

  ```json
  {
    "kind": "key_reject",
    "key_uuid": "<uuid запрошенного ключа>",
    "request_message_uuid": "<uuid отклонённого запроса>",
    "sender_device_id": "<строковый ID устройства, отклонившего запрос>",
    "recipient_device_id": "<строковый ID запрашивающего устройства>"
  }
  ```

  `e2ee.content` содержит binary envelope ChaCha20-Poly1305 со salt и ciphertext/tag; `key_grant.content` содержит HPKE `enc` и ciphertext/tag. Оба кодируются обычным Base64 с `=` padding без переносов. Это разные контейнеры с разделением назначения и привязкой к контексту; спецификация в новом плане. У остальных трёх `kind` поля `content` нет.

- Markdown и другие данные сообщения могут находиться внутри зашифрованного `content`. Backend не должен обрабатывать его как открытый Markdown.
- `key_uuid` обозначает поколение симметричного ключа. У каждого сообщения свой неизменный `key_uuid`; клиент выбирает `GroupKey` по owner/device/чат/поколение.
- Перевыпуск означает новый `GroupKey` и новый `key_uuid`, затем публичное объявление без секрета. Устройства запрашивают новый ключ сами. Реализация ротации не входит в текущую волну.
- Отправка требует локального `GroupKey`: возможности отправлять по одному публичному ключу больше нет. Backend PR180 сам не отклоняет старые поколения, поэтому выбор ключа отправки проверяет клиент.
- Перевыпуск не отзывает старый секрет: его обладатель сохраняет доступ к старой истории и сообщениям, которые продолжат шифровать старым ключом. Выдача старых поколений и строгий отзыв — отдельные решения.

## Менеджмент ключей

- Сохраняются симметричные ключи поколений и временные пары запросов, а не асимметричная пара чата или постоянная device pair.
- Backend хранит ciphertext и публичные metadata; `GroupKey` и приватные ключи запросов остаются в отдельном локальном хранилище.
- Утечка `GroupKey` открывает сообщения его поколения. Если все устройства и резервные копии такого секрета утрачены, соответствующую историю восстановить нельзя.

## Доступ и устройства

- Автор аккаунта и ID устройства — разные данные. Автору аккаунта из внешней структуры сообщения доверяем как данным backend. `device_id`, `sender_device_id` и `recipient_device_id` задаёт клиент; отдельного серверного реестра устройств, проверки этих ID или криптографической подписи устройства сейчас не предполагается. ID устройства — метка для адресации, а не доказательство авторства.
- Запрашивать ключ может любой пользователь, которому доступна отправка сообщений в этот чат; отдельная привилегия для `key_request` не требуется. Выдавать ключ через приложение могут только пользователи с разрешёнными правами чата, у которых локально есть нужный `GroupKey`. Базовое правило — выдача администраторами; точное соответствие существующих ролей и прав ещё нужно определить.
- Проверка права выдачи относится к логике чата на клиенте: до создания `key_grant` проверяются доступные права выдающего пользователя, а при принятии выдачи — автор аккаунта, его разрешённые права и связь с запросом. Одного `sender_device_id` для разрешения выдачи недостаточно. Это правило штатного клиентского сценария; серверное ограничение отправки `key_grant` пока не является требованием первой версии.
- Для первой версии нужны пять сценариев из payload выше: зашифрованное сообщение, объявление, запрос, выдача и отказ в выдаче ключа. При выдаче `GroupKey` передаётся устройству в HPKE-контейнере; отказ ссылается на запрос и не содержит ключа.
- Новое устройство того же пользователя не получает доступ автоматически: оно отправляет запрос со своим `device_id`. По выбранному правилу доступ выдаёт администратор после проверки нового устройства; точная проверка пока открыта.
- Генерация `GroupKey` и шифрование его выдачи происходят на клиенте. Проверка права выдачи должна выполняться в логике операции, а не только через скрытие кнопки.
- Любой обладатель `GroupKey` технически может скопировать его и передать вне приложения. Ролевое правило ограничивает штатную выдачу, но не предотвращает такую передачу.
- Вход в аккаунт подтверждает пользователя для backend, но не подтверждает владение уже допущенным устройством. Сам вход не должен автоматически выдавать новому устройству ключ чата; при выдаче нужно проверить привязку его публичного ключа к устройству и согласие доверенного участника.
- Выдача и отказ должны указывать `request_message_uuid`, `sender_device_id`, `recipient_device_id` и `key_uuid`. Автор сообщения уже известен из внешней структуры; `sender_device_id` уточняет его устройство, но сам по себе не доказывает, что сообщение отправлено именно с него. Доступ к новому ключу и к старой истории — разные решения; выдача одного ключа сама по себе не открывает сообщения других поколений.
- Запись о выдаче ещё не доказывает, что устройство успешно получило доступ; подтверждение получения и отображение статуса требуют отдельного решения.
- `device_id` — непрозрачная непустая строка, а не обязательный UUID или аппаратный ID. Она обозначает локальное устройство и сохраняется отдельно от кэша сообщений; пары относятся к отдельным запросам. Способ генерации, хранения и восстановления для Mobile, Electron и Web будет описан при реализации.
- `device_name` — читаемое имя запрашивающего устройства для отображения запроса доступа, например «MacBook» или «iPhone 16». Клиент хранит его как `deviceName` рядом с `deviceId` в `ChatDeviceIdentity`; API-адаптер передаёт его в `key_request` как `device_name`. Имя не является идентификатором или доказательством авторства; изменение имени не меняет ID и ключи устройства. Генерация имени и `device_id` остаётся отдельным открытым решением, вне криптографического провайдера и интерфейса хранения.
- При потере локальной идентичности устройство получает новый ID и запрашивает доступ заново. Если все устройства и резервные копии необходимых секретов утрачены, старую историю восстановить нельзя.

## Открытые решения

- Threat model, проверка поддержки выбранных алгоритмов на всех клиентах, внутренний формат зашифрованного конверта и backend-контракт; не реализовывать криптографию только по этому черновику.
- Backend подтверждает автора аккаунта; специальные права выдачи ключей проверяет клиент по доступным правам чата. Отдельная подпись устройства в текущую модель не входит. Серверные права выдачи могут появиться позднее и будут согласованы отдельной задачей; сейчас на них не опираемся.
- Публичный ключ отдельного запроса устройства передаётся в запросе и сохраняется backend в истории, без отдельного каталога. Он связывается с устойчивой request записью; TTL приватных ключей запросов сейчас отсутствует.
- Права на выпуск уведомлений, достоверность объявления и защита от поддельных/повторных объявлений. Уведомление раскрывает факт смены ключа, его идентификатор и публичные metadata; один лишь `kind: "key_announced"` не доказывает полномочия отправителя.
- Доступ нового участника к старой истории, отзыв устройства и восстановление. Строгий отзыв доступа к будущим сообщениям несовместим с неограниченной отправкой на старом ключе; если он потребуется, понадобится отдельное правило перехода.
- Права администраторов, шифрование вложений и поведение поиска, редактирования, реакций и уведомлений; окончательный контракт режима стрима.
- Локальный backend PR180 принимает все пять новых `kind`; его `encryption` metadata и обязательный `public_key` проверены. Финальный production контракт зависит от принятой серверной версии и решения о fingerprint.

## Исторические предложения backend, сверять с PR180

- Поддержать `markdown` и пять новых `kind` с отдельными схемами payload. У `key_request`, `key_reject` и `key_announced` нет обязательного `content`; `key_grant` содержит зашифрованный ключ в `content`.
- Добавить признак E2EE в создание и выдачу стрима, сохранять его и проверять допустимый `kind` сообщения по нему. Актуальный `key_uuid` backend не выбирает.
- Сохранять и возвращать поля новых payload через создание, историю и realtime. Не требовать глобального «текущего ключа» и не блокировать сообщения со старым `key_uuid`.
- Не обрабатывать пять новых `kind` как Markdown для упоминаний, текстового поиска и серверных резюме; поведение уведомлений и счётчиков определить отдельно.
- Сохранять клиентские ID устройств и адресацию выдачи как данные payload без отдельной серверной проверки устройства. Для `key_request` пока не вводить особую привилегию сверх обычного доступа к отправке сообщений в чат. Специальные серверные права для `key_grant` не являются требованием первой версии; при их появлении согласовать их отдельно. Правила редактирования/удаления служебных сообщений ещё нужно определить.
