# E2EE-чаты — рабочий черновик

Статус: согласованы общая асимметричная пара ключей на поколение чата и пять новых `kind` ниже. Проверка криптопротокола, backend API и ADR ещё не завершена. Связанная задача: [workspace_ui #177](https://github.com/exordos/workspace_ui/issues/177).

[Подготовка окончательного плана после компакта](E2EE_IMPLEMENTATION_PLANNING.md): макеты, принятые решения, открытые вопросы и работа оркестратора через субагентов.

## Цель

- Содержимое защищённого чата шифруется и расшифровывается на устройствах участников. Backend хранит и доставляет сообщения, но не получает открытый текст и секреты чата.
- Создатель чата становится первым администратором. По продуктовой политике ключи через приложение выдают администраторы чата; какие из существующих ролей сюда входят, ещё нужно уточнить.
- Секретный ключевой материал остаётся на устройствах. Каталог публичных ключей на backend пока не планируется. Шифрование push-уведомлений — отдельная задача.

## Признак E2EE у стрима

- Предложение: добавить к самому стриму `e2ee: boolean` (по умолчанию `false`, задаётся при создании). У самого Workspace-стрима сейчас нет отдельного типа `group`: значение `group` есть только у `chat_type` элемента папки. Групповой разговор может быть приватным стримом с несколькими участниками; флаг `private` обозначает доступ к стриму, а не шифрование сообщений.
- Для `e2ee`-стрима клиент показывает защищённый чат и отправляет `e2ee` либо служебные сообщения о ключах; backend отклоняет `markdown`. Для обычного стрима backend отклоняет `e2ee` и служебные сообщения о ключах.
- Служебные сообщения видны backend. Поэтому режим обещает шифрование содержимого пользовательских сообщений, но не скрывает события о ключах и метаданные.
- Признак предлагается не менять после создания, чтобы не смешивать открытую и зашифрованную историю. Поддержку E2EE для существующих и прямых чатов нужно решить отдельно.

## Алгоритмы и протокол

- Рабочая модель: на каждое поколение чата устройство создаёт пару `chat_public` / `chat_private`. Сообщения шифруются для `chat_public`; устройство с `chat_private` может их читать. Для шифрования рассматриваем [HPKE](https://www.rfc-editor.org/rfc/rfc9180.html) с X25519, HKDF-SHA256 и ChaCha20-Poly1305 внутри. Это асимметричная схема на внешнем уровне; ChaCha20-Poly1305 внутри неё остаётся симметричным шифром. Выбор реализации для всех клиентов нужно проверить.
- У каждого устройства есть отдельная пара ключей для получения доступа. Владелец `chat_private` шифрует его для публичного ключа запрашивающего устройства и отправляет в `key_grant`. Приватный ключ устройства отправителя не передаётся. Проверка личности устройств и правила выпуска ключей остаются нашему протоколу; HPKE в базовом режиме сам по себе не доказывает авторство отправителя.
- [MLS 1.0](https://www.rfc-editor.org/rfc/rfc9420.html) остаётся альтернативой, если потребуются защита старых шифртекстов после утечки текущего криптографического состояния, восстановление безопасности после компрометации при обновлении секретов и частые изменения больших групп. Одна сохраняемая пара ключей на поколение этих свойств не даёт.

## Контракт провайдера и хранение ключей

- Каркас опирается на модель «пара ключей на поколение чата + выдача ключа отдельному устройству». Выбор HPKE, набора алгоритмов и библиотеки остаётся открытым. Переход к другой модели управления ключами, например MLS, может потребовать изменения интерфейса и доменной логики.
- [ChatCryptoProvider](../packages/web/src/entities/messenger/chat-crypto-provider.types.ts) описывает создание пар ключей устройства и чата, шифрование/расшифровку сообщений и упаковку/получение ключа чата для устройства. Провайдер не проверяет роли, не отправляет сообщения и не сохраняет ключи. Доверенный backend подтверждает автора аккаунта и предоставляет права пользователя относительно чата; специальные права выдачи ключей пока проверяет клиент. Взлом аккаунта исключён из рассматриваемых сценариев.

  | `kind`          | Криптографическая операция                                                                                                       | Ответственность логики чата                                                                  |
  | --------------- | -------------------------------------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------- |
  | `e2ee`          | `encryptMessage` / `decryptMessage`                                                                                              | Выбрать поколение, получить ключ, отправить сообщение или показать расшифрованное содержимое |
  | `key_request`   | `createDeviceKeyPair`, только если локальной идентичности ещё нет; публичный ключ берётся из сохранённой идентичности устройства | Сформировать запрос с `device_id`, `device_name`, `key_uuid` и публичным ключом              |
  | `key_grant`     | `encryptChatKeyGrant` / `decryptChatKeyGrant`                                                                                    | Проверить права и связь с запросом; отправить выдачу или сохранить полученный ключ           |
  | `key_announced` | `createChatKeyPair` при выпуске поколения; получение объявления не требует расшифровки                                           | Отправить объявление или сохранить объявленный публичный ключ                                |
  | `key_reject`    | Криптографическая операция не требуется                                                                                          | Проверить автора/права и связь с запросом; отправить отказ или обновить состояние доступа    |

- Все криптографические операции асинхронны и возвращают результат либо явную причину отказа. Публичные ключи и контейнеры содержат только непрозрачные байты. Это внутренние типы приложения; поле `bytes` не передаётся в backend как отдельное поле payload.
- При интеграции с API нужен отдельный адаптер сериализации: для `e2ee` и `key_grant` он преобразует `ChatCryptoEnvelope.bytes` в обычный Base64 с `=` padding и записывает строку в `payload.content`. При получении из истории, ответа API или realtime адаптер декодирует `content` в `{ bytes: Uint8Array }` до вызова провайдера. Для `key_request` и `key_announced` аналогичное преобразование связывает `ChatCryptoPublicKey.bytes` с `payload.public_key`; у `key_reject` криптографических байтов нет. Провайдер работает с байтами и не отвечает за JSON/Base64. Дополнительные заголовки версии или схемы не добавляются.
- При реализации адаптера проверить двустороннее преобразование без потери байтов, отказ при некорректном Base64 и одинаковую обработку REST и realtime. Это требования к будущей реализации; сейчас адаптер ещё не добавлен. Base64 уже выбран; точный бинарный формат контейнера и окончательное согласование backend-контракта остаются открытыми.
- Контекст сообщения связывает контейнер со стримом и поколением ключа. Для выдачи добавляются UUID запроса и ID обоих устройств. Реализация обязана криптографически привязать контекст к контейнеру, разделить операции сообщения и выдачи ключа и при получении выдачи проверить соответствие приватного ключа ожидаемому публичному ключу чата. Кодирование контекста и защита от повторной доставки будут определены отдельно.
- Представление приватного ключа задано параметром типа: библиотека может использовать байты или собственный объект/дескриптор. Общий код не требует открытого экспорта секрета; перенос ключа происходит внутри операции выдачи. Ключи чата должны поддерживать такую передачу; несовместимая реализация возвращает `key-not-transferable`.
- [ChatKeyStorage](../packages/web/src/entities/messenger/chat-key-storage.types.ts) — отдельный контракт хранения идентичности устройства и ключей поколений. Данные разделяются по существующему `WorkspaceRuntimeOwner`, устройству, стриму и `keyUuid`; `runtimeGeneration` не входит в постоянный адрес. Публичный ключ можно хранить без приватного; обновление публичных данных не должно стирать уже полученный секрет. Представление приватных ключей и способ их постоянного хранения согласуются адаптерами провайдера и хранилища. Идентичность пока ограничена runtime owner; повторное использование между проектами требует отдельного решения.
- Доменный слой проверяет актуальность runtime после асинхронных операций, до применения результата в store или записи ключей. Хранилище должно сохранять идентичность устройства независимо от очистки кэша сообщений. Замена идентичности и удаление секретов требуют явного сценария, а не обычной очистки кэша.
- Версионирование и обозначение криптографической схемы отложены. Сейчас не добавляем соответствующие поля backend и не упаковываем такие метаданные внутрь `content` или `public_key`. Провайдер выбирается при сборке приложения, без автоматического определения схемы по данным. Замена библиотеки должна сохранять совместимость с существующими ключами и контейнерами; переход на несовместимый формат и чтение старой истории требуют отдельного решения.
- На этом этапе добавлены только интерфейсы. Тестовый провайдер допустим для тестов и локального стенда; в обычной сборке отсутствие настоящего провайдера должно запрещать отправку E2EE. UI, backend, криптография и постоянное хранение ещё не подключены.

## Сообщения и поколения ключей

- На текущем этапе опираемся на стандартную валидацию backend API. Дополнительные ограничения длины и отдельные правила валидации для `device_name`, `device_id`, `public_key` и зашифрованного `content` сейчас не проектируем. Это не блокирует интерфейс провайдера и каркас клиентской логики.
- Обычный payload сейчас имеет вид `{ "kind": "markdown", "content": "..." }`. Добавляем пять `kind`: `e2ee`, `key_request`, `key_grant`, `key_announced` и `key_reject`. У каждого своя структура payload:

  ```json
  {
    "kind": "e2ee",
    "key_uuid": "<uuid ключа>",
    "content": "<HPKE-конверт для публичного ключа чата, base64>"
  }
  ```

  ```json
  {
    "kind": "key_request",
    "key_uuid": "<uuid ключа>",
    "device_id": "<строковый ID запрашивающего устройства>",
    "device_name": "<читаемое имя устройства, например MacBook или iPhone 16>",
    "public_key": "<публичный ключ устройства base64>"
  }
  ```

  ```json
  {
    "kind": "key_grant",
    "key_uuid": "<uuid ключа>",
    "request_message_uuid": "<uuid запроса>",
    "sender_device_id": "<строковый ID устройства, выдавшего ключ>",
    "recipient_device_id": "<строковый ID устройства получателя>",
    "content": "<HPKE-конверт с приватным ключом чата, base64>"
  }
  ```

  ```json
  {
    "kind": "key_announced",
    "key_uuid": "<uuid нового ключа>",
    "public_key": "<публичный ключ чата base64>"
  }
  ```

  ```json
  {
    "kind": "key_reject",
    "key_uuid": "<uuid запрошенного ключа>",
    "request_message_uuid": "<uuid отклонённого запроса>",
    "sender_device_id": "<строковый ID устройства, отклонившего запрос>",
    "recipient_device_id": "<строковый ID запрашивающего устройства>"
  }
  ```

  Оба `content` содержат две части результата HPKE: публичный компонент `enc` и шифртекст с тегом проверки. Это одно поле JSON, но внутри нужно однозначно разделить части; для выбранного X25519 возможен формат `base64(enc[32 байта] || ciphertext)`. Для всех бинарных полей используем обычный Base64 с `=` padding (дополнением) и без переносов строк. Привязку к ID чата, ключа и адресата ещё нужно определить. У `key_request`, `key_reject` и `key_announced` поля `content` нет.

- Markdown и другие данные сообщения могут находиться внутри зашифрованного `content`. Backend не должен обрабатывать его как открытый Markdown.
- `key_uuid` обозначает поколение пары ключей чата (прежнюю «эпоху»). У каждого сообщения свой неизменный `key_uuid`; клиент ищет соответствующий публичный или приватный ключ по паре «чат + key_uuid». Порядковый номер эпохи и единый «текущий ключ» на backend не нужны.
- «Перевыпустить ключ» означает локально создать новую пару с новым `key_uuid` и отправить открытое сообщение `key_announced` с публичным ключом чата **без приватного ключа**. Клиент без приватного ключа предлагает запросить доступ.
- Отправитель выбирает поколение ключа: публичный ключ позволяет отправить сообщение, а приватный — прочитать его. Поэтому обладатель только старого приватного ключа технически может отправить сообщение на новый публичный ключ и не суметь прочитать его сам; клиентское правило отправки ещё нужно определить. Сообщения со старым ключом по-прежнему можно отправлять и читать. Backend не синхронизирует переход и не отклоняет старый `key_uuid` только из-за выпуска нового.
- Следствие: перевыпуск в таком режиме **не отзывает** старый ключ. Его обладатель сохраняет доступ к старой истории и ко всем будущим сообщениям, которые кто-либо ещё зашифрует старым ключом. Выбор ключа по умолчанию, конкурирующие выпуски и индикацию «старого ключа» в UI нужно определить отдельно.

## Менеджмент ключей

- Разделяем пары ключей устройств (идентификация и получение доступа могут требовать разных пар) и пары ключей поколений чата. Одна общая неизменная пара на весь чат не предполагается.
- На каждом устройстве нужен локальный реестр «чат + key_uuid → публичный ключ и, если есть доступ, приватный ключ». Backend может видеть публичный `key_uuid` и публичный ключ чата в сообщениях, но не хранит приватные ключи чата или такой реестр.
- Приватный ключ чата позволяет повторно читать все сообщения, связанные с его `key_uuid`; его утечка открывает те же сообщения. Новому устройству старые приватные ключи можно выдавать отдельно. Если все устройства и резервные копии старых приватных ключей утрачены, соответствующая история недоступна.

## Доступ и устройства

- Автор аккаунта и ID устройства — разные данные. Автору аккаунта из внешней структуры сообщения доверяем как данным backend. `device_id`, `sender_device_id` и `recipient_device_id` задаёт клиент; отдельного серверного реестра устройств, проверки этих ID или криптографической подписи устройства сейчас не предполагается. ID устройства — метка для адресации, а не доказательство авторства.
- Запрашивать ключ может любой пользователь, которому доступна отправка сообщений в этот чат; отдельная привилегия для `key_request` не требуется. Выдавать ключ через приложение могут только пользователи с разрешёнными правами чата, у которых локально есть нужный приватный ключ. Базовое правило — выдача администраторами; точное соответствие существующих ролей и прав ещё нужно определить.
- Проверка права выдачи относится к логике чата на клиенте: до создания `key_grant` проверяются доступные права выдающего пользователя, а при принятии выдачи — автор аккаунта, его разрешённые права и связь с запросом. Одного `sender_device_id` для разрешения выдачи недостаточно. Это правило штатного клиентского сценария; серверное ограничение отправки `key_grant` пока не является требованием первой версии.
- Для первой версии нужны пять сценариев из payload выше: зашифрованное сообщение, объявление, запрос, выдача и отказ в выдаче ключа. При выдаче приватный ключ чата передаётся устройству в HPKE-контейнере; отказ ссылается на запрос и не содержит ключа.
- Новое устройство того же пользователя не получает доступ автоматически: оно отправляет запрос со своим `device_id`. По выбранному правилу доступ выдаёт администратор после проверки нового устройства; точная проверка пока открыта.
- Генерация пары ключей чата и шифрование выдаваемого приватного ключа происходят на клиенте. Проверка права выдачи должна выполняться в логике операции, а не только через скрытие кнопки.
- Любой обладатель приватного ключа чата технически может скопировать его и передать вне приложения. Ролевое правило ограничивает штатную выдачу, но не предотвращает такую передачу.
- Вход в аккаунт подтверждает пользователя для backend, но не подтверждает владение уже допущенным устройством. Сам вход не должен автоматически выдавать новому устройству ключ чата; при выдаче нужно проверить привязку его публичного ключа к устройству и согласие доверенного участника.
- Выдача и отказ должны указывать `request_message_uuid`, `sender_device_id`, `recipient_device_id` и `key_uuid`. Автор сообщения уже известен из внешней структуры; `sender_device_id` уточняет его устройство, но сам по себе не доказывает, что сообщение отправлено именно с него. Доступ к новому ключу и к старой истории — разные решения; выдача одного ключа сама по себе не открывает сообщения других поколений.
- Запись о выдаче ещё не доказывает, что устройство успешно получило доступ; подтверждение получения и отображение статуса требуют отдельного решения.
- `device_id` — непрозрачная непустая строка, а не обязательный UUID или аппаратный ID. Она обозначает локальную криптографическую идентичность и должна сохраняться вместе с её ключами, отдельно от кэша сообщений. Способ генерации, хранения и восстановления для Mobile, Electron и Web будет описан при реализации.
- `device_name` — читаемое имя запрашивающего устройства для отображения запроса доступа, например «MacBook» или «iPhone 16». Клиент хранит его как `deviceName` рядом с `deviceId` в `ChatDeviceIdentity`; API-адаптер передаёт его в `key_request` как `device_name`. Имя не является идентификатором или доказательством авторства; изменение имени не меняет ID и ключи устройства. Генерация имени и `device_id` остаётся отдельным открытым решением, вне криптографического провайдера и интерфейса хранения.
- При потере локальной идентичности устройство получает новый ID и запрашивает доступ заново. Если все устройства и резервные копии необходимых секретов утрачены, старую историю восстановить нельзя.

## Открытые решения

- Threat model, проверка поддержки выбранных алгоритмов на всех клиентах, внутренний формат зашифрованного конверта и backend-контракт; не реализовывать криптографию только по этому черновику.
- Backend подтверждает автора аккаунта; специальные права выдачи ключей проверяет клиент по доступным правам чата. Отдельная подпись устройства в текущую модель не входит. Серверные права выдачи могут появиться позднее и будут согласованы отдельной задачей; сейчас на них не опираемся.
- Публичный ключ нового устройства передаётся в запросе и сохраняется backend в истории, без отдельного каталога. Нужно определить проверку его привязки к устройству и срок хранения таких запросов.
- Права на выпуск уведомлений, достоверность объявления и защита от поддельных/повторных объявлений. Уведомление раскрывает факт смены ключа, его идентификатор и публичный ключ; один лишь `kind: "key_announced"` не доказывает полномочия отправителя.
- Доступ нового участника к старой истории, отзыв устройства и восстановление. Строгий отзыв доступа к будущим сообщениям несовместим с неограниченной отправкой на старом ключе; если он потребуется, понадобится отдельное правило перехода.
- Права администраторов, шифрование вложений и поведение поиска, редактирования, реакций и уведомлений; окончательный контракт режима стрима.
- Сейчас backend принимает только `markdown`; для пяти новых `kind` нужен новый контракт.

## Изменения backend для отдельной задачи

- Поддержать `markdown` и пять новых `kind` с отдельными схемами payload. У `key_request`, `key_reject` и `key_announced` нет обязательного `content`; `key_grant` содержит зашифрованный ключ в `content`.
- Добавить признак E2EE в создание и выдачу стрима, сохранять его и проверять допустимый `kind` сообщения по нему. Актуальный `key_uuid` backend не выбирает.
- Сохранять и возвращать поля новых payload через создание, историю и realtime. Не требовать глобального «текущего ключа» и не блокировать сообщения со старым `key_uuid`.
- Не обрабатывать пять новых `kind` как Markdown для упоминаний, текстового поиска и серверных резюме; поведение уведомлений и счётчиков определить отдельно.
- Сохранять клиентские ID устройств и адресацию выдачи как данные payload без отдельной серверной проверки устройства. Для `key_request` пока не вводить особую привилегию сверх обычного доступа к отправке сообщений в чат. Специальные серверные права для `key_grant` не являются требованием первой версии; при их появлении согласовать их отдельно. Правила редактирования/удаления служебных сообщений ещё нужно определить.
