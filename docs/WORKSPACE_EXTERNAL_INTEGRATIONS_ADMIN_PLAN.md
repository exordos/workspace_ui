# План административной панели внешних интеграций

Дата среза: 2026-07-24.

## Цель

Добавить во вкладку «Внешние аккаунты» отдельный вход в административные
настройки внешних интеграций.

Административная панель:

- не зависит от наличия у администратора личного аккаунта Zulip;
- управляет общей политикой провайдера в организации;
- доступна только при наличии соответствующих IAM-разрешений;
- не смешивается с формами подключения аккаунта и выбора чатов;
- открывается в отдельной модалке.

Первая версия поддерживает провайдер `zulip`, но названия типов и границы
модулей не должны мешать добавлению других провайдеров.

## Продуктовая граница

### Пользовательский уровень

Пользовательский внешний аккаунт содержит:

- адрес сервера Zulip;
- email и записываемый только один раз API key;
- глубину истории;
- проект назначения;
- состояние подключения;
- каталог и состояние синхронизации чатов.

### Административный уровень

Политика провайдера содержит:

- разрешена ли интеграция Zulip;
- аварийно ли она приостановлена во всей организации;
- максимум аккаунтов Zulip на одного пользователя;
- максимум выбранных чатов на один внешний аккаунт;
- максимальный размер передаваемого файла;
- метаданные собственного набора сертификатов центра сертификации;
- агрегированное техническое состояние аккаунтов, моста и операций.

Административная модалка не принимает `accountUuid` и не читает
`external-account` store.

Управление отдельными экземплярами моста не входит в первую версию. Это другая
административная сущность с отдельными разрешениями и необратимым действием
отзыва сертификата.

## Размещение и названия

Текущий раздел правого меню:

```text
Подключённые внешние аккаунты
```

переименовывается в:

```text
Внешние аккаунты
```

Внутри раскрытого раздела остаются:

1. действие «Подключить внешний аккаунт»;
2. список подключённых аккаунтов;
3. только для администратора — отдельное действие
   «Настройки интеграций».

Административное действие существует и при пустом списке пользовательских
аккаунтов. На странице `/services` его в первой версии не дублируем.

## API

Базовый путь:

```text
/api/workspace/v1/messenger
```

| Метод  | Путь                                                       | Назначение                          |
| ------ | ---------------------------------------------------------- | ----------------------------------- |
| `GET`  | `/external_provider_policies/zulip`                        | Политика и `ETag`                   |
| `PUT`  | `/external_provider_policies/zulip`                        | Полная замена политики с `If-Match` |
| `POST` | `/external_provider_policies/zulip/actions/suspend/invoke` | Аварийная остановка                 |
| `POST` | `/external_provider_policies/zulip/actions/resume/invoke`  | Возобновление                       |
| `GET`  | `/external_provider_health/zulip`                          | Агрегированное состояние            |

Политика:

```ts
interface ExternalProviderPolicyDto {
  uuid: string;
  created_at: string;
  updated_at: string;
  revision: number;
  provider: "zulip";
  enabled: boolean;
  emergency_suspended: boolean;
  limits: {
    max_accounts: number;
    max_selected_chats_per_account: number;
    max_file_bytes: number;
  };
  custom_ca_bundle: null | {
    uuid: string;
    generation: number;
    sha256: string;
    certificate_count: number;
  };
}
```

Состояние:

```ts
interface ExternalProviderHealthDto {
  provider: "zulip";
  status: "healthy" | "unavailable";
  account_counts: Record<string, number>;
  bridge_counts: Record<string, number>;
  operation_counts: Record<string, number>;
  metrics: Record<string, number>;
  updated_at: string;
}
```

В отличие от ветки Cassi, текущий backend не возвращает `chat_counts`.
Несуществующие показатели чатов, сообщений и пользователей нельзя подставлять
нулями.

## Доступ и права

Backend проверяет пять точных IAM-разрешений:

- `workspace.external_provider_policy.read`;
- `workspace.external_provider_policy.update`;
- `workspace.external_provider_policy.suspend`;
- `workspace.external_provider_policy.resume`;
- `workspace.external_provider_health.read`.

Роль администратора отдельного потока Messenger, старая роль Zulip, имя
пользователя и наличие подключённого аккаунта не являются источником права.

### Целевое решение

Workspace-сессия или отдельный endpoint возможностей отдаёт интерфейсу точный
список IAM-разрешений. Интерфейс отдельно вычисляет возможность:

- видеть административный вход;
- изменять политику;
- приостанавливать;
- возобновлять;
- видеть техническое состояние.

Backend остаётся окончательной точкой проверки каждого действия.

### Временное решение до появления списка прав

При раскрытии раздела «Внешние аккаунты» выполняется только:

```http
GET /external_provider_policies/zulip
```

- `200` подтверждает право чтения и разрешает показать кнопку;
- `401` или `403 + ExternalResourceForbiddenError` скрывает кнопку;
- сетевая ошибка или `5xx` не превращается в вывод «пользователь не
  администратор»: кнопка остаётся скрытой до успешной проверки, запрос можно
  повторить;
- `GET health` выполняется только после открытия модалки и не участвует в
  решении о показе кнопки.

Успешное чтение не доказывает наличие прав на изменение или аварийные действия.
Пока точные права не доступны интерфейсу, `403` от каждой команды
обрабатывается отдельно и не закрывает всю модалку.

## Структура модалки

Предлагаемое название:

```text
Настройки внешних интеграций
```

Подзаголовок объясняет область действия:

```text
Общие настройки Zulip для всех пользователей организации
```

### 1. Общее состояние

- провайдер Zulip;
- «Работает» / «Недоступен»;
- включена ли политика;
- действует ли аварийная остановка;
- время последнего обновления;
- отдельное действие «Обновить».

Ошибка загрузки состояния не блокирует редактирование уже загруженной
политики.

### 2. Доступность и лимиты

- переключатель «Разрешить интеграцию Zulip»;
- «Аккаунтов на пользователя»;
- «Чатов на внешний аккаунт»;
- «Максимальный размер файла».

Пределы backend:

| Поле                             | Минимум |   Максимум | Семантика нуля             |
| -------------------------------- | ------: | ---------: | -------------------------- |
| `max_accounts`                   |       0 |     100000 | новые аккаунты запрещены   |
| `max_selected_chats_per_account` |       0 |    1000000 | новый выбор чатов запрещён |
| `max_file_bytes`                 |       0 | 5368709120 | передача файлов отключена  |

Размер файла показывается в понятной единице, но в модели хранится в байтах,
чтобы открытие формы без изменений не меняло значение из backend.

Уменьшение лимитов не удаляет существующие аккаунты и чаты. Подсказки формы
должны явно это сообщать.

### 3. Собственный центр сертификации

В первой версии показываются только:

- установлен ли набор;
- количество сертификатов;
- отпечаток SHA-256;
- поколение набора.

Исходные сертификаты и закрытые ключи backend не возвращает.

Замена и удаление набора откладываются до исправления контракта. Нельзя
имитировать сохранение сертификата метаданными и нельзя молча отправлять
`custom_ca_bundle: null`.

### 4. Техническое состояние

Показываются только фактически доступные агрегаты:

- аккаунты по состояниям;
- экземпляры моста по состояниям;
- операции по состояниям;
- время снимка.

Известные статусы переводятся через `i18n`. Неизвестные ключи не становятся
непереведёнными основными подписями.

Текущий `metrics.queue_depth` считается по всем операциям, включая завершённые,
поэтому в первой версии его нельзя подписывать как точное число ожидающих
задач. Метрику лучше скрыть до уточнения backend-семантики.

### 5. Аварийное управление

Отдельная визуально опасная зона:

- «Приостановить интеграцию» при активном провайдере;
- «Возобновить интеграцию» при аварийной остановке;
- обязательное подтверждение остановки;
- явное предупреждение, что действие затронет всех пользователей организации;
- повторный запрос политики и состояния после команды.

Аварийное действие не сохраняет и не сбрасывает черновик лимитов.

## Загрузка и состояние

Административная политика не сохраняется в IndexedDB или `localStorage`.
Опасно показывать долговременно закешированные настройки как актуальные.

Используется только состояние в памяти:

- проверка доступа;
- снимок политики и `ETag`;
- черновик формы;
- снимок состояния;
- независимые статусы загрузки, сохранения и аварийного действия;
- ошибки каждого запроса.

На открытии политика загружается строго с сервера. Состояние загружается
отдельно и может обновляться вручную или ограниченным опросом только при
открытой модалке.

Все запросы:

- получают `AbortSignal`;
- привязаны к полному owner key;
- проверяют `runtimeGeneration` после каждого `await`;
- отменяются при закрытии, выходе, смене пользователя, организации или проекта;
- не применяют поздний ответ runtime A после перехода A → B → A.

## Сохранение и конфликты

`PUT` отправляется только с `If-Match`, полученным вместе с последним `GET`.

При `412 ExternalPreconditionFailedError`:

1. автоматического повтора записи нет;
2. локальный черновик сохраняется;
3. свежая политика загружается отдельно;
4. показывается сообщение об изменении другим администратором;
5. пользователь сам решает загрузить актуальные значения и повторить правку.

Отсутствующий `ETag` — ошибка контракта; синтезировать его из `revision`
интерфейс не должен.

После `suspend` и `resume` политика загружается заново, потому что эти команды
тоже увеличивают ревизию и делают старый `ETag` непригодным.

## Известные ограничения backend

### 1. Сохранение при установленном собственном CA

`PUT` требует полную модель с обязательным `custom_ca_bundle`. `GET` возвращает
только метаданные, а `PUT` принимает исходные PEM или `null`. Значения «оставить
как есть» нет.

До изменения backend:

- если собственного CA нет, политику можно сохранять с
  `custom_ca_bundle: null`;
- если CA установлен, сохранение `enabled` и лимитов блокируется с понятным
  объяснением;
- аварийные действия и чтение состояния остаются доступны.

Требуемое изменение backend: разрешить отсутствие `custom_ca_bundle` как
«не изменять» либо вынести замену и удаление сертификатов в отдельные действия.

### 2. Нет публичного списка прав

Текущий frontend не получает список IAM-разрешений. Проверочный `GET`
подтверждает только право чтения.

Желаемое изменение: добавить в достоверный Workspace bootstrap/session
действующие разрешения или серверные признаки `can_read`, `can_update`,
`can_suspend`, `can_resume`, `can_read_health`.

### 3. Ошибка при отсутствии активного моста

Изменение, остановка и возобновление политики требуют ровно один активный мост.
Сейчас отсутствие или несколько активных мостов может привести к `500`.

Желаемое изменение: типизированный `409` или `503` с безопасным кодом ошибки.
До этого интерфейс показывает общую ошибку действия и сохраняет черновик.

## Последовательная разбивка для агентов

### Задача 1. Контракт API

Результат:

- строгие DTO и guards по фактическому ответу backend;
- API чтения, сохранения, остановки, возобновления и состояния;
- сохранение `ETag`;
- `If-Match` только для `PUT`;
- поддержка `AbortSignal`;
- тесты URL, методов, тела, заголовков, `403`, `412` и ошибочного DTO.

Задача не меняет интерфейс.

### Задача 2. Проверка доступа и оркестрация состояния

Начинается после задачи 1.

Результат:

- временная проверка права чтения через `GET policy`;
- независимая загрузка policy и health;
- черновик формы;
- раздельные состояния load/save/action;
- защита owner/org/project/runtimeGeneration;
- отмена запросов;
- обработка A → B и A → B → A;
- конфликт без автоматической перезаписи;
- тесты поздних ответов и частичного отказа.

### Задача 3. Форма и модалка

Начинается после задачи 2.

Результат:

- отдельная адаптивная модалка;
- блоки состояния, доступности, лимитов, CA-метаданных и аварийного управления;
- перевод байтов в единицу отображения без изменения исходного значения;
- проверка числовых границ;
- безопасная блокировка сохранения при установленном CA;
- подтверждение аварийной остановки;
- доступность с клавиатуры и корректные роли;
- тесты основных, ошибочных и конфликтных состояний.

### Задача 4. Встраивание в правую панель

Начинается после задачи 3.

Результат:

- раздел переименован в «Внешние аккаунты»;
- административная кнопка не зависит от наличия аккаунтов;
- кнопка появляется только после подтверждённого доступа;
- обычный пользователь не видит кнопку;
- новая модалка открывается с текущим runtime;
- тексты добавлены в `ru` и `en`;
- обновлены тесты правого меню.

### Задача 5. Независимый обзор и общая проверка

Начинается после объединения задач 1–4.

Проверяется:

- отсутствие зависимости от `external-account`;
- отсутствие legacy Zulip API и ролей;
- отсутствие выдуманных health-полей;
- отсутствие утечки PEM, ключей и персональных данных;
- корректность `ETag` и конфликтов;
- stale-write safety;
- поведение без аккаунтов;
- поведение при частичных разрешениях;
- `vitest` затронутых модулей;
- `npm run typecheck`;
- `git diff --check`;
- `git status --short`.

## Что можно параллелить

Контракт API должен быть завершён первым.

После него визуальную форму и тестовые сценарии можно частично готовить
параллельно, но hook состояния и встраивание в правую панель лучше выполнять
последовательно: они используют общие типы доступа и открывают одну модалку.

Предпочтительная схема:

```text
API-контракт
      ↓
доступ и состояние
      ↓
форма и модалка
      ↓
правая панель и i18n
      ↓
независимый обзор
```

## Критерии готовности

- раздел называется «Внешние аккаунты»;
- обычный пользователь не видит административную кнопку;
- администратор видит кнопку даже без личного Zulip-аккаунта;
- модалка не принимает и не загружает внешний пользовательский аккаунт;
- policy и health могут завершиться независимо;
- изменение политики использует настоящий `ETag`;
- конфликт не перезаписывает изменения другого администратора;
- остановка требует подтверждения и затрагивает весь провайдер;
- установленный CA нельзя случайно удалить обычным сохранением;
- не показываются несуществующие показатели Cassi;
- поздние ответы другого runtime не меняют активный интерфейс;
- все новые тексты присутствуют на русском и английском.
