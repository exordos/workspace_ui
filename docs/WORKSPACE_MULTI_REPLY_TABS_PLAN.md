# План: несколько ответов в одном Workspace-сообщении через вкладки

Дата среза: 2026-07-14.

Документ фиксирует продуктовую модель и рабочее разбиение реализации на
саб-агентов. Это план, а не готовая реализация.

## Главное решение

Одно отправленное сообщение может содержать несколько последовательных пар
«цитата + ответ»:

```text
> цитата Алексея
ответ для Алексея

> цитата Марии
ответ для Марии
```

В интерфейсе каждая пара представлена отдельной вкладкой. Вкладка содержит
свою цитату и свой текст ответа. Поле ввода одно, но при переключении вкладки
оно показывает текст ответа активной вкладки.

Ключевое различие действий:

- **Ответить** заменяет цитату в активной вкладке и сохраняет её текст ответа.
- **Добавить ответ** создаёт новую вкладку с новой цитатой и пустым текстом.

Если активной сессии ещё нет, оба действия создают первую вкладку. После
добавления новая вкладка становится активной.

Новая вкладка всегда создаётся из конкретного исходного сообщения. Поэтому в
самих вкладках не будет кнопки `+ Добавить`: без выбранного сообщения она не
имеет однозначного действия. Для создания вкладки используется только пункт
**Добавить ответ** в меню конкретного сообщения.

Workspace API менять не нужно. На сервер уходит одно обычное Markdown-сообщение
с несколькими блоками цитирования. Отдельной серверной связи `reply_to` или
списка ответов в текущем контракте нет.

## Текущее состояние

Сейчас Workspace-чат хранит только одну цитату:

- `replyQuote` находится в состоянии `ChatPageWorkspace`;
- обработчик ответа создаёт новый объект и заменяет предыдущий;
- `MessageComposer` показывает одну плашку ответа;
- `buildOutgoingMessageBody` добавляет одну цитату перед текстом пользователя;
- при отправке `sendMessengerMessage` получает уже готовый Markdown-текст.

`urn:message` и Markdown-блок с цитатой.

## Цель первой реализации

Сделать рабочий механизм, в котором пользователь может:

1. ответить на первое сообщение;
2. написать текст ответа;
3. добавить второе сообщение в новую вкладку;
4. написать отдельный текст для второй вкладки;
5. переключиться обратно и изменить первый ответ;
6. удалить вкладку крестиком;
7. изменить порядок вкладок;
8. увидеть итоговый порядок и тексты в предварительном просмотре;
9. отправить все пары одним Workspace-сообщением.

## Не входит в первую реализацию

- отдельный режим «один общий ответ под всеми цитатами»;
- отдельное серверное поле для связей между сообщениями;
- треды и ветки сообщений;
- сложная визуальная полировка вкладок;
- перетаскивание вкладок мышью и жестами;
- сохранение сессии вкладок в черновике;
- восстановление вкладок при редактировании уже отправленного составного
  сообщения;
- массовое выделение сообщений для создания вкладок одним действием;
- изменение старого Zulip-пути за пределами необходимых общих контрактов.

Общий ответ технически можно получить без отдельного режима: оставить ответы
промежуточных вкладок пустыми и написать текст в последней вкладке. Пустые
ответы не должны создавать лишние пустые абзацы в итоговом Markdown.

## Целевая модель данных

Для первой версии достаточно состояния на уровне Workspace-страницы или
Workspace-фичи. Глобальный Zustand-store не нужен: сессия относится к текущему
чату и должна очищаться при уходе из него.

```ts
interface WorkspaceReplyTab {
  id: string;
  messageUuid: string;
  senderUuid: string;
  senderName: string;
  quotedContent: string;
  selectedText?: string;
  createdAt: string;
  answer: string;
}

interface WorkspaceReplySession {
  tabs: WorkspaceReplyTab[];
  activeTabId: string | null;
}
```

Правила модели:

- `id` — стабильный локальный идентификатор вкладки, не индекс массива;
- `messageUuid` — идентификатор исходного Workspace-сообщения;
- `quotedContent` — снимок текста на момент выбора;
- `selectedText` — необязательный выделенный фрагмент, если пользователь
  отвечал на выделение;
- `answer` — отдельный текст ответа этой вкладки;
- `createdAt` нужен для начального хронологического порядка;
- замена цитаты не меняет `id`, позицию и `answer` активной вкладки;
- добавление создаёт новый `id` и пустой `answer`;
- перемещение меняет только порядок вкладок, а не содержимое их пар.

Текст в поле ввода является проекцией `answer` активной вкладки. Источником
правды для всех ответов остаётся массив вкладок.

## Переходы состояния

### Ответить

Если сессии нет:

```text
пусто -> одна вкладка с выбранной цитатой и пустым ответом
```

Если активная вкладка есть:

```text
activeTab.quote = новое сообщение
activeTab.answer сохраняется
activeTab.id сохраняется
activeTab.position сохраняется
```

Нажатие **Ответить** не добавляет новую вкладку и не очищает уже набранный
текст. Это намеренная семантика замены цитаты в текущем контексте.

### Добавить ответ

Если сессии нет, создаётся первая вкладка.

Если сессия уже есть:

```text
новая вкладка = новая цитата + пустой answer
activeTabId = новая вкладка
```

Новая вкладка добавляется в конец текущего порядка. При начальном создании
нескольких вкладок из набора сообщений допускается хронологическая сортировка.
После ручного изменения порядка он становится пользовательским и не должен
тихо пересортировываться.

### Переключение вкладки

При переключении:

1. текущее значение поля уже сохранено в `answer` активной вкладки;
2. выбирается новая вкладка;
3. в поле ввода подставляется её `answer`;
4. фокус остаётся в поле ввода;
5. режим предварительного просмотра возвращается в режим написания, если это
   необходимо текущим поведением композера.

### Удаление вкладки

- крестик удаляет только выбранную вкладку;
- при удалении активной выбирается ближайшая оставшаяся вкладка;
- если удалена последняя вкладка, сессия ответа закрывается;
- закрытие сессии очищает активный контекст ответа, но не меняет обычный
  черновик чата.

### Перемещение вкладок

Для первой версии достаточно команд «влево» и «вправо» или другой простой
реализации, которая меняет массив `tabs`. Визуальное перетаскивание оставить
отдельной задачей UX.

При перемещении вкладка переносится вместе со своим ответом. Отправка и
предварительный просмотр используют именно текущий порядок `tabs`.

## Сборка сообщения

Нужна чистая функция, которая принимает вкладки и возвращает итоговый Markdown:

```text
for tab in tabs:
  append quote block for tab
  append tab.answer when it is not empty
```

Для каждого элемента:

1. строится Workspace-заголовок с автором и ссылкой на исходное сообщение;
2. содержимое цитаты помещается в Markdown quote block;
3. добавляется текст `answer` этой вкладки;
4. между парами сохраняется читаемый разделитель.

Пустая вкладка с цитатой допустима. Если у нескольких вкладок нет ответа,
цитаты всё равно остаются в сообщении, но лишние пустые строки не добавляются.

Если все ответы пустые, отправка должна оставаться недоступной по текущему
правилу пустого композера.

Собранная строка передаётся в существующий Workspace-путь отправки. Backend,
realtime, cache и формат исходящего сообщения менять не нужно.

## Интеграция с композером

### Что должно остаться в композере

- одно поле ввода;
- обычное форматирование текста;
- упоминания, файлы и остальные уже поддержанные действия;
- текущий режим `write/preview`;
- отправка текущего текста активной вкладки.

### Что не должно храниться в композере

- список всех вкладок;
- выбранные исходные сообщения;
- порядок вкладок;
- логика добавления и удаления вкладок;
- обращение к Workspace message store для поиска цитат.

Состояние вкладок и операции над ним принадлежат странице или отдельной
Workspace-фиче. Композер получает текущий текст активной вкладки и сообщает об
изменениях через существующий `onValueChange` или уточнённый контролируемый
контракт.

Текущий `initialValue` уже умеет обновлять локальное значение композера при
смене входного значения. Это можно использовать как переходный механизм, но
нужно отдельно проверить отсутствие потери текста при быстром переключении
вкладок.

### Предварительный просмотр

Обычный предварительный просмотр композера должен получать полное собранное
тело всех вкладок, а не только текст активной вкладки. Для этого нужен один из
вариантов:

1. передать в композер готовое Workspace preview body;
2. передать функцию сборки preview body;
3. вынести Workspace preview рядом с вкладками, сохранив общий переключатель
   `write/preview`.

Предпочтительный вариант — небольшой необязательный контракт готового
preview body. Он не заставляет общий композер знать о модели вкладок и сохраняет
старое поведение для других путей.

## UI первой версии

Нужен отдельный небольшой компонент Workspace-вкладок, расположенный рядом с
полем ввода:

```text
[ Алексей × ] [ Мария × ]
```

Минимальные свойства компонента:

- список вкладок;
- активная вкладка;
- переключение;
- удаление вкладки крестиком;
- перемещение влево/вправо;
- доступное имя вкладки для клавиатуры и экранного диктора.

Вкладка должна показывать хотя бы имя автора и короткое отличие цитаты.
Добавление новой вкладки выполняется только из меню сообщения через действие
**Добавить ответ**. Компонент вкладок не открывает самостоятельный выбор
сообщения.
Детальные правила ширины, переполнения, мобильного отображения и анимаций
вынести в отдельную UX-задачу.

## Разбиение на саб-агентов

Главный агент выступает оркестратором: не делает крупную реализацию сам,
раздаёт независимые зоны, проверяет пересечения, принимает отчёты и запускает
проверку после каждой фазы.

Каждый саб-агент в отчёте указывает:

- изменённые файлы;
- что реализовано;
- какие тесты запущены;
- какие решения остались незафиксированными;
- какие файлы потребуются следующей фазе.

Саб-агенты не должны править файлы за пределами своей зоны. Если требуется
общий файл другой фазы, агент оставляет передачу, а не меняет чужой участок.

Проверить:

- текущие вызовы `onReplyMessage`;
- место формирования `replyQuote`;
- как `MessageComposer` синхронизирует `initialValue` и `onValueChange`;
- как строится тело отправки и preview body;
- где включён режим редактирования;
- какие тесты уже покрывают ответ, preview и отправку;
- текущий Workspace backend contract для Markdown-сообщения.

Файлы только для чтения:

Выход:

- список потенциально конфликтующих файлов;
- рекомендация по preview contract;
- список узких тестов для следующих фаз.

Параллельность: запускается первой и отдельно.

- переключение активной вкладки;
- удаление вкладки;

Реализовать:

- заменить одиночный Workspace `replyQuote` на `WorkspaceReplySession`;
- оставить старый путь ответа отдельно, если он используется вне Workspace;
- разделить обработчики `handleReplyMessage` и `handleAddReplyMessage`;
- при `Ответить` заменять цитату активной вкладки;
- при `Добавить ответ` добавлять новую вкладку;
- передавать в композер текст активной вкладки;
- сохранять `onValueChange` в активную вкладку;
- при отправке собирать весь Markdown из вкладок;
- очищать сессию после успешной отправки;
- очищать или закрывать сессию при переходе в редактирование;
- очищать сессию при смене чата или уходе со страницы;
- подключить вкладки рядом с полем ввода;
- передавать в preview полное собранное тело.

Отдельно проверить сценарий:

1. вкладка А содержит ответ А;
2. добавлена вкладка Б и написан ответ Б;
3. нажато **Ответить** на сообщение В при активной вкладке Б;
4. вкладка Б теперь цитирует В, но сохраняет ответ Б;
5. вкладка А по-прежнему содержит цитату и ответ А.

Зависимости: Фазы 1, 2 и 3. Эта фаза должна идти после стабилизации их
контрактов, потому что затрагивает страницу и отправку.

### Фаза 5. Действия в меню сообщения и переводы

Агент: `workspace-reply-actions-i18n`.

Зона изменений:

- `packages/web/src/widgets/workspace-message-list/workspace-message-bubble-menu.ui.tsx`;
- связанные типы и тесты меню;
- `packages/web/src/i18n/en.json`;
- `packages/web/src/i18n/ru.json`.

Реализовать:

- оставить действие **Ответить**;
- добавить действие **Добавить ответ**;
- передавать выбранное сообщение и выделенный текст в правильный обработчик;
- проверить, что при активной сессии два действия не перепутаны;
- не добавлять кнопку создания вкладки в панели вкладок;
- добавить русские и английские подписи и доступные названия.

Если меню требует изменения общей структуры, агент не меняет страницу чата
самостоятельно, а передаёт точный контракт Фазе 4.

Параллельность: после стабилизации callback-контрактов, может идти параллельно
с частью Фазы 4, если файлы страницы и меню не пересекаются.

### Фаза 7. Отдельный обзор

Агент: `workspace-reply-review`.

Проверить отдельно:

- не очищается ли ответ при действии **Ответить**;
- не создаёт ли **Ответить** новую вкладку вместо замены;
- не заменяет ли **Добавить ответ** активную вкладку;
- не перепутаны ли цитата и ответ при перестановке;
- не отправляется ли только активная вкладка;
- не показывает ли preview только активный ответ;
- не теряется ли текст при смене `initialValue`;
- не остаётся ли старый Workspace `replyQuote`-путь в активной отправке;
- не появились ли лишние зависимости от legacy Zulip-кода;
- не нарушены ли правила FSD и импортов без barrel-файлов.

Если найдены проблемы, обзорный агент сначала составляет короткий список
исправлений по приоритету, а затем передаёт их оркестратору для отдельной
исправительной фазы. Он не расширяет задачу самостоятельным UX-редизайном.

## Порядок запуска саб-агентов

```text
Фаза 0: карта контрактов
          |
          v
Фаза 1: модель и сборщик
          |
      +---+---+
      |       |
      v       v
Фаза 2   Фаза 3
      |       |
      +---+---+
          |
          v
Фаза 4: подключение страницы
          |
      +---+---+
      |       |
      v       v
Фаза 5   Фаза 6
      +---+---+
          |
          v

```

Правило параллельности: одновременно запускать только агентов, которые не
редактируют один файл. Фазы 2 и 3 можно вести параллельно после Фазы 1. Фазы
4 и 5 можно частично вести параллельно только при строгом разделении страницы
и меню.

## Критерии готовности

Задача считается выполненной, когда:

- у пользователя есть отдельные вкладки для отдельных ответов;
- **Ответить** заменяет цитату активной вкладки и сохраняет её ответ;
- **Добавить ответ** создаёт новую вкладку;
- у каждой вкладки свой независимый текст;
- вкладки удаляются крестиком;
- порядок вкладок влияет на итоговое сообщение;
- текст не теряется при переключении;
- preview показывает полный итоговый текст;
- отправка создаёт одно Workspace-сообщение с правильными парами;
- обычная отправка без вкладок продолжает работать;
- backend contract и Workspace UUID-модель не изменены;
- тесты модели, UI, страницы и типы проходят.

## Последующие UX-задачи

После проверки механизма отдельным планом можно заняться:

- видом вкладок на узком экране;
- длинными именами и переполнением;
- отображением выделенного текста;
- перетаскиванием;
- быстрым добавлением из списка сообщений;
- подтверждением замены цитаты, если в активной вкладке уже набран текст;
- сохранением вкладок в черновике;
- красивым режимом общего ответа;
- восстановлением структуры вкладок при редактировании отправленного
  сообщения.
