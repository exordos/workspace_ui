# E2EE: подготовка окончательного плана после компакта

Дата: 2026-10-01. Статус: записка для продолжения работы, не окончательный план реализации.

Продолжение: [этапы реализации и первый каркас](E2EE_IMPLEMENTATION_PLAN.md). При дальнейшей работе учитывать последнее требование пользователя: максимально переиспользовать существующие UI-компоненты, Pixel Perfect не нужен.

## Задача следующего запуска

Пользователь попросил сначала подготовить план составления плана. После компакта главный агент должен прочитать эту записку, выступить оркестратором и работать через субагентов. Сначала изучить макеты и текущий код, закрыть необходимые вопросы и составить окончательный план. Реализацию выполнять в следующей согласованной фазе, не подменять подготовку плана немедленной вёрсткой.

Ожидаемый результат подготовки: инвентаризация экранов и состояний, границы компонентов, модель взаимодействия с будущим API, последовательность этапов, зависимости, задачи субагентов и критерии проверки. Не требуется заново выбирать криптографические алгоритмы на этом этапе.

## Два направления работы

### Сначала: макеты, композиция и представление

- У шифрованных чатов есть отдельный дизайн и собственный сайдбар/настройки. Точное место нового раздела в навигации ещё нужно подтвердить по макетам и текущему приложению.
- Основной новый визуальный объём — сайдбар с настройками. Именно на него направить основной разбор Figma и вёрстку.
- Существующий список сообщений и обычные bubble-компоненты преимущественно переиспользовать. Пользователь отдельно указал: на повторное изучение обычных bubble-макетов не тратить основной ресурс.
- Появляются специальная иконка защищённого чата, представления с блюром и служебные сообщения о ключах. Служебные строки добавить в план, но подробную их вёрстку можно делать постепенно.
- Компоненты представления должны быть без бизнес-логики. Они могут иметь предметные названия и жить в feature/widget, но получают готовые данные, состояния и callbacks через props.
- Не проводить общий рефакторинг существующего мессенджера ради этого принципа. Улучшать границы только в затронутых компонентах.

### Затем: модель, сценарии и подключение

- Отдельно определить состояния доступа, поколения ключей, корреляцию запросов/ответов и их отображение.
- Проверки прав, API, store, выбор поколения и операции провайдера относятся к доменной/сценарной логике, не к визуальным компонентам.
- Криптографический провайдер и постоянное хранение подключаются через уже подготовленные интерфейсы. Выбор библиотеки, схемы и генерацию идентичности устройств можно решать позже.
- Не дублировать существующие message store, загрузку истории, realtime или auth/runtime ради отдельного визуального раздела.

## Чтение Figma: именно Figma Bridge MCP

- Пользователь явно указал Figma Bridge MCP. Не заменять его обычным Figma connector по умолчанию. В текущей сессии инструменты Bridge доступны; наличие подключения конкретного файла после компакта нужно проверить заново.
- Загрузить skills `figma` и `figma:figma-design-to-code` перед design context и будущей реализацией. Следовать реальным схемам Bridge: не передавать параметры обычного connector, если их нет у Bridge.
- Начать с `mcp__figma_bridge__list_files`. В подключённой копии `fileKey` может отличаться от URL и иметь вид `unsaved-...`; использовать актуальный ключ из списка, не старые сохранённые значения.
- Получить нужные узлы через `get_node` с ID через двоеточие, контекст через `get_design_context`, визуальные эталоны через `get_screenshot`. Читать ограниченные поддеревья вместо всего файла.
- У Bridge `get_design_context` читает selection/page. Если необходим `set_selection`, оркестратор последовательно управляет выбором; параллельные агенты не должны менять общую selection. Для параллельных запросов использовать explicit node IDs там, где они поддерживаются.
- Передавать агентам небольшие выдержки: узлы, размеры, токены, ассеты, скриншоты и состояния. Не рассылать всему дереву огромный Figma-ответ.
- Figma не редактировать: нужны чтение и реализация компонентов в репозитории. Не создавать новые страницы или дубли макетов.
- При отсутствии подключения сообщить точный сбой и запросить подключение нужного файла/plugin. Продолжать независимый аудит кода. Не заявлять визуальное соответствие по неподтверждённым размерам.

## Принятые решения: не открывать их заново без причины

- Пять payload `kind`: `e2ee`, `key_request`, `key_grant`, `key_announced`, `key_reject`. Четыре из них служебные; `e2ee` — пользовательское зашифрованное сообщение. Универсальный `system.type` не вводить.
- У каждой генерации ключа чата есть пара публичного/приватного ключей и `key_uuid`. Устройство имеет собственную идентичность и пару ключей для получения доступа.
- `device_id` задаётся клиентом. Backend не удостоверяет этот ID и не предоставляет отдельную криптографическую проверку устройства. Автор аккаунта берётся из внешней структуры сообщения и подтверждается доверенным backend.
- `device_name` передаётся в `key_request`; локально это `deviceName` рядом с `deviceId`. Это отображаемое имя, не идентификатор. Генерацию имени и ID пока не реализовывать и не превращать в блокер каркаса.
- Запрос ключа не требует особой привилегии сверх возможности отправлять сообщения в чат. Выдавать ключ через приложение могут только пользователи с разрешёнными правами чата и нужным приватным ключом.
- Права выдачи пока проверяет клиент по данным о правах чата. Специальные серверные права возможны позднее, но первая фаза на них не опирается. Отдельные подписи устройства и защита от взлома аккаунта не входят в текущий scope.
- Провайдер получает/возвращает байты. API-адаптер преобразует байты в обычный Base64 с padding: `e2ee`/`key_grant` используют `content`, `key_request`/`key_announced` — `public_key`. Для `key_reject` криптографических байтов нет. Отдельного поля `bytes` в backend нет.
- Не добавлять `formatVersion`, `suiteId`, дополнительные серверные поля или скрытые заголовки версии/схемы внутрь `content`/`public_key`. Версионирование и смена несовместимых форматов отложены.
- Дополнительные лимиты полей сейчас не проектировать; пользователь решил опираться на стандартную валидацию backend. Не возвращать этот вопрос как обязательный блокер.
- Хранилище ключей отделено от message cache. Очистка кэша сообщений не должна удалять идентичность устройства и приватные ключи.
- Перевыпуск поколения не отзывает старые ключи и не запрещает сообщения на старом поколении. Не обещать строгий отзыв доступа.

## Что уже есть и что пока предполагается

- [Черновик](E2EE_CHAT_DRAFT.md) описывает будущий контракт. Предложение `e2ee: boolean` на стриме и ограничения допустимых `kind` ещё не подтверждают реализованную серверную поддержку.
- Два файла интерфейсов готовы; настоящих провайдера, storage, API-адаптера и UI-сценариев пока нет.
- В этой сессии фронтовые DTO/guards и backend payload selector принимали только `markdown`. Последний осмотренный Python backend: `master`, `7604087`; это снимок, после компакта проверить заново. Отсутствие E2EE в текущем API не мешает изолированному preview, но не позволяет объявить серверную интеграцию работающей.
- В примерах черновика ещё встречается «HPKE-конверт», хотя выбор реализации открыт. При окончательной редакции отделить пример возможной схемы от обязательного wire-контракта.
- Простое добавление DTO недостаточно: определить путь parse → domain → message store → render и одинаковую обработку истории/REST/realtime. Не выдавать служебные сообщения за Markdown.

## План работы оркестратора через субагентов

На следующем запуске использовать collaboration subagents, а не создавать отдельные пользовательские чаты. Сейчас субагенты не запускались: это намеренно оставлено на фазу после компакта.

1. Главный агент восстанавливает контекст, проверяет дерево и подключение Bridge, фиксирует границы текущей фазы.
2. Запускает до трёх субагентов по независимым read-only задачам, с конкретными входами и ожидаемым результатом:
   - **Макеты/компоненты:** инвентаризация узлов, состояний, токенов и взаимодействий. Основной фокус `11026:27080`; общий блок нужен для контекста, `11026:27023` — для списка будущих служебных строк. Результат: матрица экран/состояние/компонент, Figma node IDs, props и reuse-кандидаты. Выводы привязать к реально прочитанным узлам.
   - **Текущая архитектура:** проверить маршруты, shell/sidebar, список сообщений, существующие UI-примитивы и допустимые FSD-зависимости. Результат: карта точек подключения, существующих компонентов, минимальных изменений и рисков регрессии.
   - **Контракты и состояния:** сверить пять `kind`, interfaces, права и корреляцию. Результат: модель состояний, таблица переходов, входы/выходы сценариев, путь API-адаптации и незакрытые вопросы. Криптоалгоритмы и серверные изменения не реализовывать.
3. Оркестратор сводит выводы, разрешает расхождения и собирает короткий список вопросов, действительно не закрываемых макетами/кодом. Не спрашивать снова о принятых решениях выше.
4. Составляет окончательный план с этапами и проверками, разделяя дизайн, локальную модель, preview, интеграцию API и настоящую криптографию. Указывает, что можно делать независимо и что требует внешнего контракта.
5. При переходе к реализации назначает агентам непересекающиеся файлы/компоненты. Общие типы, composition и integration files имеют одного владельца; при зависимости агент сначала получает согласованный интерфейс. Все агенты делят одно дерево.
6. В фазе реализации использует отдельный проход субагента для review границ представления и бизнес-логики, затем оркестратор проверяет итоговую интеграцию и фактические результаты проверок.

## Критерий компонентов без бизнес-логики

- Разрешены props, визуальные варианты, доступность, focus/keyboard и локальное состояние открытия визуального элемента.
- Через props приходят display data, ready/loading/error/locked состояния, доступность действий и callbacks.
- В компонентах представления нет API-запросов, вызовов криптографии, чтения секретов, проверки ролей, выбора поколения, обработки realtime и бизнес-записей в store/cache.
- Domain/feature controller преобразует данные в view model и выполняет операции. Widget/page композирует представление и controller в соответствии с FSD; не складывать всю бизнес-логику в route.
- Не требовать превращения каждой мелкой части в `shared/ui`. Предметный компонент может принадлежать feature, если его представление остаётся управляемым через props.
- Preview должен показывать тот же компонент, который будет подключён к реальной модели. Не делать параллельную демонстрационную копию UI.

## Вопросы для окончательного плана

Сначала искать ответы в указанных узлах Figma и актуальном коде. Вопросы ниже не означают, что все они блокируют первый UI-этап.

### Дизайн и продукт

1. Новый мессенджер — отдельный маршрут/раздел или режим текущего shell? Где вход и как возвращаемся в обычные чаты?
2. Что именно включает сайдбар с настройками: список чатов, настройки конкретного чата, общие настройки режима, drawer/right panel? Какие компоненты и состояния действительно видны в макете?
3. Где появляется блюр: preview строки сайдбара, тело закрытого сообщения, header или несколько мест? Какие состояния скрывают его, что доступно для взаимодействия? Закрытое содержимое рисовать заглушкой без отсутствующего plaintext.
4. Какие настройки меняют локальный UI, какие требуют API, какие относятся к ключам? Не подключать неподтверждённые серверные действия как успешные.
5. Входит ли создание защищённого чата в первый этап, какие поля/участники/роли нужны? Если макет не содержит этого сценария, уточнить его отдельно.
6. Что входит в первую визуальную поставку: sidebar/settings, иконка, locked preview; какие служебные строки можно подключить следующим небольшим этапом?
7. Какие responsive/desktop/Electron состояния обязательны? Не придумывать отдельный мобильный дизайн при отсутствии требования.

### Модель и сценарии

8. Каким существующим ролям соответствует право выдачи? До уточнения визуальный компонент получает готовое `canGrantKey`, а решение остаётся в controller.
9. Можно ли отправлять без приватного ключа при известном публичном? Черновик допускает такую техническую возможность, но продуктовая политика ещё не выбрана.
10. Как выбирается поколение по умолчанию, как отображается частично доступная история? Не сводить доступ ко всему чату к одному boolean.
11. Как создаётся первое объявление поколения? `decryptChatKeyGrant` ожидает известный публичный ключ чата: нужно обеспечить получение `key_announced` или явно согласовать другой источник.
12. Как запросы/выдачи/отказы коррелируются при повторных запросах, нескольких ответах, загрузке старой истории и событиях не по порядку? `request_message_uuid` ссылается на внешнюю UUID исходного запроса.
13. Как ведут себя composer и действия сообщения в locked/loading/error состояниях? Отдельно определить возможности copy/edit/delete/forward/reactions для служебных строк, не наследовать их автоматически от Markdown.

### Подключение и границы этапов

14. Первую поставку делаем как изолированный локальный preview или уже в рабочем shell за явным capability? Backend пяти новых `kind` пока может быть не готов. Тестовый провайдер не должен попадать в обычную отправку E2EE.
15. Кто и когда реализует будущий backend-контракт? Запрос на UI-план не является разрешением редактировать соседние backend-репозитории. Зафиксировать зависимости и контрактные требования отдельно.
16. Какие UI-состояния/настройки персистентны? Не сохранять plaintext в существующий общий durable message cache автоматически; границу расшифрованного представления проверить при проектировании модели.

### Намеренно отложено

Выбор HPKE/другой схемы и библиотеки; постоянное хранение секретов; генерация device ID/name; версии/идентификаторы схем; особые лимиты; серверная привилегия выдачи; строгий отзыв; восстановление/резервные копии; полный scope вложений, поиска и уведомлений. При необходимости записать зависимость будущего этапа, не блокировать этим разбор sidebar/settings и подготовку модели.

## Как должен выглядеть окончательный план

Для каждого этапа указать цель, входные решения, компоненты/границы, владельца-субагента, зависимости, наблюдаемый результат, критерии приёмки и проверки. Названия/количество новых компонентов определить после макетов и reuse-аудита.

Рекомендуемый порядок уточняется по результатам аудита:

1. Инвентаризация Figma и reuse-карта; согласование props/view models.
2. Представление sidebar/settings и защищённых состояний на фиксированных preview data.
3. Локальная модель доступа и сценарии на тестовых provider/storage; маленькие служебные строки по мере подключения сценариев.
4. API DTO/адаптеры/история/realtime после подтверждения backend-контракта.
5. Реальный провайдер и постоянное хранение после выбора реализации; отдельная проверка совместимости.

Дизайн и модель имеют общую границу props/view model: не верстать абстрактный sidebar без понимания его состояний, но и не ждать выбора криптобиблиотеки ради компонентов представления.

## Проверки и ограничения отчёта

- При подготовке плана: проверить все локальные ссылки, согласованность с черновиком и реальное наличие точек подключения; `npm run docs:check`, Prettier затронутых документов, `git diff --check`.
- В будущей реализации: focused tests для поведения, typecheck Web/Electron, ESLint/Prettier по изменённым файлам. Сценарии async owner switch и out-of-order key responses проверять, когда появится соответствующая логика.
- UI проверять в браузере по Figma: sidebar/settings, иконка, locked/loading/error состояния, клавиатура/focus. Если нет рабочего backend, изолированный preview обеспечивает визуальную проверку, но не доказывает серверную интеграцию.
- Не менять обычные чаты вне необходимой интеграции. Не заявлять manual/Electron/реальную криптографическую QA по одним unit tests.
- Не коммитить, не пушить и не создавать PR без запроса. Не редактировать Figma или backend в рамках текущей подготовки.

## Быстрый запуск после компакта

Если пользователь говорит «план», открыть эту записку и черновик, восстановить принятые решения, проверить Bridge и дерево, запустить read-only субагентов по направлениям выше. Затем представить окончательный план и только оставшиеся существенные вопросы. Не просить повторно уже предоставленные Figma-ссылки и не возвращать отложенные решения в обязательные блокеры.
